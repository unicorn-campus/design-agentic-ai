# 사내 웹 페이지 기반 커넥터 개발 방안

> **설계 지침 문서(실행 검증 없음)**  
> 이 문서에 나오는 커넥터를 실제로 구현하거나 호출 시험을 하지 않았음.  
> 공개된 공식 문서와 표준 규격을 조회해 정리한 설계 지침이며, 동작 확인 결과가 아님.  
> 작성: 커넥니(도구 연동 엔지니어)

---

## 질문

사내 업무 자동화를 위해 자체 제작된 웹 페이지와 연동할 커넥터를 어떻게 개발할 수 있는지.

---

## 한눈에 보는 답

1. 웹 페이지는 껍데기이고, 그 뒤에 거의 항상 **HTTP API**가 있음. 화면을 흉내 내기 전에 그 API부터 찾음.
2. 우선순위는 **① 기존 API 재사용 → ② 전용 API 또는 MCP 서버 신설 → ③ 브라우저 자동화 → ④ 화면 이해 자동화** 순서임.
3. 아래로 내려갈수록 느리고 잘 깨지므로, ③과 ④는 "앞의 둘이 불가능할 때만"임 [5][8].
4. 어느 방식을 고르든 바깥에 노출하는 겉모습은 **MCP 서버 하나로 통일**하면 에이전트 쪽 코드가 바뀌지 않음 [1].
5. 쓰기 작업(제출, 승인, 결재, 삭제)은 **기본 거부**로 시작해 사람 승인을 반드시 끼움 [1][9][10].

---

## 1. 먼저 알아야 할 것: 웹 페이지의 층 구조

자체 제작 사내 웹 페이지는 보통 세 층으로 되어 있음.

```
[사람이 보는 화면]  ← 브라우저가 그린 HTML
       ↑ fetch/XHR (화면이 뒤에 몰래 보내는 HTTP 요청)
[백엔드 API]        ← 실제 업무 처리 로직
       ↑
[데이터베이스]
```

- **XHR 또는 fetch**: 화면을 새로 고치지 않고 화면 뒤에서 서버와 데이터를 주고받는 HTTP 호출을 뜻함.
  목록을 스크롤할 때 새 항목이 스르륵 붙는 것이 이 호출의 결과임.

커넥터를 만든다는 것은 **이 세 층 중 어디에 손을 댈지 고르는 일**임.  
아래로 깊이 붙을수록 빠르고 안정적이며, 위(화면)에 붙을수록 만들기는 쉽지만 잘 깨짐.

## 2. 연동 지점 선택지 4가지

### 선택지 ① 웹 페이지가 이미 호출하는 백엔드 API 재사용

**원리**  
브라우저 개발자 도구의 네트워크 탭을 켜고 사람이 평소처럼 화면을 조작함.  
그때 기록되는 요청(주소, 메서드, 헤더, 요청 본문, 응답 본문)을 모아 API 명세로 옮겨 적음.  
그 명세를 **OpenAPI 문서**로 정리한 뒤, 그 문서를 보고 커넥터를 만듦.

- **OpenAPI**: HTTP API가 어떤 주소로 무엇을 받고 무엇을 돌려주는지를 적는 표준 서식임.
  사람과 프로그램이 모두 읽을 수 있고, 소스 코드를 보지 않아도 서비스 사용법을 알 수 있게 하는 것이 목적임 [11].

**장점**

- 화면 구조가 바뀌어도 API 주소와 필드가 그대로면 커넥터가 살아 있음
- 응답이 이미 구조화된 데이터(JSON)라 추가 해석이 필요 없음
- 가장 빠르고 가장 싸며, 기존 시스템 코드를 한 줄도 고치지 않아도 됨

**단점**

- 공개를 전제로 만든 API가 아니므로 예고 없이 바뀔 수 있음
- 로그인 상태(세션)에 묶여 있어 그대로 쓰면 인증 문제가 생김(5절 참고)
- 화면에만 있는 유효성 검사를 건너뛸 수 있어, 에이전트가 화면이 막던 값을 넣어 버릴 위험이 있음

**적합한 경우**  
읽기 작업이 대부분이고, 해당 페이지가 오래 유지되어 왔으며, 운영 부서와 "이 API를 쓰겠다"고 합의할 수 있을 때.

**반드시 할 일(의견)**  
관찰로 알아낸 API라도 **해당 시스템 담당 부서의 사용 승인**을 받고, 변경 시 알려 달라는 약속을 문서로 남김.  
승인 없이 쓰면 상대편에서는 정체불명의 트래픽이고, 어느 날 조용히 끊김.

---

### 선택지 ② 백엔드에 에이전트 전용 API 또는 MCP 서버를 새로 추가

**원리**  
사내 자체 제작 시스템이면 소스 코드가 우리 손에 있음.  
그러면 화면을 흉내 내지 말고 **업무 단위로 새 입구를 하나 만드는 것**이 정석임.  
기존 화면과 기존 API는 그대로 두고, 그 옆에 에이전트가 부를 입구를 붙인 뒤 조금씩 옮겨 감.

이 "기존 것을 그대로 둔 채 옆에서 새 길을 키우고 서서히 넘기는" 방식을 **스트랭글러 피그(Strangler Fig) 패턴**이라 부름.  
낡은 시스템을 한 번에 갈아엎지 않고 점진적으로 교체하는 접근을 가리키는 이름으로 널리 쓰임 [17].

**MCP로 노출하는 경우**  
MCP(Model Context Protocol)는 에이전트가 쓸 도구를 표준 서식으로 내놓는 규격임.  
도구 하나는 이름, 설명, 입력 스키마, (선택) 출력 스키마, (선택) 주석으로 기술됨 [1].

- **스키마**: 어떤 필드가 어떤 타입으로 들어오고 나가는지를 적은 약속 표임.

**장점**

- 업무 의미 단위로 입구를 설계할 수 있음(화면 클릭 순서가 아니라 "휴가 신청 제출" 같은 단위)
- 권한 범위를 에이전트 전용으로 좁게 끊을 수 있음
- 여러 에이전트와 여러 클라이언트가 같은 도구를 재사용함
- 화면 변경과 완전히 분리됨

**단점**

- 대상 시스템에 코드를 추가해야 하므로 배포와 검토 절차가 필요함
- 해당 시스템 담당 조직의 작업 일정에 의존함

**적합한 경우**  
소스 접근이 가능하고, 쓰기 작업이 있으며, 오래 쓸 연동일 때. **가장 권장하는 기본값임.**

### 선택지 ③ 브라우저 자동화로 화면 조작

**원리**  
실제 브라우저를 프로그램이 대신 조작함. 로그인하고, 버튼을 누르고, 입력란을 채우고, 결과 글자를 읽음.  
대표 도구가 Playwright임.

Playwright 공식 문서는 **화면 구조(DOM)에 의존하는 선택자를 피하라**고 명시함.  
CSS 클래스로 버튼을 찾으면 디자이너가 클래스 이름만 바꿔도 깨지기 때문임 [5].  
대신 사람이 실제로 보는 속성, 즉 역할과 이름으로 찾기를 권함(예: `getByRole('button', { name: 'Sign in' })`) [5][6].

- **DOM**: 브라우저가 HTML을 읽어 만든 화면의 뼈대 구조임.
- **선택자**: 그 뼈대에서 특정 요소 하나를 집어내는 주소 표현임.

Playwright의 로케이터는 **자동 대기**와 **재시도** 기능을 갖고 있어, 요소가 보이고 눌릴 수 있는 상태가 될 때까지 기다림 [5][6].

```javascript
// 좋은 예: 사람이 보는 역할과 이름으로 찾음 (화면 구조가 바뀌어도 잘 버팀)
await page.getByRole('button', { name: '신청서 제출' }).click();

// 피할 예: CSS 클래스에 의존 (클래스 이름만 바뀌어도 깨짐)
await page.locator('button.btn-primary.submit-icon').click();
```

브라우저 조작을 MCP 도구로 바로 노출하는 방법도 있음.  
`microsoft/playwright-mcp`는 화면 픽셀이 아니라 **접근성 트리(화면 요소의 역할과 이름을 담은 구조 정보)** 를 사용하며,  
시각 모델이 필요 없고 동작이 결정적이라고 README가 밝힘 [7].

**장점**

- 소스 접근이 전혀 없어도 됨
- 사람이 화면에서 할 수 있는 일은 원칙적으로 다 할 수 있음
- 화면단 유효성 검사를 그대로 통과하므로 잘못된 값이 들어갈 위험이 ①보다 낮음

**단점**

- 느림(브라우저를 실제로 띄우고 화면을 기다림)
- 화면 개편 시 깨짐
- 로그인, 2단계 인증, 캡차 같은 관문이 자동화를 막음
- 운영 비용이 큼(브라우저 실행 환경 유지)

**적합한 경우**  
소스를 고칠 수 없고 화면 밖에 쓸 만한 API도 없을 때. 읽기 위주이고 호출 빈도가 낮을 때.  
**최후 수단에 가까운 선택지임.**

### 선택지 ④ 화면 이해 기반 자동화(Computer use, VLM)와 RPA 도구

**원리**  
화면을 그림으로 찍어 모델에게 보여 주고, 모델이 "여기를 눌러"라고 좌표를 내놓으면 그대로 누름.  
Anthropic의 computer use 도구가 이 방식임 [8].  
RPA 도구도 비슷한 축에 있음. Microsoft Power Automate의 desktop flows는 화면 요소, 이미지, 좌표로  
애플리케이션을 조작하며 터미널 에뮬레이터 같은 낡은 응용 프로그램까지 자동화 대상으로 삼는다고 소개함 [18].

- **VLM**: 그림을 보고 내용을 이해하는 모델을 말함.
- **RPA**: 사람이 하던 화면 조작을 소프트웨어가 대신 반복하게 하는 자동화 방식임.

**Anthropic 공식 문서가 밝힌 한계** [8]

| 한계 | 문서가 적은 내용 |
|------|------------------|
| 지연 | 사람이 직접 조작하는 것보다 느릴 수 있어, 속도가 중요하지 않은 용도를 권함 |
| 좌표 정확도 | 좌표를 내놓을 때 실수하거나 없는 것을 지어낼 수 있음 |
| 도구 선택 정확도 | 보기 드문 응용 프로그램이나 여러 창을 동시에 다룰 때 신뢰도가 떨어질 수 있음 |
| 스크롤 | 스크롤이 먹지 않는 화면이 있어 키보드 대안이 필요할 수 있음 |
| 프롬프트 인젝션 | 웹 페이지나 이미지에 심긴 지시에 영향받을 수 있음 |

같은 문서는 **완벽한 정확도가 필요한 작업이나 민감한 정보를 다루는 작업을 사람 감독 없이 맡기지 말라**고 적음 [8].

**적합한 경우**  
① ~ ③이 모두 불가능한 경우. 예를 들어 선택자가 잡히지 않는 그림 기반 화면이거나,  
자동화 금지 정책 때문에 브라우저 제어가 막혀 있고 화면 캡처 판독만 허용되는 경우.  
그리고 **속도가 중요하지 않고 사람이 결과를 검토하는 용도**일 때.

## 3. 선택 판정표

아래 조건을 위에서부터 확인해 처음 맞는 행의 선택지를 씀.

| 순서 | 소스 고칠 수 있나 | 쓸 만한 API 있나 | 쓰기 작업인가 | 화면 변경 잦나 | 지연 요구 | 추천 |
|------|------------------|------------------|---------------|----------------|-----------|------|
| 1 | 예 | 있음 또는 없음 | 예 | 상관없음 | 상관없음 | **② 전용 API 또는 MCP 신설** |
| 2 | 예 | 없음 | 아니오 | 상관없음 | 빠름 필요 | **② 전용 API 또는 MCP 신설** |
| 3 | 아니오 | 있음(관찰로 확인) | 아니오 | 잦음 | 빠름 필요 | **① 기존 API 재사용** |
| 4 | 아니오 | 있음(관찰로 확인) | 예 | 상관없음 | 상관없음 | **① + 사람 승인 필수**, 가능하면 ②로 전환 추진 |
| 5 | 아니오 | 없음 | 아니오 | 드묾 | 느려도 됨 | **③ 브라우저 자동화** |
| 6 | 아니오 | 없음 | 예 | 드묾 | 느려도 됨 | **③ + 사람 승인 필수**(건당 확인) |
| 7 | 아니오 | 없음 | 상관없음 | 잦음 | 느려도 됨 | **④ 화면 이해 자동화**, 결과 사람 검토 전제 |

**해석 요령**

- 3행과 5행이 "잦음 / 드묾"으로 갈리는 이유: 화면 변경이 잦으면 화면에 붙는 ③이 계속 깨지므로 ①이 나음 [5].
- 7행은 선택지가 없어서 고르는 자리임. 성공률을 보장할 수 없으므로 사람 검토를 전제로만 운영함 [8].
- 1행과 2행이 조건을 거의 따지지 않는 이유: 소스를 고칠 수 있으면 ②가 항상 더 안전하고 오래 감(의견).

## 4. 커넥터를 MCP 서버로 감싸기

어느 선택지를 골랐든, **에이전트 쪽에서 보이는 겉모습은 MCP 도구로 통일**하기를 권함(의견).  
그러면 나중에 ③에서 ②로 갈아탈 때 에이전트 코드가 그대로임.

### 4-1. 도구 명세 작성

MCP 도구는 이름, 설명, 입력 스키마, 선택적 출력 스키마, 선택적 주석으로 기술됨 [1].

| 도구명 | 하는 일 | 입력 | 출력 | 부작용 | 승인 필요 |
|--------|---------|------|------|--------|-----------|
| `search_request` | 신청 건 목록 조회 | `{keyword, from_date, to_date, limit}` | 신청 건 요약 목록 | 없음(읽기) | 불필요 |
| `get_request_detail` | 신청 건 한 건 상세 조회 | `{request_id}` | 신청 건 상세 | 없음(읽기) | 불필요 |
| `create_request_draft` | 신청서 임시 저장 | `{form_type, fields}` | 임시 저장 ID | 있음(쓰기, 되돌릴 수 있음) | 불필요 |
| `submit_request` | 신청서 최종 제출 | `{draft_id, idempotency_key}` | 접수 번호 | 있음(쓰기, 되돌리기 어려움) | **필요** |

- 예시는 가상의 "휴가 신청 페이지"를 가정한 것이며 실제 사내 시스템이 아님.
- **되돌릴 수 있는 쓰기(임시 저장)와 되돌리기 어려운 쓰기(최종 제출)를 반드시 다른 도구로 나눔**(의견).
  그래야 사람 승인을 마지막 한 번만 받으면 됨.

```json
{
  "name": "submit_request",
  "title": "신청서 제출",
  "description": "임시 저장된 신청서를 최종 제출함. 되돌리기 어려운 작업이며 사람 승인이 필요함.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "draft_id":        { "type": "string", "description": "create_request_draft가 돌려준 임시 저장 ID" },
      "idempotency_key": { "type": "string", "description": "같은 제출이 두 번 가도 한 번만 처리되게 하는 표식" }
    },
    "required": ["draft_id", "idempotency_key"]
  },
  "outputSchema": {
    "type": "object",
    "properties": {
      "receipt_no": { "type": "string" },
      "status":     { "type": "string", "enum": ["ACCEPTED", "DUPLICATE"] }
    },
    "required": ["receipt_no", "status"]
  }
}
```

### 4-2. 허용 도구를 최소로 둠

사내 커넥터 설계 표준은 "MCP 서버가 제공하는 도구 중 이 워크플로우가 호출할 도구만 적음"을 원칙으로 둠  
(`references/design-workflow-connector.md` 3-3절).  
OWASP도 같은 방향을 권함. LLM 에이전트가 부를 수 있는 확장을 꼭 필요한 최소로 줄이고,  
각 확장의 기능도 최소로 줄이라고 명시함 [10].

### 4-3. MCP 서버 자체의 보안 설정

| 항목 | 지침 | 근거 |
|------|------|------|
| Origin 헤더 검사 | 들어오는 모든 연결의 `Origin` 헤더를 검사해 DNS 리바인딩 공격을 막아야 함(MUST) | [4] |
| 로컬 바인딩 | 로컬 실행 시 모든 네트워크 대역이 아니라 `127.0.0.1`에만 묶기를 권함(SHOULD) | [4] |
| 도구 주석 신뢰 | 신뢰할 수 있는 서버에서 온 것이 아니면 도구 주석을 믿지 않아야 함(MUST) | [1] |
| 사람 개입 | 도구 호출을 거부할 수 있는 사람이 흐름 안에 있어야 함(SHOULD) | [1] |

- **DNS 리바인딩**: 공격자가 만든 웹 페이지가 주소 해석을 바꿔치기해 내 컴퓨터 안의 서버를 몰래 부르게 만드는 수법임.

## 5. 인증과 권한

### 5-1. 로그인 세션 쿠키를 그대로 쓰면 안 되는 이유

브라우저 자동화를 하면 "사람 계정으로 로그인해서 쿠키를 저장해 두고 계속 쓰자"는 생각이 먼저 떠오름.  
이 방식을 기본으로 삼지 않기를 권함. 이유는 아래와 같음.

| 문제 | 설명 | 근거 |
|------|------|------|
| 권한이 과도함 | 그 사람이 할 수 있는 모든 일을 에이전트도 할 수 있게 됨. 최소 권한 원칙에 어긋남 | [9][10] |
| 책임 추적 불가 | 감사 로그에 사람 이름만 남아 에이전트가 한 일인지 구분되지 않음 | 의견 |
| 비밀번호를 넘기게 됨 | 아이디와 비밀번호를 클라이언트에 주는 방식(ROPC)은 **쓰면 안 됨(MUST NOT)**. 2단계 인증과도 맞지 않음 | [13] |
| 세션 만료와 CSRF 토큰 | 세션은 끊기고 CSRF 토큰은 갱신되므로 쿠키만으로는 오래 못 감 | [16] |

- **CSRF**: 사용자가 로그인한 상태를 노려 다른 사이트가 몰래 요청을 보내게 만드는 공격임.
  막는 방법으로 서버가 발급한 일회성 토큰을 요청마다 함께 보내는 동기화 토큰 방식과 `SameSite` 쿠키 설정이 쓰임 [16].

### 5-2. 권장 인증 방식

| 상황 | 권장 방식 | 설명 | 근거 |
|------|-----------|------|------|
| 에이전트가 시스템 권한으로 조회 | 서비스 계정 + Client Credentials | 클라이언트 자기 자격만으로 토큰을 받는 방식. 기밀 클라이언트만 써야 함 | [12] |
| 에이전트가 특정 사용자를 대신해 작업 | OAuth 2.0 권한 위임 + 최소 scope | 사용자가 동의한 범위만 토큰에 담김. `scope`는 공백으로 구분한 문자열 목록임 | [12] |
| MCP 서버를 보호할 때 | OAuth 2.1 기반, 토큰 대상자 검증 | MCP 서버는 자신을 대상으로 발급된 토큰인지 반드시 확인해야 함(MUST) | [2] |
| 공개 클라이언트가 있을 때 | PKCE 적용 | 공개 클라이언트는 PKCE를 반드시 써야 함(MUST) | [13] |
| 네이티브 앱에서 로그인할 때 | 외부 브라우저 사용 | 앱 안에 끼워 넣은 브라우저 대신 사용자의 브라우저를 쓰도록 요구함 | [14] |

- **scope**: 토큰이 할 수 있는 일의 범위를 적은 꼬리표임. 좁게 끊을수록 사고 영향이 작아짐.
- **PKCE**: 인가 코드를 중간에서 가로채도 쓸 수 없게 만드는 추가 확인 절차임.

### 5-3. 토큰 취급 규칙

| 규칙 | 내용 | 근거 |
|------|------|------|
| 토큰 통과 금지 | 받은 토큰을 검증 없이 뒷단으로 그대로 넘기는 것은 MCP 사양이 **명시적으로 금지**하는 안티패턴임 | [3] |
| 대상자 검증 | 토큰이 나를 대상으로 발급된 것인지 반드시 확인함(MUST) | [2] |
| 리프레시 토큰 보호 | 공개 클라이언트의 리프레시 토큰은 발신자에 묶이거나 1회용이어야 함(MUST) | [13] |
| 대리 혼동 방지 | 프록시 역할을 하는 MCP 서버는 "혼동된 대리인" 문제를 막는 조치를 해야 함(MUST) | [3] |
| 저장 위치 | 비밀값 저장소에만 두고, 코드와 이미지와 로그와 프롬프트에 절대 넣지 않음 | 팀 규칙 |

- **혼동된 대리인(confused deputy)**: 권한 있는 중간 프로그램이 속아서 남의 권한으로 일을 해 주는 문제를 말함 [3].
- **토큰 통과(token passthrough)**: 클라이언트가 준 토큰을 검사도 하지 않고 뒷단 시스템에 그대로 전달하는 행위임 [3].

> 실제 키, 토큰, 사내 주소는 이 문서에 적지 않음. 설정 예시는 `{BASE_URL}`, `{CLIENT_ID}` 같은 자리표시자만 씀.

## 6. 안전장치

### 6-1. 쓰기 작업 승인 지점

MCP 사양은 도구 호출을 거부할 수 있는 사람이 흐름 안에 있어야 한다고 적고,  
애플리케이션이 호출 시 확인 창을 띄울 것을 권함 [1].  
OWASP도 권한이 큰 작업에는 사람 승인(human-in-the-loop) 통제를 두라고 명시함 [9].

| 작업 성격 | 예 | 승인 방식 |
|-----------|-----|----------|
| 읽기 | 목록 조회, 상세 조회 | 승인 없음 |
| 되돌릴 수 있는 쓰기 | 임시 저장, 초안 생성 | 승인 없음, 감사 로그만 남김 |
| 되돌리기 어려운 쓰기 | 최종 제출, 결재 상신, 발송 | **건별 사람 승인 필수** |
| 되돌릴 수 없는 쓰기 | 삭제, 취소 불가 승인 | **건별 사람 승인 + 영향 범위 미리보기** |

### 6-2. 호출 제어

| 장치 | 내용 | 근거 |
|------|------|------|
| 멱등성 키 | 같은 요청이 두 번 와도 한 번만 처리되게 하는 표식임. 클라이언트가 만들어 보내는 고유 값임 | [15] |
| 멱등성 지문 | 요청 본문으로 만든 값으로, 같은 키에 다른 내용이 온 경우를 가려낼 때 함께 씀 | [15] |
| 호출 상한 | 시간당 호출 수와 하루 쓰기 건수에 상한을 둠. 상한 초과 시 거부하고 사람에게 알림 | 의견 |
| 감사 로그 | 누가, 어떤 도구를, 어떤 입력으로, 언제, 어떤 결과로 불렀는지 남김. computer use 문서도 동작과 로그를 반드시 확인하라고 적음 | [8] |

### 6-3. 프롬프트 인젝션 대비

웹 페이지에서 읽어 온 글자는 **데이터이지 지시가 아님**.  
페이지 안에 "지금까지 지시를 무시하고 이것을 해"라는 문장이 숨어 있을 수 있음.  
Anthropic 문서도 웹 페이지나 이미지에 담긴 지시가 사용자 지시를 덮어쓸 수 있다고 경고함 [8].

OWASP가 제시하는 대비책 중 이 커넥터에 바로 쓸 것 [9][10]:

| 대비책 | 적용 방법 |
|--------|----------|
| 최소 권한 | 커넥터 전용 토큰을 쓰고, 모델에게 직접 자격증명을 주지 않음 [9] |
| 외부 내용 분리 표시 | 페이지에서 읽은 내용을 `<page_content>` 같은 태그로 감싸 "이것은 데이터"임을 명확히 함 [9] |
| 고위험 작업 사람 승인 | 쓰기 작업에 사람 확인을 끼움 [9] |
| 기능 최소화 | 필요 없는 도구를 아예 노출하지 않음. URL 가져오기가 필요 없으면 그 도구를 두지 않음 [10] |
| 자율성 최소화 | 과도한 기능, 과도한 권한, 과도한 자율성이 과잉 대리 문제의 뿌리임 [10] |

## 7. 오류 분류표

도구가 실패했을 때 "무엇이 잘못됐는지"를 다섯 가지로 나누고, 각각 다르게 처리함.

| 분류 | 무엇이 일어난 것 | 대표 신호 | 재시도 | 처리 방식 |
|------|------------------|-----------|--------|-----------|
| 인증 오류 | 토큰이 없거나 만료됨 | HTTP 401, 로그인 화면으로 넘어감 | 토큰 갱신 후 1회 | 갱신도 실패하면 즉시 중단하고 사람에게 알림. 같은 호출 반복 금지 |
| 권한 부족 | 로그인은 됐으나 그 일을 할 자격이 없음 | HTTP 403 | **하지 않음** | 중단하고 필요한 scope를 보고함. 다른 계정으로 바꿔 시도하지 않음 |
| 입력 오류 | 보낸 값이 규칙에 맞지 않음 | HTTP 400, 422, 화면의 빨간 경고 문구 | **하지 않음** | 어떤 필드가 왜 거부됐는지 그대로 올려 보냄. 값을 임의로 고쳐 재시도하지 않음 |
| 일시 장애 | 상대가 잠깐 못 받는 상태임 | HTTP 429, 5xx, 연결 시간 초과 | 지수 백오프로 2 ~ 3회 | 쓰기는 멱등성 키를 붙여 재시도함 [15]. 상한 초과 시 안전 종료 |
| 화면 변경 | 찾던 버튼이나 입력란이 사라짐 | 로케이터 시간 초과, 요소 없음 | **하지 않음** | 즉시 중단, 화면 캡처를 증거로 남기고 커넥터 점검 알림 발생 |

- **지수 백오프**: 재시도 간격을 1초, 2초, 4초처럼 점점 늘려 상대 시스템에 부담을 덜 주는 방식임.
- 쓰기 작업을 멱등성 키 없이 재시도하면 중복 제출이 생김. 그래서 멱등성 키는 쓰기 도구의 필수 입력임 [15].

## 8. 단계별 개발 절차

| 단계 | 하는 일 | 산출물 | 끝났다고 보는 기준 |
|------|---------|--------|-------------------|
| ① 관찰 | 개발자 도구 네트워크 탭을 켜고 사람이 업무를 한 번 수행함. 오가는 요청을 기록함 | 요청 기록(주소, 메서드, 헤더, 본문, 응답) | 업무 한 건이 끝까지 재현되는 요청 순서가 기록됨 |
| ② 명세 | 기록을 OpenAPI 문서로 옮기고, 화면 조작 부분은 흐름도로 적음 [11] | OpenAPI 문서, 흐름도, 커넥터 목록(`C-NN`) | 모든 필드에 이름, 타입, 필수 여부, 설명이 있음 |
| ③ 커넥터 구현 | 선택지 ① ~ ④ 중 정한 방식으로 호출 코드를 만듦. 인증, 재시도, 오류 분류를 여기 넣음 | 커넥터 모듈, 오류 분류 매핑 | 7절의 다섯 분류가 모두 코드에 나타남 |
| ④ MCP 노출 | 업무 단위 도구로 감싸고, 읽기와 쓰기를 나누고, 허용 도구를 최소로 둠 [1][10] | 도구 명세표, MCP 서버 설정 | 되돌리기 어려운 도구마다 승인 지점이 지정됨 |
| ⑤ 시험 | 정상 흐름, 인증 만료, 권한 부족, 잘못된 입력, 중복 제출, 화면 변경을 각각 재현함 | 시험 결과 기록 | 여섯 경우 모두 실제로 실행해 결과가 기록됨 |
| ⑥ 운영 감시 | 감사 로그를 쌓고, 실패율과 화면 변경 알림을 지켜봄 | 감사 로그 스키마, 알림 규칙 | 화면 변경 오류가 사람에게 도달하는 경로가 동작함 |

**⑤에 관한 주의**  
"코드가 컴파일된다"와 "커넥터가 동작한다"는 다름.  
각 경우를 실제로 재현해 로그나 응답을 남기기 전에는 완료로 보고하지 않음(팀 정직한 보고 규칙).

## 9. 흔한 실패와 대처

| 증상 | 원인 | 대처 |
|------|------|------|
| 어제까지 되던 클릭이 안 됨 | 화면 개편으로 선택자가 바뀜 | CSS 클래스 대신 역할과 이름으로 찾도록 바꿈 [5][6]. 그래도 바뀌면 ①이나 ②로 전환 검토 |
| 한참 뒤 "요소를 찾을 수 없음" | 화면이 아직 안 그려졌는데 조작함 | 고정 시간 대기 대신 자동 대기 기능이 있는 로케이터를 씀 [5][6] |
| 30분쯤 지나면 전부 실패 | 세션 만료 | 세션 재사용을 그만두고 서비스 계정 또는 OAuth 토큰으로 바꿈 [12][13] |
| 제출만 403으로 막힘 | CSRF 토큰 누락 | 폼이 내려 줄 때 함께 오는 토큰을 그대로 실어 보냄. 토큰은 요청마다 갱신될 수 있음 [16] |
| 2단계 인증 창에서 멈춤 | 사람 확인이 필요한 관문임 | 자동화로 뚫지 않음. 서비스 계정 경로를 따로 발급받음(의견) |
| 같은 신청이 두 건 접수됨 | 재시도가 중복 제출을 만듦 | 쓰기 도구에 멱등성 키를 필수 입력으로 둠 [15] |
| 페이지 글을 읽은 뒤 엉뚱한 일을 함 | 페이지에 숨은 지시(프롬프트 인젝션) | 페이지 내용을 태그로 감싸 데이터로만 취급하고, 쓰기에는 사람 승인을 둠 [9] |
| 좌표를 눌렀는데 엉뚱한 곳이 눌림 | 화면 이해 방식의 좌표 오류 | ④ 대신 ③으로 내려감. 유지한다면 사람 검토를 전제로 운영함 [8] |
| 상대 시스템에서 과도한 호출이라고 항의받음 | 호출 상한 없음 | 시간당 호출 수와 하루 쓰기 건수 상한을 둠(의견) |

## 10. 요약 권고

1. **먼저 네트워크 탭을 켜 봄.** 화면 뒤에 API가 있으면 화면을 조작할 이유가 대부분 사라짐.
2. **소스를 고칠 수 있으면 ②를 고름.** 기존 화면을 그대로 둔 채 옆에 전용 입구를 키우는 방식임 [17].
3. **겉모습은 MCP로 통일함.** 안쪽 구현이 ①에서 ②로 바뀌어도 에이전트는 모름 [1].
4. **읽기와 쓰기를 분리하고, 되돌리기 어려운 쓰기에는 사람 승인을 붙임** [1][9].
5. **권한은 기본 거부부터.** 필요한 도구와 필요한 scope만 엶 [10][12].
6. **페이지에서 읽은 글은 데이터임.** 지시로 실행하지 않음 [9].

## 12. 열린 질문

- 대상 페이지가 단일 페이지 앱인지 서버 렌더링 방식인지에 따라 ①의 관찰 난이도가 크게 달라짐. 대상 확인 필요
- 사내 인증 기반(SSO 제품, OAuth 지원 여부, 서비스 계정 발급 절차)이 확인되지 않아 5-2절 선택지를 좁히지 못함
- 쓰기 작업 승인을 어떤 창구(채팅, 결재 시스템, 별도 승인 화면)로 받을지는 워크플로우 담당(플로니)과 협의 필요
- 호출 상한의 구체 수치는 대상 시스템 용량을 받아야 정할 수 있음
