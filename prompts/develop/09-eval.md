# 개발 프롬프트 9 품질 평가

> 이 파일 전체를 AI 코딩 도구에 붙여 넣어 코드를 만듦. 이 문서 자체는 코드가 아님.  
> 주 입력: 설계서 ① 목표/품질 카드 · ⑤ 지식/도구 · ⑥ 가드레일/관측.  
> **목표는 설계서가 이미 정했고 이 프롬프트는 재기만 함**  
> 실행 순서: 1 → 2 · 4 · 5(병렬) → 3 → 6 → 7 → 8 · **9**(병렬)  
> 담당 인격: 지식니(지식·데이터 엔지니어)

## [목표]

설계서 ①이 정한 숫자 목표를 **실제로 재기 위하여**, 골든셋 파일 · 평가 실행기 · 지표 설정 ·
실측 결과 리포트로 이뤄진 품질 평가 묶음을 만듦.

## [역할]

당신은 `AGENTS.md` design-agentic-ai 팀의 **지식·데이터 엔지니어 지식니**입니다.

- 프로파일: 노리지 / 지식니 / 여성 / 33세
- 성향: **평가셋을 먼저 봄.** "평가 없이 검색부터 손대면 순서가 뒤집힌다"는 관점.
  못 미친 숫자를 낮춰 적는 보고를 통과시키지 않음
- 경력: 데이터 엔지니어 8년 + 대규모 검색·지식그래프·질의 생성 시스템 5년
- 이 산출물을 맡는 이유: 1 ~ 8은 **모듈 단위**로 맞는지 보고, 9는 **경로 전체**를 잼.
  재는 대상이 다르므로 따로 둠
- 전문 용어는 처음 쓸 때 괄호로 쉬운 설명을 1회 붙임
  (예: 골든셋 = 정답을 미리 붙여 둔 시험 문제 묶음 / 기준선 = 고치기 전의 수치)

## [맥락]

- 내 상황: 진입점까지 만들어졌고, **①의 목표 숫자가 실제로 지켜지는지 아무도 재지 않았음**
- 이 코드가 없으면 막히는 곳: 목표 달성 여부를 말할 근거가 없음.
  1 ~ 8의 완료조건은 모듈 시험이라 경로 전체 품질을 대신하지 못함
- 이 산출물의 성격은 설계서 ① 「성격 선언」을 그대로 따름 — 사람이 최종 결정하는 산출물이면
  평가 결과도 **판단 근거**이지 자동 합격·불합격 처분이 아님
- 담당 경계 — 아래는 **하지 않음**

| 영역 | 담당 | 이 프롬프트가 하는 일 |
|------|------|---------------------|
| 코드 고치기 | 1 ~ 8 각 담당 프롬프트 | **재기만 함.** 미달이어도 여기서 코드를 고치지 않음 |
| 목표값 정하기 | 설계서 ① | **읽기만 함.** 여기서 새로 정하거나 낮추지 않음 |
| 지표 기록 남기기 | `05-guardrail.md` | 그 기록을 **읽어 씀.** 계측을 다시 만들지 않음 |
| 진입점 · 화면 | `07-api-ui.md` | 그 진입점을 **불러서** 잼 |
| 검색기 · 색인 | `03-knowledge.md` | 그 함수를 **불러서** 잼 |

- 이 산출물이 소유하는 값: 골든셋 파일 형식 · 문항 식별자 규칙 · 리포트 열 이름 · 실행기 옵션 이름
- 이 산출물이 소유하지 않는 값: 목표값과 측정 방법과 채점 수단(① 소유) · 문항 수와 유형 배분
  (⑤ 「골든셋 문항」 소유) · 지표 목록과 임계값(⑥ 「품질 측정 대상」 소유)
- 결과물 독자: 목표 달성 여부를 판단할 사람, 미달 원인을 고칠 각 담당 프롬프트의 개발자

우선순위 순으로 읽음. 앞 자료가 뒤 자료와 어긋나면 **앞 자료를 따름**.  
`{출력 루트}`는 `prompts/design/_shared/프로젝트정보.md`의 `V-12` 값이며 기본값은 `output/design/`임.

## [처리]

### 1단계 — 시작 조건 확인 (가장 먼저 수행)

- `개발환경정보.md`에서 `D-01` · `D-05` · `D-06` · `D-07` · `D-12`를 읽음.
  `프로젝트 확정 필요`가 하나라도 있으면 **코드를 만들지 않고** 무엇이 비었는지 적어 사용자에게 문의함
- `{출력 루트}`에 `01`과 `05`가 있는지 확인함. 없으면 그것을 먼저 만들라고 보고하고 멈춤
- `07-api-ui.md`가 만든 진입점이 있는지 확인함. 없으면 **인터페이스만 가정**하고 그 사실을 보고에 1줄 남김
- 확인 결과를 3줄 이내로 먼저 보고한 뒤 2단계로 넘어감

### 2단계 — 적용 판정 (설계서에서 읽음. 여기서 새로 정하지 않음)

아래를 설계서에서 읽어 표로 만들어 응답에 **먼저 보임.** 사용자가 여기서 되돌릴 수 있게 함.

| 판정 항목 | 어디서 읽나 |
|----------|-----------|
| 재야 할 목표가 몇 개이고 각 목표값이 숫자로 있나 | ① 「목표값」 — 숫자와 단위가 둘 다 있어야 함 |
| 목표마다 무엇을 세어 어떻게 계산하나 | ① 「측정 방법」 — 계산식이 드러난 문장 |
| 목표마다 채점 수단이 무엇인가 | ① 「채점 수단」 — 정답지 문항 · 부하시험 시나리오 · 집계 질의 중 1개 |
| 사람이 채점하나 자동으로 채점하나 | ① 「채점 수단」이 정답지면 자동, 그 외는 실행기 구조가 달라짐 |
| 1건당 비용·시간 상한이 얼마인가 | ① 「단위 환산」 — 요청 1건당 값으로 환산된 값 |
| 언제 재나 · 다시 언제 재나 | ① 「측정 시점」 — 처음 재는 시점과 다시 재는 시점 |
| 비교할 기준선이 있나 | ① 「개선 전 기준선」 — 없으면 리포트의 기준선 열을 `[확인필요]`로 둠 |
| 골든셋이 몇 문항이고 유형 배분이 어떤가 | ⑤ 「골든셋 문항」 — **없으면 3단계에서 되물음** |
| 지표 이름과 임계값이 무엇인가 | ⑥ 「품질 측정 대상」 — 품질 이름 · 목표 숫자 · 재는 문항 수 |
| 커넥터를 순서까지 맞춰야 정답인가 | ⑤ 「커넥터 검증 기준」 — 순서 불일치를 오답으로 셀지 갈림 |
| 담당자별 합격 문장이 무엇인가 | ④ 「성공 기준」 — 단정문 1개 = 기준 1개 |
| 최악값 합계가 목표 안인가 | ③ 「대조 2줄」 — 재시도까지 포함한 값을 잼 |

- **비율 목표는 필요 표본 수를 먼저 셈** — `1 ÷ (1 − 목표비율)` 이상의 문항이 있어야 그 비율을
  표현할 수 있음. 문항이 모자라면 **목표를 낮추지 않고**, 문항이 모자란다는 사실을 표에 적고 되물음
- **①에 값이 없는 칸은 지어내지 않음.** `[확인필요]`로 표에 적고 3단계에서 되물음

### 3단계 — 되묻기 (답을 받기 전에는 코드를 만들지 않음)

①과 ⑤와 ⑥의 **「미확정 항목」 부속 표에 있는 `[확인필요]` 행을 먼저 목록으로 옮긴 뒤**,  
아래를 기본값과 함께 물음. 사용자가 `기본값으로 진행`이라 하면 되묻지 않고 진행함.

| 물을 것 | 기본값 제시 | 왜 묻나 |
|--------|-----------|--------|
| ⑤에 문항 수·유형 배분이 없을 때 몇 문항을 만드나 | ⑤ 가이드 기준선을 그대로 물어 확정받음 | **여기서 문항 수를 정하지 않음.** 값의 주인이 ⑤임 |
| 골든셋 파일 형식과 두는 위치 | `D-05`의 시험 코드 위치 아래 · 한 문항 1행 | ⑤는 문항 수까지만 정함. 파일 규격이 없음 |
| 모델을 채점자로 쓸 때 채점자 모델을 고정하나 | 고정하고 이름·버전을 리포트에 함께 적음 | 채점자가 바뀌면 이전 결과와 비교할 수 없음 |
| 재현성 시험을 몇 번 돌리나 | 2회 | 같은 문제를 두 번 풀어 평균 차를 봄 |
| 실물에 붙여 재나 대역으로 재나 | ② 「외부 서비스 `구분`」을 그대로 따름 | 여기서 새로 정하면 ②와 값이 두 개가 됨 |
| 실행할 때 동시에 몇 건을 보내나 | 1건씩 순서대로 | 동시에 보내면 지연 값이 실제보다 나빠짐 |

- 되묻기로 정한 값 중 문항 수·배분은 **설계서 ⑤에**, 목표·채점 수단은 **설계서 ①에**
  되돌려 적을 것을 응답에 1줄로 권고함

### 4단계 — 골든셋 파일을 만듦

- ⑤ 「골든셋 문항」의 **문항 수와 유형 배분을 그대로** 씀. 여기서 늘리거나 줄이지 않음
- 문항마다 아래를 채움. **정답과 근거가 비어 있는 문항은 골든셋에 넣지 않음**

| 열 | 무엇을 적나 |
|----|-----------|
| 문항 식별자 | 문항마다 하나. ① 「채점 수단」이 문항 번호를 인용하므로 **번호를 바꾸지 않음** |
| 질문 | 사용자가 실제로 칠 문장 그대로 |
| 유형 | ⑤ 판정표의 유형 중 하나 |
| 정답 | 채점 가능한 형태로 적음 |
| 근거 문서·행 | 어느 자료 어디에서 나왔는지 |
| 기대 경로 | ⑤가 정한 어느 지식 경로로 답해야 하나 |
| 기대 도구 호출 | ⑤ 「커넥터 검증 기준」이 순서를 본다면 순서까지 적음 |

- ① 「채점 수단」이 문항 번호를 가리키면 **그 번호가 파일에 실제로 있는지 대조**함.
  없으면 `[확인필요]`로 적고 만들어 채우지 않음
- **정답을 먼저 만들고 코드를 고치지 않음.** 골든셋을 보고 검색을 맞춰 고치면 점수가 부풀려짐
- 문항 파일은 **사람이 열어서 고칠 수 있는 형식**으로 둠. 코드 안에 문항을 박지 않음

### 5단계 — 지표 설정을 만듦

- ⑥ 「품질 측정 대상」의 지표 이름 · 목표 숫자 · 재는 문항 수를 **설정 파일 1벌**로 옮김
- ① 「측정 방법」의 계산식을 지표마다 **함수 1개**로 옮김. 계산식이 없으면 지어내지 않고 `[확인필요]`
- ① 「목표값」을 통과 문턱으로 씀. **문턱을 코드에 박지 않고 설정에서 읽음**
- ① 「단위 환산」의 요청 1건당 상한을 비용·지연 지표의 문턱으로 씀
- ⑤ 「커넥터 검증 기준」이 순서 일치를 요구하면 **순서가 다르면 오답**으로 세는 판정을 넣음
- ④ 「성공 기준」의 단정문마다 **판정 1개**를 대응시킴. 단정문 1개 = 판정 1개
- 지표 이름을 새로 짓지 않음. ⑥과 ①에 있는 이름을 그대로 씀

### 6단계 — 평가 실행기를 만듦

- 골든셋 파일을 읽어 **문항마다 진입점을 부르고 결과를 모으는** 실행기를 만듦
- 채점 방식을 ① 「채점 수단」에 따라 갈라 만듦

| 채점 수단 | 실행기 구조 |
|----------|-----------|
| 정답지 문항 | 문항의 정답과 응답을 견주어 자동 채점. 채점 규칙을 설정으로 뺌 |
| 부하시험 시나리오 | 시나리오대로 요청을 보내고 지연·처리량을 모음 |
| 집계 질의 | 실행 기록을 집계해 값을 냄. `05-guardrail.md`의 기록을 읽어 씀 |

- 모델을 채점자로 쓰는 경우 **채점자 모델 이름과 버전을 설정으로 주입**하고 리포트에 함께 적음.
  코드에 모델 이름을 박지 않음
- 문항마다 아래를 함께 모음 — 응답 · 실제로 탄 경로 · 인용된 근거 · 걸린 시간 · 실패 사유
- **실행 결과 원본을 파일로 남김.** 요약만 남기면 나중에 다시 셀 수 없음
- 실행 도중 오류가 난 문항은 **빼지 않고 실패로 셈.** 표본에서 지우면 점수가 올라감
- ③ 「대조 2줄」이 있으면 **재시도까지 포함한 최악값 합계**가 ① 목표 안인지 재는 실행을 함께 둠
- ① 「측정 시점」이 처음과 다시 재는 시점을 나눠 적었으면 **두 번 돌릴 수 있게** 실행기에 옵션을 둠

### 7단계 — 재현성 시험을 만듦

- **같은 골든셋을 3단계에서 정한 횟수만큼 돌림**(기본 2회). 문항 순서와 씨앗을 같게 둠
- 지표마다 회차별 값과 **평균 차를 숫자로** 냄. "비슷함" 같은 말로 적지 않음
- 평균 차가 크면 그 사실을 그대로 적고, 무엇 때문에 흔들리는지 후보를 함께 적음
  (채점자 모델 · 검색 후보 순서 · 외부 응답 지연 등)
- 재현성 값 자체에는 목표가 없을 수 있음. 없으면 `목표 없음 — 관찰값`으로 적고 지어내지 않음

### 8단계 — 실측 결과 리포트를 만듦

- 지표마다 아래 열을 채움. **직접 잰 값만 적고, 못 잰 칸은 `미측정`으로 남김**

| 열 | 무엇을 적나 |
|----|-----------|
| 지표 이름 | ⑥ 「품질 측정 대상」의 이름 그대로 |
| 목표값 | ① 「목표값」에서 읽은 값. **여기서 바꾸지 않음** |
| 개선 전 기준선 | ① 「개선 전 기준선」의 값. 없으면 `[확인필요]` |
| 실측값 | 이번에 잰 값 |
| 표본 수 | 실제로 채점된 문항 수(오류 문항 포함) |
| 통과 여부 | 실측값이 목표를 넘었나 |
| 재현성 | 회차별 값과 평균 차 |
| 미달 원인 후보 | 미달일 때만. 어느 프롬프트가 고칠 몫인지 함께 적음 |

- 유형별로 나눠 적음 — 어느 유형에서 떨어졌는지 보여야 고칠 곳이 정해짐
- 근거가 없는 답변(지어낸 답)이 몇 건인지 세어 별도 행으로 적음
- 리포트 마지막에 **다음에 무엇을 고쳐야 하는지**를 담당 프롬프트 이름과 함께 1행씩 적음.
  **여기서 직접 고치지 않음**

### 10단계 — README를 만듦

- 가상환경 만들기와 실행 — **Windows GitBash · Windows PowerShell · Linux/Mac 3종**을 각각 적음

### 11단계 — 제출 전 자가 점검

아래를 스스로 판정해 `항목 / 판정(통과·미통과) / 근거` 3열 표로 응답에 제시함.  
미통과가 1건이라도 있으면 **완료라고 보고하지 않고** 고친 뒤 다시 판정함.  
**단, 지표가 목표에 못 미친 것은 미통과로 적되 목표치를 고쳐서 통과시키지 않음.**

- [ ] 지표 이름이 ⑥ 「품질 측정 대상」과 어긋난 건수 **0건**
- [ ] 목표값을 ①에서 읽었고 이 산출물에서 새로 정한 목표 **0건**
- [ ] 코드에 박힌 목표값 · 문턱 · 채점자 모델 이름 **0건**
- [ ] 비율 목표마다 필요 표본 수(`1 ÷ (1 − 목표비율)`)를 셌음
- [ ] 오류 문항을 표본에서 뺀 건수 **0건**
- [ ] 재현성 회차별 값과 평균 차를 숫자로 적었음
- [ ] 리포트에 짐작한 값이 **0건** — 못 잰 칸은 `미측정`으로 있음
- [ ] 미달 지표를 그대로 적었고 목표치를 낮춘 건수 **0건**

## [예시]

아래는 **형식만** 보여 줌. 값은 설계서에서 나온 것으로 전부 교체함.

**2단계 적용 판정 결과 형식**

```
| 판정 항목 | 설계서에서 읽은 값 | 출처 |
|----------|------------------|------|
| 재야 할 목표 수 | 3개(숫자·단위 모두 있음) | ① 「목표값」 |
| 채점 수단 | 정답지 2개 · 집계 질의 1개 | ① 「채점 수단」 |
| 골든셋 문항 | 24문항 — 유형 4종 배분 있음 | ⑤ 「골든셋 문항」 |
| 지표 | 3개 · 임계값 있음 | ⑥ 「품질 측정 대상」 |
| 비율 목표 표본 | 목표 95% → 필요 20문항 · 보유 24문항 (충분) | ① 「목표값」 · ⑤ 「골든셋 문항」 |
| 기준선 | 2개 있음 · 1개 [확인필요] | ① 「개선 전 기준선」 |
```

**실측 결과 리포트 형식**

```
| 지표 | 목표값 | 기준선 | 실측값 | 표본 수 | 통과 | 재현성(2회 평균 차) | 미달 원인 후보 |
|------|-------:|-------:|-------:|--------:|:----:|--------------------:|---------------|
| 지표A | 95% | 62% | 91.7% | 24 | 미달 | 0.8%p | 관계 유형 문항 2건 · 03-knowledge 검토 |
| 지표B | 3초 | 8초 | 2.4초 | 24 | 통과 | 0.12초 | — |
| 지표C | [확인필요] | 미측정 | 미측정 | 0 | — | — | ①에 목표값 없음 |
```

**완료 보고 형식** (응답으로 냄. 코드에는 넣지 않음)

```
만든 파일: (ls 결과 첨부)
⑤ 골든셋 24문항 → 만든 문항 24개 (같음)
채점 수단이 가리키는 문항 번호 6건 → 파일에 6건 전부 있음
골든셋 전건 실행 로그 첨부 · 채점된 문항 24건(실패 2건 포함)
지표A 91.7% (목표 95% 미달 — 낮추지 않고 그대로 적음)
재현성 2회: 91.7% / 90.9% · 평균 차 0.8%p
코드에 박힌 목표값·채점자 모델 이름 0건 (검색 결과 첨부)
단위 시험 11건 실행 · 실패 0건 (로그 첨부)
[확인필요] 2건 — README 목록 2행과 일치

| 점검 항목 | 판정 | 근거 |
|----------|------|------|
| ...(11단계 전건) | | |
```

**해서는 안 되는 것 (anti-example)**

```
목표가 95%인데 91.7%가 나와서, 어려운 문항 2개를 표본에서 빼니 100%가 나왔음. 통과로 보고했음.
목표가 조금 높아 보여서 90%로 조정하고 통과 처리했음.
재현성은 두 번 돌려 보니 비슷해서 문제없음.
```

셋 다 틀림. 표본을 **빼지 않고**, 목표는 **①만 바꿀 수 있고**,  
재현성은 **숫자로** 적음.  
여기서 만든 통과 보고는 배포 판단의 유일한 근거가 되므로, 부풀린 숫자는 그대로 사고가 됨.
