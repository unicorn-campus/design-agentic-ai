### 1-3. 피크 조건을 내가 직접 다시 센 결과 — 예산이 성립하지 않음

⑦ 2절 I-2는 `동시 1,000명 처리 · DB 커넥션 풀 최대 100`을 인용함. ③는 그 두 숫자를 예산에 넣지 않음.  
**두 문서가 같은 숫자를 알면서 아무도 곱해 보지 않았음.** 내가 곱함(값은 배정값 기준 `추정값`임).

요청 1건이 저장소 자리를 붙잡는 시간 — ③ 9-1절 배정값에서 저장소 접근 단계만 뽑음.

| 단계 | 접근 대상 | 점유 시간 |
|---|---|---|
| S-R2 | 회원·취향 저장소(DB1) | 100ms |
| S-R3 | 식사기록(DB3) · 추천 이력(DB2) | 150ms |
| S-R4 | **식당 캐시(DB4)** — J-6으로 저장소 조회가 됨 | 400ms |
| S-R6 | 코드 매핑 표 | 50ms |
| S-R11 | 추천 이력 저장(DB2) | 100ms |
| **합계** | — | **800ms** |

- 요청 1건 총 소요 = 2,680ms(배정값) · 그중 저장소 점유 = 800ms → 점유 비율 **약 30%**
- 동시 1,000명이면 **평균 동시 저장소 점유 = 1,000 × (800 ÷ 2,680) ≈ 299개**
- 쓸 수 있는 자리 = 커넥션 풀 **100개** → **필요량이 약 3배 초과**
- 처리량으로 다시 봄 — 커넥션 100개로 낼 수 있는 처리량 = 100 ÷ 0.8s = **125건/초**
- 요구 처리량 = 동시 1,000명 ÷ 2.68s = **373건/초**
- **373 > 125.** 요구가 능력의 약 3배이므로 대기 줄이 계속 길어짐. 이 상태에서는 p95가 3초로 수렴하지 않음

**판정 — ③ 9-1절 `2,680 ≤ 3,000 통과`는 동시 1명일 때만 성립하는 판정임.**  
①이 목표값에 `(피크 포함)`을 명시했으므로, 피크 조건이 빠진 판정은 ① Q-1을 검증하지 못함.  
같은 방식으로 LLM 쪽도 셈 — 동시 LLM 호출 = 1,000 × (1,200 ÷ 2,680) ≈ **448건 동시**.  
모델 API의 분당 요청 상한을 어느 문서도 확인하지 않았음(축 2 참조).

**계산 성격** — 위 숫자는 전부 `추정값(근거: ③ 배정값 + US:NFR-SYS-020 원문 두 값)`임.  
실측이 아니며, 커넥션 풀을 늘리거나 캐시를 앞에 두면 달라짐. 다만 **지금 표에 그 행이 없다**는 사실은 확정임.

### 1-4. `p95`와 `최악값`을 한 표에서 섞어 쓰는가 — 판정

**섞여 있음.** 같은 표 안에서 열 이름은 `타임아웃`·`최악값`인데, 마지막 두 행이  
`총 예산 3,000ms(p95 3초)` · `2,680 ≤ 3,000 — 통과. 여유 320ms`임.

| 읽는 방식 | 성립하나 | 무엇이 어긋나나 |
|---|---|---|
| ① 최악값 합계 ≤ 예산 | **논리적으로 성립** | 최악값은 상한이므로 상한이 3초 이하면 p95도 3초 이하임. **충분조건으로는 옳음** |
| ② 단계별 p95 배정값의 합 = 전체 p95 | **성립하지 않음** | 단계별 p95를 더하면 전체 p95보다 커짐(모든 단계가 동시에 느릴 확률이 낮음). 안전한 쪽이나 같은 값이 아님 |
| ④ `여유 320ms`를 p95 여유로 읽음 | **틀림** | 320ms는 "모든 단계가 상한까지 쓰고 재시도가 다 터졌을 때"의 여유임. 실측 p95의 여유가 아니며, 피크 대기(1-3)를 넣으면 마이너스가 됨 |

**어떻게 해야 맞나** — 열을 2개로 나눔.

- `p95 배정값` 열 — 각 단계에서 실제로 목표할 시간. 합계는 3,000ms 이하여야 하고 **여기에 큐잉 행을 더함**
- `타임아웃(상한)` 열 — 그 단계를 포기할 시각. p95 배정값의 2 ~ 3배로 두는 것이 통상임
- 합계도 2줄로 — `p95 합계`(목표 검증용)와 `최악값 합계`(폭주 방지용)를 따로 적음
- 재시도 배수는 **최악값 줄에만** 곱함. p95 줄에 곱하면 드물게 일어나는 일을 상시로 세는 것이 됨

지금은 두 값이 한 칸에 들어 있어 어느 쪽으로 읽어도 표를 고쳐야 함. ③의 산술 잘못이 아니라 **표 구조의 문제**이며,  
가이드가 이 구조를 요구하고 있음(마지막 절 참조).

### 1-5. 폴백이 최악값을 줄인다는 서술이 틀림 — HIGH

③ 9-1절 주석과 9-3절 L-2가 이렇게 적음 — "C-1 실패 시 기본 추천 이유로 대체. **LLM을 건너뛰므로  
1,200ms를 쓰지 않고 더 빨라짐**".

**다시 세면 반대임.** 폴백은 실패를 알고 난 다음에 도는 경로임.

```
정상   : … S-R8(10) → S-R9 LLM(1,200) → S-R10 … → S-R12   = 2,680ms
L-2 폴백: … S-R8(10) → S-R9 타임아웃 대기(1,200) → 폴백 조립(값 없음) → S-R10 … → S-R12
        = 2,680ms + 폴백 조립 시간
```

C-1이 실패했다는 것을 아는 시점이 **타임아웃 1,200ms를 다 쓴 뒤**이므로 1,200ms는 이미 소진됨.  
거기에 기본 추천 이유(거리·평점) 조립 시간이 **더해짐**. ③에는 그 조립 단계의 시간 배정이 없음 →  
**폴백 경로의 최악값이 표에 0으로 잡혀 있음.**

여유가 320ms뿐이므로 폴백 조립이 320ms를 넘으면 그 순간 예산을 넘김. 값이 없어 검증 불가.

**L-3 캐시 폴백은 서술이 맞음** — C-2가 800ms를 소진한 뒤 캐시된 이전 추천을 그대로 표시하므로  
S-R9 ~ S-R11이 실제로 빠짐. 이 행은 다시 세도 문제 없음.

## 축 2 — LLM 단가 산식이 예산 안에 들어오는가

### 2-1. 원값에서 요청당 금액을 직접 계산

원문 인용 — `BM:3-비용구조#변동비용`(월, MAU 10,000 기준)

- LLM API 비용: 300만 원 (Claude/GPT API, **일 추천 10,000건 × 30일**)
- 지도/식당 API: 50만 원 (카카오 로컬 + 네이버 플레이스)
- 클라우드 서버: 150만 원 (AWS/GCP, 오토스케일링)

| 항목 | 산식 | 결과 |
|---|---|---|
| 월 요청 건수 전제 | 10,000건/일 × 30일 | **300,000건/월** |
| **LLM 요청당 상한** | 3,000,000원 ÷ 300,000건 | **10원/건** |
| 지도 API 건당 | 500,000원 ÷ **분모 불명** | **계산 불가**(2-5 참조) |
| 클라우드 건당 | 1,500,000원 ÷ 300,000건 | 5원/건 (⑦ 소관. 참고값) |

**교차검증 1건 — 10원/건이 BM 자체와 맞는지 확인함.**  
`BM:1-CostStructure#BEP`가 `월 변동비(구독자당) ~200원 (API 추가 비용)`이라 적음.  
200원 ÷ 10원 = **월 20건** = 구독자 1명이 월 20끼 점심에 추천을 받는 것과 같음.  
평일 20일과 일치함. **BM 내부의 두 숫자가 서로 맞음** — 10원/건은 BM이 실제로 쓰고 있는 값임.

### 2-2. LLM 호출이 실제로 몇 곳인가 — ④③⑤ 대조

### 2-3. 토큰 수 전제가 어디에도 없음 — `claude-sonnet-5`로 10원/건이 성립하는지 개략 판단

**모델 단가를 기억으로 쓰지 않았음.** `claude-api` 스킬의 모델·단가 표(캐시 기준일 2026-06-24)로 확인함.

| 확인 항목 | 결과 | 출처 |
|---|---|---|
| `claude-sonnet-5` 모델 ID가 실재하나 | **실재함.** 날짜 접미사 없는 정식 ID임 | `claude-api` 스킬 현행 모델표 |
| 입력·출력 단가(정가) | 입력 **$3.00 / 1M토큰** · 출력 **$15.00 / 1M토큰** | 같음 |
| 도입 특가 | 입력 **$2.00** · 출력 **$10.00** — **2026-08-31까지** | 같음 |
| 문맥창 · 최대 출력 | 1M토큰 · 128K토큰 (런치픽에는 제약 아님) | 같음 |
| 프리픽스 캐시 최소 길이 | **1,024토큰** (그보다 짧으면 소리 없이 캐시 안 됨) | 같음 |
| 적응형 사고 기본값 | **`thinking` 파라미터를 생략하면 켜짐**. 사고 토큰은 **출력 단가로 과금** | 같음 |

**환율은 확인하지 못했음** → `[확인필요: 원-달러 환율 전제]`. 아래 계산은 **1,400원/USD 가정**임(`추정값`).  
10원/건 = 약 **USD 0.00714/건**.

C-1 출력 규격(⑤ 7절)에서 출력 토큰을 개략 셈 — 추천 3건 × (근거 문장 1줄 + confidence + context_tags).  
한 줄 근거를 한글 40자로 보면 약 60토큰, 3건 = 180토큰. 스코어·태그·JSON 껍데기 포함 **약 250토큰**.

| 요금 기준 | 출력 250토큰 비용 | 입력에 남는 예산 | 쓸 수 있는 입력 토큰 |
|---|---|---|---|
| 도입 특가($2/$10) | $0.00250 | $0.00464 | **약 2,320토큰** |
| 정가($3/$15) | $0.00375 | $0.00339 | **약 1,130토큰** |

C-1 입력은 지시문 + 코드값 몇 개 + **후보 목록**임. 후보 1건 = `restaurant_id` + `display_name`으로  
JSON 껍데기까지 약 25토큰. 지시문을 500토큰으로 보면 —

- 도입 특가 기준: (2,320 − 500 − 100) ÷ 25 ≈ **후보 68건까지 가능**
- 정가 기준: (1,130 − 500 − 100) ÷ 25 ≈ **후보 21건까지 가능**

**판정 — 10원/건은 성립 가능하나 여유가 크지 않고, 정가 전환 후 후보 목록 길이에 바로 걸림.**  
⑤ 2절이 반경 500m 후보를 `수십 개 규모`로 적었으므로 정가 기준 21건은 **경계선을 이미 만짐**.  
그런데 **C-1 입력 후보 건수의 상한을 정한 문서가 하나도 없음** — ⑤ 3절은 이력 조회 행 수 상한만  
`[확인필요]`로 두었고, C-1 입력 목록 길이는 어느 절에도 없음. 상한이 없으면 요청당 단가에 천장이 없음.

`[확인필요: 요청당 토큰 수 전제]` — 이 값이 없으면 위 계산은 내 가정이며 확정으로 읽을 수 없음.

**여기서 새로 찾은 것 2건 — 어느 설계서도 적지 않았음.**

| # | 내용 | 왜 단가를 흔드나 |
|---|---|---|
| ㄱ | **적응형 사고가 기본으로 켜짐** | `claude-sonnet-5`는 `thinking` 파라미터를 생략하면 사고가 돌고, 사고 토큰이 **출력 단가**($10 ~ 15/1M)로 과금됨. 눈에 보이는 250토큰 외에 사고 토큰이 그 몇 배 붙으면 10원/건이 즉시 깨짐. 또 사고 시간이 ③ S-R9 예산 1,200ms 안에 들어감. **④③⑤⑦ 어디에도 사고 설정 칸이 없음** |
| ㄴ | **도입 특가가 2026-08-31에 끝남** | 설계서 작성일이 2026-08-06이므로 25일 뒤 정가로 바뀜. 입력 1.5배·출력 1.5배가 되어 위 표의 여유가 절반 이하로 줄어듦. 어느 문서도 특가·정가를 구분하지 않음 |

**절감 수단 1건 — 지금 쓸 수 없음.** 지시문을 프리픽스 캐시에 올리면 입력 단가가 크게 줄지만,  
`claude-sonnet-5`의 캐시 최소 길이가 **1,024토큰**임. 지시문이 500토큰 규모면 **캐시가 걸리지 않고  
오류도 나지 않음**(소리 없이 실패). 캐시를 절감 수단으로 쓰려면 지시문 길이를 먼저 정해야 함.

### 2-4. 콜드스타트 사용자와 학습된 사용자의 입력 길이 차이 — 단가를 하나로 잡았나

**하나로 잡았음. 다만 이 건은 영향이 작음.**

| 입력 키 | 콜드스타트 | 학습된 사용자 | 토큰 차이 |
|---|---|---|---|
| `preference_codes` | 온보딩 카드 기준 소수 | 누적 학습 결과로 더 많음 | 수십 토큰 |
| `recent_category_codes`(최근 7일) | **0건** | 최대 7건 | 약 30 ~ 50토큰 |
| `coldstart` | `true` | `false` | 1토큰 |
| `candidates` | 같음 | 같음 | 0 |

차이는 **약 50 ~ 100토큰**이며 입력 총량(1,000 ~ 2,000토큰)의 5% 안쪽임.  
`candidates`가 입력 토큰을 지배하므로 콜드스타트 여부보다 **후보 건수**가 단가를 정함.  
따라서 단가를 하나로 잡은 것은 **이 케이스에서는 문제 없음** — 다만 그 판단을 한 문서가 없고,  
지배 변수가 후보 건수라는 사실도 어느 문서에도 없음.

### 2-5. 거절 → 대체 추천 → 전체 새로고침 루프가 요청당 호출 수를 늘리는가

**늘림. 그리고 ③가 이미 지목했으나 숫자를 내지 않았음.** 내가 냄.

③ 10절 L-2 — `3건 전부 거절 → 새 3건`은 반복마다 C-1을 다시 부름. `max_iter`는 `[확인필요]`임.

| L-2 반복 상한 | 요청당 LLM 호출 | 요청당 단가 | 월 300,000건 환산 | BM 상한 300만 원 대비 |
|---|---|---|---|---|
| 0회(거절 없음) | 1 | 10원 | 300만 원 | 100% — 딱 맞음 |
| 1회 | 2 | 20원 | 600만 원 | **200% 초과** |
| 3회 | 4 | 40원 | 1,200만 원 | **400% 초과** |
| 상한 없음 | 무제한 | 무제한 | 무제한 | **상한 확정 불가** |

**연결 판정 — `[확인필요: 전체 새로고침 상한]`이 열려 있는 동안 LLM 단가 상한도 확정 불가임.**  
③가 `max_iter`를 `[확인필요]`로 둔 것은 지어내지 않은 옳은 처리이나, **그 태그가 비용 상한 태그와  
같은 태그**라는 점이 두 문서에 적혀 있지 않음. ① 9절은 `[확인필요: LLM 비용 상한 단위]`를  
"월 300만 원만 있고 요청당 상한이 없음"으로 적었는데, 실제로는 요청당 상한이 **10원으로 계산되며**  
막힌 것은 단위가 아니라 **반복 상한**임. ①의 진단이 한 칸 어긋남.

L-1(개별 거절 → 대체 1건)은 ③가 "C-1을 다시 부르지 않아도 되는 경로가 **있음**"으로 적었음.  
`있음`은 `안 부름`이 아니므로 L-1도 상한이 없으면 호출이 늘 수 있음. ③가 L-1 상한을 따로  
되물은 것은 맞는 판단임.

**MAU·DAU 전제가 10배 어긋남 — 새로 찾음, HIGH.**

- `BM:3-비용구조#변동비용` — `MAU 10,000 기준, 일 추천 10,000건`
- `PR:MVP정의#성공지표`(① 2절 #12로 인용) — **DAU 1,000명**

MAU 10,000에 DAU 1,000이면 매일 쓰는 비율이 10%임. 그러면 **일 추천은 1,000건**이고 월 30,000건임.  
BM은 MAU 전원이 매일 쓴다고 가정해 일 10,000건을 썼음. 어느 쪽이 맞느냐에 따라 —

| 전제 | 월 건수 | 요청당 상한 |
|---|---|---|
| BM 그대로(일 10,000건) | 300,000건 | **10원** |
| DAU 1,000명(일 1,000건) | 30,000건 | **100원** |

**요청당 허용 단가가 10배로 갈림.** ④ 4-2절이 `claude-sonnet-5`를 고른 근거가 "월 300만 원 상한을  
지키려면 요청당 단가가 낮은 등급이 유리함"인데, 그 상한이 10원인지 100원인지에 따라 모델 등급 판단  
자체가 달라짐. 100원이면 상위 등급도 들어갈 자리가 생김.

### 2-6. 지도 API 월 50만 원 — J-6 이후 상한을 지키는지 계산 가능한가

**계산 불가. 산식의 변수 3개 중 3개가 없음.**

J-6으로 추천 경로가 C-2를 부르지 않게 되었으므로 분모가 **추천 건수가 아님**.  
호출 주체는 `SYNC` 워커와 길찾기 단계 2곳임(⑤ 7절 · ⑦ 4-2 K-2).

```
월 지도 API 호출 = ① 동기화 워커 호출 + ② 길찾기 호출

① = (대상 식당 수 ÷ 1회 응답 건수) × (30일 × 24시간 ÷ 갱신 주기h)
② = 월 추천 수락 건수 × 1
```

| 변수 | 값이 있나 | 어디를 봤나 |
|---|---|---|
| 대상 식당 수 | **없음** | 반경 500m는 있으나(`BM:6-GTM#Launch`) 서비스 지역 전체 식당 수가 없음 |
| 1회 응답 건수 | **없음** | ⑤ 7절 C-2 출력 규격에 페이지 크기 칸이 없음 |
| **갱신 주기** | **없음** | ② 4절이 `주기 갱신`이라고만 적음. ⑤ 15절 `[확인필요: 식당 캐시 갱신 주기]`로 이미 열려 있음 |
| 월 수락 건수 | **없음** | 첫 추천 수락률 40%는 `BM:4-KeyMetrics`에 있으나 공동 책임 지표이며 월 건수 환산 근거가 없음 |

**판정 — 지도 API 50만 원 상한의 준수 여부는 지금 판정할 수 없음.**  
갱신 주기 1개만 정해져도 ①이 계산 가능해지므로, ⑤의 `[확인필요: 식당 캐시 갱신 주기]`는  
데이터 신선도 문제이면서 **동시에 비용 상한 문제**임. ⑤ 15절은 신선도 쪽만 적었음.

**J-6이 만든 좋은 효과 1건은 확인됨** — ⑦ 5-1절이 "캐시를 컨테이너 메모리에 두면 복제본 수만큼  
지도 API 호출이 늘어 50만 원 상한을 먼저 만짐"으로 저장소를 런타임 밖에 둔 판정은 다시 세도 맞음.  
복제본이 늘어나는 피크에 호출이 복제본 배수로 곱해지는 것을 막았음.

### 3-1. ① 목표값 ↔ ⑤ 골든셋 24문항 대조 — 어느 문항이 무엇을 채점하나

**24문항 중 ①의 1순위 품질속성 Q-1을 채점하는 문항이 0건임.**  
골든셋은 "답이 맞나"를 보는 도구이고 시간은 안 봄. ⑤가 지연을 다루지 않는 것은 성격상 옳음  
(⑤ 9절 성격 선언대로 타임아웃은 ③ 소유). 문제는 **③가 예산만 배정하고 측정 문항을 만들지 않았고  
⑤가 문항만 만들고 시간을 넣지 않아, 두 문서 사이에 Q-1의 채점 수단이 통째로 빠졌다**는 점임.  
값 주인은 ⑥이므로 ⑥ 미작성이 이 공백을 덮고 있음.

측정 수단이 무엇이어야 하는지는 ①이 이미 적어 놓았음 — `요청 이벤트 ~ 응답 완료 이벤트 시각 차 p95`.  
필요한 것은 문항이 아니라 **부하시험 시나리오**임. 24문항을 몇 번 돌려도 동시 1,000명이 재현되지 않음.  
축 1-3에서 예산이 안 맞는다고 계산된 그 조건이 곧 시험 조건임.

### 3-2. ①의 `정확성` 탈락 판정 검증 — 이진 피드백으로 만족도를 잴 수 있는가

①이 적은 사유 — "목표값 `추천 만족도 4.0/5.0`의 측정 수단이 앱 내 이진 피드백(좋아요/별로)이라  
**5점 척도로 계산 불가**함."

내 전문 관점으로 판정함. 이진 값에서 만족도를 재는 통상적인 방법이 **있음**.

| 방법 | 이진 피드백으로 되나 | 내용 |
|---|---|---|
| **만족률(좋아요 비율 %)** | **됨** | (좋아요 수) ÷ (좋아요 + 별로 수). 이진 값의 가장 직접적인 만족도 지표임. 시스템 기록만으로 계산되며 사람 설문이 불필요함 |
| **Top-box 대응** | **됨(재정의 필요)** | 5점 척도의 `4점 이상 비율`과 이진 `좋아요 비율`을 대응시키는 것이 통상 방식임. `4.0/5.0`을 `만족률 N%`로 목표값을 바꿔 적으면 잴 수 있음. 다만 4.0 ↔ N%의 환산에는 근거가 필요함 |
| **5점 평균 4.0 직접 산출** | **안 됨** | 이진 값에서 5점 평균을 복원할 수 없음. **①의 말은 이 부분에서 맞음** |
| **NPS** | 해당 없음 | 11점 척도임. `BM:4-KeyMetrics#Referral`에 NPS 30+가 있으나 별도 수집 수단이 필요하며 이진 피드백으로 대체 불가 |
| **수락률(앱 이벤트)** | **됨** | 첫 추천 수락률 40%(`BM:4-KeyMetrics#Activation`)는 클릭 기록이라 이진 피드백보다 오히려 신호가 강함. `US:UFR-REC-040`이 수락 기록을 남김 |

**판정 — ①의 결론은 유지 가능하나 사유가 과함.**

- 옳음 — `4.0/5.0`이라는 **그 숫자를** 그대로 재는 것은 불가함
- 과함 — `정확성`이라는 **품질속성 자체가** 측정 불가는 아님. 만족률(%)은 시스템 기록으로 계산됨
- 우선 3개에서 내리는 결론 — **유지됨.** 다만 근거는 "측정 불가"가 아니라 **T-4(사용자 주관 행동이 끼어듦)**  
  하나로 서야 함. ①도 T-4를 함께 적었으므로 결론은 흔들리지 않음
- 고칠 것 — ① 4절 탈락 사유의 `5점 척도로 계산 불가함` 문장과 9절 `[확인필요: 만족도 측정 척도]`를  
  "척도 환산 불가 → 목표값을 만족률(%)로 재정의 요청"으로 바꿔야 ⑥이 문항을 만들 수 있음.  
  지금 문장대로면 ⑥은 "잴 수 없는 것"으로 읽고 측정 대상에서 빼게 됨

### 3-3. Q-2 태그 일치율 95%를 기계적으로 채점할 수 있나 — 판정 3건

⑤ 11절 채점 방법 — "근거의 `context_tags`를 그 요청의 **실제 입력값과 대조**. 태그가 입력에 없는 것을  
말하면 불합격." ⑤가 "근거 문장이 그럴듯한지를 보지 않음"이라 명시함.

| # | 점검 | 판정 | 근거 |
|---|---|---|---|
| B-1 | 기계 채점 자체가 되나 | **됨** | `context_tags`는 `날씨·이력·취향` 라벨 목록이므로 집합 비교로 자동 채점 가능함. 사람 판단이 안 들어감 — 이 부분은 잘 설계됨 |
| B-2 | **95%를 6문항으로 표현할 수 있나** | **안 됨 — MED** | 아래 눈금 계산 참조 |
| B-3 | **대조 대상인 `실제 입력값`이 남아 있나** | **확인 불가 — MED** | 아래 참조 |

**B-2 눈금 계산 — 95%를 재려면 최소 20눈금이 필요함.**

어떤 비율을 `95%`로 판정하려면 눈금 1개가 5%p 이하여야 함. 즉 표본이 **최소 20개** 필요함(1 ÷ 20 = 5%).

| 세는 단위 | 표본 수 | 눈금 1개 | 95% 판정 가능? |
|---|---|---|---|
| 문항 단위 | 6문항 | 16.7%p | **불가.** 6개 중 5개 = 83.3%, 6개 = 100%. 95%가 눈금 사이에 있음 |
| 태그 단위(문항당 태그 3종) | 6 × 3 = **18태그** | 5.56%p | **불가(간신히 모자람).** 18개 중 17개 = 94.4% < 95% → 불합격. 18개 = 100% |

**결과 — 실질 합격선이 100%가 됨.** `95% 이상`을 걸어 놓고 하나만 틀리면 94.4%로 불합격이므로,  
설계 의도(5%까지는 허용)가 채점에서 사라짐. 태그를 하나도 안 틀려야 통과하는 기준이 됨.

**필요한 표본 수** — 태그 단위로 최소 **20태그**(문항당 3태그면 **7문항 이상**). ±2%p 정밀도를 원하면  
50태그(17문항 이상)임. 지금 6문항은 부족함.

**B-3 대조 원본 보존 — 요구한 문서가 없음.**

⑤는 `context_tags`를 "그 요청의 실제 입력값"과 대조하라고 함. 그런데 —

- ④ A-2 성공 기준은 `출력 context_tags가 **입력** context_tags와 일치함`임
- 입력 `context_tags`를 만드는 것은 **A-1**임(④ A-1 출력 `context_tags: list[str] 필수 공유`)
- 즉 ④의 성공 기준은 **A-1이 준 태그를 A-2가 그대로 되돌렸는지**만 봄
- **A-1이 태그를 잘못 붙인 경우는 이 비교로 잡히지 않음** — 날씨 코드가 안 왔는데 A-1이 `날씨` 태그를  
  붙였으면 A-2는 그것을 충실히 되돌리고 통과함

⑤가 요구한 "실제 입력값"은 A-1 **앞의 원시값**(`weather_code`·`recent_category_codes`·`preference_codes`)임.  
그 원시값을 추천 이력 저장소(DB2)에 함께 남기라는 요구가 **④③⑤ 어디에도 없음.**  
③ 4절 S-R11은 `추천 이력·근거·컨텍스트 태그 저장`이며 원시 입력값이 목록에 없음.

**판정 — 채점 방법은 성립하나, 채점에 필요한 데이터의 보존 요구가 빠져 있음.** 새 `[확인필요]`로 올림.

**B-4 곁가지 지적 1건 — 사용자가 읽는 것이 채점 밖임.**

⑤가 "근거 문장이 그럴듯한지를 보지 않음"이라 못 박은 것은 채점을 기계화하려는 옳은 선택임.  
그러나 그 결과 **`reason_text`(사용자가 실제로 읽는 문장)와 `context_tags`가 서로 다른 말을 해도 통과함.**  
태그에 `날씨`가 있고 입력에 날씨 코드가 있으면 합격이며, 문장이 날씨를 한 마디도 안 하거나  
반대로 말해도 걸리지 않음.

① Q-2의 목적은 킹핀 문제 P2("나를 위한 추천인지 알 수 없다") 해소이고, 사용자가 신뢰를 얻는 통로는  
문장임. 요약·생성 품질을 재는 통상 방식은 **근거 표기**와 **본문 ↔ 근거 일치**를 따로 재는 것임.  
지금은 앞쪽만 재고 있음. 뒤쪽은 자동 채점이 어려우므로 소표본 사람 확인(예: 월 30건 표본)을  
⑥이 별도로 두어야 함. ⑤를 고칠 일이 아니라 ⑥에 넘길 요구사항임.

- `출력 측 노출 검사` → ⑤ 8절 F-5(근거 문장에 알레르기·좌표가 섞였는지 출력측 검사) · ④ A-2 중단 조건 ③

즉 파라미터블록이 0건으로 처리한 2계열이 실제 설계에서 필수였음. 파라미터블록 사례 B의 계열 판정을  
그대로 믿고 두 계열 작업방법을 지웠다면 ①의 성격 선언과 F-5가 사라졌을 것임.

### 4-3. `{데이터 원천·비정형}` ↔ ⑤ 4절 — 원재료·알레르겐 표시는 어느 쪽이 맞나

사례 B 값 — `메뉴 설명, 추천 이유 자연어 텍스트, **원재료·알레르겐 표시**`

**기획 산출물을 직접 확인함.** `원재료`·`알레르겐`·`식재료`·`8대`·`비건`·`할랄`을 `docs/plan` 전체에서 찾음.

**판정 — ⑤가 맞음. 파라미터블록이 틀렸음 — HIGH.**

원문에 있는 것은 전부 **사용자가 자기 알레르기를 입력하는 쪽**임. **식당·메뉴가 어떤 원재료를 쓰는지를  
알려 주는 데이터의 원천은 기획 산출물 전체에 없음.** ⑤ 16절 1번과 15절 최우선 미확정이 정확함.

파라미터블록은 사용자 입력 라벨을 **식당 쪽 비정형 원천으로 잘못 분류**했음. 이 오분류가 위험한 이유 —  
`{데이터 원천·비정형}`이 필수 변수이고 값이 채워져 있으면 "원천이 있다"로 읽힘. 그러면 ⑤가  
"이 설계서 전체에서 가장 무거운 미확정"으로 올린 항목이 **파라미터블록 단계에서 이미 해결된 것으로  
보이게 됨.** 원천 부재는 ① G-3 위반 0건을 측정 불가로 만들고 페일세이프가 반경 내 전 식당을 제외해  
추천 0개가 되는 경로(⑤ 6절 · ④ 4-1 착지 표)로 이어지므로, 감춰지면 구현에서 무너짐.

나머지 2개 값도 함께 봄.

- `메뉴 설명` → ⑤ 4절 벡터 RAG 행의 `대상 문서`에 `식당·메뉴 설명 텍스트`로 들어 있음(미채택). **대응됨**
- `추천 이유 자연어 텍스트` → 이것은 **원천이 아니라 산출물**임. C-1이 만들어 DB2에 저장하는 값이며  
  검색 대상이 아님. ⑤는 이것을 F-5(민감 필드)로 다루었고 그 처리가 맞음. 파라미터블록이 산출물을  
  원천 칸에 넣은 것이며, V-05 `비정형` 필드의 정의(`비정형 검색 대상 문서 유형`)와 어긋남 — LOW

### 4-4. `{데이터 원천·관계 특성}` ↔ ⑤의 GraphRAG 미채택 판정

사례 B 값 — `사용자–메뉴–식당–원재료(알레르겐) 간 관계`

V-05 규격 — `관계 특성` 미기입 시 ⑤ 작업방법의 관계 검색 강점·한계 서술 단계를 제거함.  
값이 기입되어 있으므로 ⑤가 강점·한계를 서술해야 함 → **⑤ 2절에 `관계 검색의 강점·한계 구간` 표가  
실제로 있음.** 규격 준수됨.

미채택 판정의 타당성을 3축으로 봄.

| 축 | ⑤의 근거 | 내 판정 |
|---|---|---|
| 원료 데이터 | 3홉의 재료 쪽 데이터가 없음 | **타당.** 4-3에서 원천 부재를 원문으로 확인했음. 그래프를 만들 원료가 없는 것이 사실임 |
| 구축 비용 | 원료 확보 → 개체·관계 추출 → 그래프 구축이 14주 계획에 없음. 메뉴 텍스트 수십만 건 LLM 호출이 LLM 월 300만 원과 다툼 | **타당.** 축 2에서 계산한 10원/건 상한을 대입하면 메뉴 10만 건 추출 = 100만 원 규모의 일회성 비용이 되어 월 상한의 1/3을 한 번에 씀 |
| 질문 쪽 필요성 | 식당 간 관계를 건너가는 질문이 없음 | **타당.** ⑤ 1절 K-1 ~ K-5를 다시 읽었음. 관계를 2홉 이상 건너가는 질문이 **0건**임. 하드필터는 관계 질의로 볼 수 있으나 결정론 매칭이면 충분하며, 확률 매칭은 ① Q-3 위반 0건과 원리적으로 부딪힘(⑤ 2절 K-5가 같은 판정) |

**판정 — 관계 특성이 명시돼 있어도 미채택이 타당함. 문제 없던 것으로 기록함.**  
다만 조건이 붙음 — **원재료 원천이 확보되면 하드필터 자체가 3홉 질의**(식당 → 메뉴 → 식재료 → 알레르겐)가 되어  
관계 검색이 다시 후보가 됨. ⑤도 "2차 스프린트 이후로 미룸"으로 적었으므로 방향이 맞음.

파라미터블록이 `벤더 2종`으로 도출했음. ④은 1종만 배정했고, ③ 9-3절 L-2 폴백도 다른 벤더가 아니라  
`기본 추천 이유(거리·평점)` 즉 **모델을 안 쓰는 경로**임. ⑦ 4-2 K-1도 LLM API 키 1개임.  
즉 벤더 2종 정책이 어디에도 반영되지 않았음.

이것이 축 1·2에 걸리는 지점 — 한 벤더가 장애·속도저하일 때 갈 곳이 LLM 없는 폴백뿐임.

BM이 예산에 두 벤더를 잡아 둔 것과는 어긋남. 1종으로 갈 것이면 BM 쪽을 정정해야 하고,  
2종으로 갈 것이면 ④에 두 번째 모델 행과 ⑦에 두 번째 API 키가 필요함.

**파라미터블록 규칙상 실행 차단 상태인데 설계서 6종이 만들어진 것 — 1줄 판정.**

> **설계서 6종은 파라미터블록의 치환 절차를 거치지 않고 작성됐고, 차단 대상이던 기술 스택 5행 중  
> 4행을 설계 과정이 스스로 산출했음** — 즉 파라미터블록이 `실행 전 필수 기입`으로 분류한 값의 상당수가  
> 실제로는 **설계의 결과물**이므로, 6절 1단계 차단 규칙은 인과를 거꾸로 잡고 있음.

보강 1줄 — 정말 실행 전에 있어야 하는 것과 설계가 산출하는 것을 가르는 기준은  
"**기획이 이미 정한 값인가(BM·US에 적혀 있나)**"임. 모델 벤더 정책·기획 산출물 경로·출력 루트는  
기획 쪽 값이므로 사전 필수가 맞음. 정형·비정형 접근 방식과 패키징 단위는 ⑤·⑦의 판정 결과이므로  
사전 필수로 두면 아무도 채울 수 없는 칸이 됨.

## 가이드 적용 기록

가이드 ①·③가 지연 예산·단가 검증을 요구하는 방식에서 빈 곳을 찾은 결과임.  
설계서의 잘못이 아니라 **가이드를 그대로 따라도 검증이 안 되는 자리**를 적음.

| 가이드 절 | 무엇이 문제인가 | 어떻게 우회했나 | 가이드 수정 제안 |
|---|---|---|---|
