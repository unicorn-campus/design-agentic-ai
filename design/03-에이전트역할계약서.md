# 설계서 ③ 에이전트 역할 계약서 — 런치픽(LunchPick)

작성: 2026-08-06 · 작성자: 플로니(오케스트레이션 엔지니어) · 가이드: [03-에이전트역할계약서-가이드](../guides/03-에이전트역할계약서-가이드.md)  
선행 입력: [① 목표·품질속성 카드](01-목표품질속성카드.md) · [② 논리 아키텍처](02-논리아키텍처.md)  
CYCLE C-1 상태: ⑤ 지식·도구 설계 **미생성**. 6절 `민감 필드 × 권한 매트릭스`가 ⑤로 넘기는 **초안**이며 ⑤ 확정 후 1회 되돌려 갱신함.

③은 **누가 무엇을 책임지고 어디까지 손대나**만 정함. 시퀀스 단계 순서·타임아웃 값(④) · 마스킹 방식(⑤) ·  
배포 단위(⑦)는 여기에 없음. 중단 조건은 ③이 소유하나 **재시도·폴백 횟수는 ④ 소유**임(G-5).

## 1. 단일·멀티 판정 사다리 기록

가이드 2-1의 3단계를 실제로 밟은 기록임. 결론만 쓰지 않고 밟은 과정을 남김.

### 1-1. 1단계 — 이 시스템이 할 일 (유저스토리에서 7개)

`시스템으로서` 표기 스토리 2건과 `사용자로서` 스토리의 시스템 자율 판단 항목을 합쳐 뽑음.  
NFR 접두 ID는 후보에서 빼고 품질 목표로만 씀.

| # | 할 일 | 근거 출처 |
|---|-------|----------|
| J-1 | 위치·시각·날씨·최근 7일 이력·취향 프로파일을 모아 컨텍스트를 만듦 | `US:UFR-REC-010#검증요구사항` |
| J-2 | 알레르기·식이제한 식재료를 포함한 식당을 후보에서 뺌 | `US:UFR-MBR-040#검증요구사항` |
| J-3 | 후보 식당을 고르고 최근 3일 내 같은 식당을 뺌 | `US:UFR-REC-010#검증요구사항` |
| J-4 | 추천 3개를 고르고 근거 문장 1줄과 확신 스코어를 만듦 | `US:UFR-REC-020#검증요구사항` |
| J-5 | 피드백 5건 미만을 감지해 직군 클러스터 Prior 안전망으로 바꿈 | `US:UFR-REC-030#검증요구사항` |
| J-6 | 거절된 식당을 뺀 뒤 차순위 대체 추천 1개를 냄 | `US:UFR-REC-050#검증요구사항` |
| J-7 | 매일 03:00에 전일 피드백으로 취향 벡터를 갱신함 | `US:UFR-REC-100#시나리오` |

### 1-2. 2단계 — 후보안 2개

| 후보안 | 구성 | 근거 출처 |
|--------|------|----------|
| **A(단일)** | J-1 ~ J-7을 에이전트 1개가 전부 맡음. 저장소·외부 API는 도구 호출로 씀 | `설계판단` |
| **B(3개)** | ①「안전 후보 선별」 J-1·J-2·J-3·J-5 / ②「추천 근거 생성」 J-4·J-6 / ③「일일 취향 학습」 J-7 | `설계판단` |

B안을 3개로 묶은 기준은 업무 종류가 아니라 **읽는 자료와 손대는 권한**임. 알레르기 항목명을 읽는 묶음,  
읽지 못하는 묶음, 취향 벡터에 쓰는 묶음으로 갈림.

### 1-3. 3단계 — B안에 3문을 던짐

| 질문 | 판정 | 근거 |
|------|------|------|
| **Q1 컨텍스트 오염** | **아니오** | A로 묶어도 한 호출에 들어가는 규칙은 하드필터 1종임. 문서·규칙 3종 이상이 아님. `이력`이 추천 이력과 식사 이력 두 뜻으로 쓰이나 같은 호출에 함께 들어가지 않음 |
| **Q2 병렬화** | **아니오(판정 불가)** | 순차 실행이 3초를 몇 초 넘기는지 셀 수 없음 — 지도·날씨·LLM 호출의 단계별 소요시간이 기획 산출물에 없음. `[확인필요: 단계별 지연 예산]`. 넘기는 초 수를 못 적으므로 `예`로 판정하지 않음 |
| **Q3 전문화** | **예** | 아래 2건 |

**Q3이 `예`인 근거 2건** — ⑤ 민감 필드 분류표가 없어도 ②의 정보만으로 답함.

| # | 권한 등급이 갈리는 지점 | 근거 출처 |
|---|----------------------|----------|
| Q3-a | 알레르기·식이제한 항목명은 건강 관련 민감정보이며 별도 암호화 키 대상임. 하드필터를 실행하는 묶음은 이 필드를 읽어야 하고, LLM을 부르는 묶음은 절대 읽지 못해야 함(②의 TB-2가 넘기지 않는 항목 1번) | `US:NFR-SYS-030#체크리스트`, `US:UFR-MBR-040#검증요구사항` |
| Q3-b | 실시간 추천 경로는 취향 벡터를 **읽기만** 하고, 일일 배치는 취향 벡터에 **씀**. 같은 저장소에 대한 권한 등급이 다름 | `US:UFR-REC-100#시나리오` |

Q2를 `아니오`로 처리한 이유를 1줄 더 남김 — 설령 병렬 실행이 필요해도 그것은 **노드 병렬 실행**이며  
④가 소유함. 동시 실행 때문에 에이전트를 복제하는 것은 판정 사다리가 막는 일임(`설계판단`).

## 2. 자문 반대 가설 검증

자문 의견: **"런치픽은 단일 에이전트 + 도구 호출로 충분하며 멀티 에이전트화는 오판임."**

| 구분 | 내용 | 근거 출처 |
|------|------|----------|
| **동의하는 부분** | 실시간 추천 경로만 보면 자문이 옳음. Q1 아니오 · Q2 판정 불가이며, LLM 호출은 근거 문장 생성 1건뿐임. 나머지는 저장소·외부 API 조회임 | `설계판단` |
| **다른 부분** | 사다리 결과는 **Q3 예 → 3개 분할**임. 이유는 업무량이 아니라 **알레르기 항목명의 권한 등급**임. 하드필터를 도구로 두면 LLM이 호출 여부를 판단하게 되어 위반 0건을 구조로 보장하지 못함 | `US:UFR-MBR-040#검증요구사항` |
| **자문과 실질 차이** | A-1·A-3은 모델을 쓰지 않는 결정론적 실행 단위임. 즉 "LLM 에이전트는 1개"라는 자문의 뼈대는 유지됨. 갈리는 지점은 **필터를 도구로 두느냐(자문) / 앞단 고정 단계로 두느냐(본 설계)** 한 곳임 | `설계판단` |

**결론 — 사다리 결과가 자문과 다름.** 자문의 "단일 에이전트"는 채택하지 않되, 자문이 지적한  
"과도한 멀티화"는 콜드스타트·대체 추천을 별도 에이전트로 만들지 않는 방식으로 반영함(3절 참조).

| ID | 에이전트명 | ② 대응 내부 실행 단위 |
|----|-----------|---------------------|

### 별도 에이전트로 만들지 않은 것 3건

| 후보 | 흡수 위치 | 사유 |
|------|----------|------|
| J-5 콜드스타트 안전망(`UFR-REC-030`) | A-1 안의 분기 | 읽는 자료와 권한 등급이 A-1과 같음. 후보를 고르는 방식만 다름. 동사로 쪼개면 에이전트만 늘어남 |

새로 둘 필요가 없음. 결제(E-5)는 이번 범위 밖임(`BM:2-가격계층#팀플랜` 판정과 별개로 PAY는 자율 판단 없음).

## 4. 에이전트별 계약 7칸

에이전트 1건을 1개 표(7행)로 표현하며 3건에 같은 구조를 적용함.  
**이 문서의 `입출력 형식` 칸이 키 이름의 단일 출처임.** 후행 인용 형식은 `③ {에이전트명} · 출력`으로 고정함.  
`공유` = 다른 에이전트도 읽는 출력 키(④ 상태 스키마의 씨앗).

### 4-1. A-1 「안전 후보 선별」

| 계약 항목 | 내용 | 근거 출처 |
|----------|------|----------|
| 책임 | 컨텍스트를 모아 알레르겐·식이제한 위반 식당을 뺀 후보 식당 목록 1건 산출 | `US:UFR-REC-010#검증요구사항` |
| 접근 가능한 정보 항목 | `회원·취향`(회원 참조키·직군 클러스터 코드·취향 카테고리 코드·누적 피드백 건수) · `식이제한`(알레르기 항목명·식이 유형) **포함** · `식사기록`(최근 7일 카테고리 코드 배열·최근 3일 식당ID 배열) · `식당 캐시`(식당ID·표시명·원재료 알레르겐 코드·거리·영업상태 `[확인필요: 식당 영업 상태 필드]`) · 현재 위치 좌표(위도·경도) **포함** · 날씨 코드 · 요일·시각 코드 — 회원 이메일·닉네임 **제외** · 식당명·메뉴명 원문 이력 **제외** | `US:UFR-REC-010#입력요구사항` · `US:NFR-SYS-030#체크리스트` |
| 입출력 형식 | 입력 `{member_ref: str 필수, geo_point: {lat: float, lng: float} 필수, at: datetime 필수, manual_area_code: str 선택}` / 출력 `{candidates: list[{restaurant_id: str, display_name: str, distance_m: int, walk_min: int}] 필수 `공유`, filter_applied: bool 필수 `공유`, excluded_count: int 필수, context_tags: list[str] 필수 `공유`, coldstart: bool 필수 `공유`, prior_source: str 선택}` | `US:UFR-REC-010#입력요구사항` · `US:UFR-REC-010#성공1` |
| 사용 도구 | (E)지도·식당 API `읽기` · (E)날씨 API `읽기` · 회원·취향 저장소 `읽기` · 식당 캐시 저장소 `읽기` · 식사기록·피드백 저장소 `읽기` — 저장소 접근 수단 이름은 `[확인필요: 커넥터명 확정]`(⑤ 미생성) | `설계판단`(② 외부 서비스 목록 E-2·E-3, ② 내부 구성도 저장소 이름) |
| 사용 모델 | **모델 미사용(결정론적 실행)** — 배정 이유: 하드필터 위반 0건은 확률적 모델로 보장 불가하므로 LLM을 쓰지 않음. 모델 단가·지연이 0이므로 Q-1 3초 예산을 깎지 않음 | `설계판단` |
| 성공 기준 | 알레르겐 포함 식당의 후보 잔존 0건 · 최근 3일 내 동일 식당 후보 0건 · 필터 판정이 불확실한 식당을 후보에서 뺀 기록 100% 저장 | `US:UFR-REC-010#검증요구사항` · `US:UFR-MBR-040#검증요구사항` |
| 중단 조건 | ① 좌표와 수동 입력 지역 코드가 모두 없음 → 중단 ② 원재료 알레르겐 코드가 없는 후보를 만남 → 해당 식당을 후보에서 뺀 뒤 계속하고, 후보가 0건이 되면 중단 ③ `filter_applied`가 true가 아닌 출력이 만들어지려는 시점 → 즉시 중단 — 판정 주체: 오케스트레이터 / 시점: ①②는 노드 종료 직후, ③은 출력 직렬화 직전 | `US:UFR-REC-010#실패1` · `US:UFR-MBR-040#검증요구사항` |

## 6. 민감 필드 × 권한 매트릭스 (⑤로 넘기는 C-1 초안)

②의 후행 소비처가 HARD로 넘긴 **TB-2가 넘기지 않는 항목 4종**을 필드 단위로 펼침.

**⑤가 이 표를 받아 변환 지점을 걸고, 되돌려 받은 결과로 ③을 1회 갱신함.**

### ⑤에 되묻는 3가지

| 되묻는 것 | 왜 필요한가 |
|----------|-----------|
