# 설계서 ⑤ 지식·도구 설계 — 런치픽(LunchPick)

작성: 2026-08-06 · 작성자: 지식니(지식·데이터 엔지니어) · 가이드: [05-지식도구설계-가이드](../guides/05-지식도구설계-가이드.md)  
선행 입력: [① 목표·품질속성 카드](01-목표품질속성카드.md)(SOFT) · [② 논리 아키텍처](02-논리아키텍처.md)(HARD) ·  
[③ 에이전트 역할 계약서](03-에이전트역할계약서.md)(CYCLE C-1)  
**CYCLE C-1 상태: 되돌려 반영 1회 완료(2판, 2026-08-06).** ③ 6절 권한 매트릭스와 8절을 필드 단위로  
대조해 `[확인필요: 선행 미생성]` 5행을 닫음. 남은 순환은 ④↔⑤ C-2뿐임

**성격 선언** — ⑤는 **무엇을 근거로 답하는가**만 정함. 단계 순서·타임아웃(④) · 배포 단위·포트(⑦) ·  
관측 스팬·비용 상한(⑥)은 여기에 없음. Mock·실물 구분의 **값 주인은 ②**이며 ⑤는 펼쳐 쓰기만 함(G-10).

**쉬운 말 먼저** — 이 문서에 나오는 낱말을 그 자리에서 한 줄로 풀어 씀.  
`정형`은 표(행·열)로 정리된 데이터, `비정형`은 문장·문서처럼 틀이 없는 데이터임.

## 1. 질문 유형 목록 — 사용자가 실제로 치는 문장

가이드 2절 1단계임. 화면에서 실제로 벌어지는 일을 문장으로 적음.  
런치픽은 자유 입력창이 없는 앱이므로 "치는 문장"은 **버튼·화면 진입이 대신 던지는 질문**임.

| # | 질문 유형 | 대표 질문 3개 이상 | 언제 발생하나 | 근거 출처 |
|---|---|---|---|---|
| K-1 | (가) 주변 후보 선별 | "지금 내 주변에서 뭘 먹을까" / "여기서 걸어갈 만한 곳은" / "최근 간 곳 말고 다른 데" | 앱 메인 진입 시 자동 | `US:UFR-REC-010#입력요구사항` |
| K-2 | (나) 왜 이 메뉴인가 | "왜 이 메뉴인가" / "무엇을 보고 고른 건가" / "이 추천을 얼마나 믿어도 되나" | 추천 카드의 `왜?` 탭 | `US:UFR-REC-020#검증요구사항` |
| K-3 | (다) 내 취향이 어떻게 변했나 | "지난 30일 뭘 먹었나" / "내가 제일 자주 먹는 종류는" / "만족도가 나아지고 있나" | 이력·인사이트 화면 진입 | `US:UFR-REC-110`, `US:UFR-REC-120` |
| K-4 | (라) 데이터가 없는 첫 사용자 | "가입 첫날인데 뭘 추천하나" / "이 근처 사람들은 뭘 먹나" / "학습 중이면 무엇으로 대신하나" | 누적 피드백 5건 미만 | `US:UFR-REC-030#검증요구사항` |
| K-5 | (마) 낱말을 코드로 고정 | "`한식-국물`은 어떤 코드인가" / "`땅콩`은 어느 식재료와 같은가" / "`비건`이 막는 재료는" | K-1 ~ K-4 전부의 앞단 | `설계판단`(② TB-2 통과 항목) |

**K-5는 위임 프롬프트가 준 (가) ~ (라)에 없던 유형임.** ②가 TB-2로 넘기는 것을 `취향 카테고리 코드`  
(예: `KOR-SOUP`)로 못 박았으므로, 코드 체계를 고정하지 않으면 K-1 ~ K-4가 모두 성립하지 않음.  
질문 유형을 4개로 끝내면 이 앞단이 문서에서 사라짐 → 1행 신설함(`신설`).

**멈춤 신호 점검** — 가이드 2절은 "질문 3개가 전부 같은 경로로 몰리면 질문을 잘못 뽑은 것"이라 함.  
K-1 ~ K-5의 채택 경로는 3종으로 갈림(정형 반경 조회 · 컨텍스트 조립 · 고정 집계 · 사전 조회).  
한 경로로 몰리지 않으므로 멈춤 신호에 걸리지 않음.

## 2. 경로 매핑 판정표 — 가이드 2절 2단계를 질문마다 다시 돌린 결과

| # | 질문 유형 | 채택 경로 | 채택 근거 | 버린 대안(이유) | 근거 출처 |
|---|---|---|---|---|---|
| K-1 | 주변 후보 선별 | **정형 반경 조회 + 결정론 하드필터 + 취향 코드 가중 정렬** | 답이 `조건에 맞는 목록과 정렬`임. 원천이 식당 캐시 표와 취향 프로파일 표뿐임 | 벡터 검색 — 반경 500m 후보가 수십 개 규모라 색인·갱신 비용이 이득을 넘음(`BM:6-GTM#Launch` 반경 500m) · GraphRAG — 식당 간 관계를 건너가는 질문이 없음 · NL2SQL — 문장이 화면에서 고정되어 SQL을 매번 생성할 이유가 없음 | `US:UFR-REC-010#검증요구사항`, `BM:6-GTM#Launch` |
| K-2 | 왜 이 메뉴인가 | **컨텍스트 조립 + LLM 문장 생성 + 반영 태그 기록**(검색 아님) | 근거의 원천이 문서가 아니라 우리 표의 값임(날씨·이력·취향). 찾아올 문단이 없고 이미 손에 있는 값을 문장으로 바꾸는 일임 | 벡터 RAG — 검색할 문서가 존재하지 않음. 근거는 입력값 자체임 · GraphRAG — 관계를 따라갈 대상이 없음 · 사람이 쓴 문구 템플릿 — 조합 수가 컨텍스트 4종 곱이라 문구가 폭발함 | `US:UFR-REC-020#검증요구사항`, `핵심솔루션:A8#상세설명` |
| K-3 | 취향 인사이트 | **고정 집계 쿼리(읽기 전용)** | 답이 개수·비율·추이임. 벡터 검색이 원리적으로 답할 수 없는 구간임 | NL2SQL — 화면이 던지는 질문이 3종으로 고정(카테고리 Top 5·주간 패턴·만족도 추이)이라 SQL 생성이 불필요하고 검증 비용만 늘어남 · 벡터 RAG — 집계·개수 세기 불가 | `US:UFR-REC-120#검증요구사항` |
| K-4 | 콜드스타트 | **정형 조회(직군 클러스터 Prior 표) + 지역 인기 집계 가중** | 개인 데이터가 없는 상태의 정의 자체가 `개인 벡터 부재`임. 남은 근거는 집단 통계뿐임 | 개인 취향 벡터 유사도 — 콜드스타트는 그 벡터가 없는 상태임(자기모순) · 벡터 RAG — 같은 이유 | `US:UFR-REC-030#검증요구사항` |
| K-5 | 낱말 고정 | **용어사전·온톨로지(코드 매핑 표)** | 사내 코드를 1:1로 고정해야 하는 경우임. 알레르기 항목명 ↔ 식재료, 음식 종류 ↔ 카테고리 코드 2쌍 | 벡터 유사도 매칭 — 알레르기 판정을 확률로 하면 ① Q-3 `위반 0건`이 원리적으로 불가함 · LLM 판정 — 같은 이유 | ① 4절 Q-3, `US:UFR-MBR-040#검증요구사항` |

**"모든 걸 RAG로"를 하지 않은 결과** — 5개 유형 중 벡터 RAG 채택은 **0건**임.  
런치픽 데이터는 케이스 요약대로 대부분 정형이며, 사용자가 자유 문장을 치는 화면이 없음.  
가이드 6절 1번(전부 벡터 RAG로 밀어붙임)의 반대 방향 함정 — 정형만 보고 비정형을 놓쳤는지는 3절에서 따로 점검함.

### 관계 검색의 강점·한계 구간 (GraphRAG 판정 근거)

| 구간 | 내용 | 근거 출처 |
|---|---|---|
| 강점 | `식당 ↔ 메뉴 ↔ 식재료 ↔ 알레르겐` 3홉을 따라가면 "이 알레르겐을 품은 메뉴를 파는 식당"을 한 번에 뽑을 수 있음(홉은 관계를 한 번 건너감) | `설계판단` |
| 한계 | 그 3홉의 **재료 쪽 데이터가 지금 없음**. 외부 식당 API가 식재료를 주는지 확인 안 됨 → 그래프를 만들 원료가 없음 | `[확인필요: 식당 식재료·알레르겐 정보 원천]` |
| 판정 | **MVP에서 GraphRAG를 뺌.** 원료 확보 → 개체·관계 추출 → 그래프 구축이 14주 스프린트 계획에 없음. 트레이드오프는 아래 문단에 적음 | `US:스프린트계획#MVP기준` |

**GraphRAG를 넣으면 무엇이 커지나(트레이드오프)** — 식재료 추출은 메뉴 텍스트 수십만 건 단위 LLM  
호출이 되므로 `BM:3-비용구조#변동비용`의 LLM API 월 300만 원 항목과 직접 다툼. 또 관계 갱신 주기가  
식당 캐시 갱신 주기에 얹혀 지연이 늘어 ① Q-1 `3초`를 깎음. 그래서 2차 스프린트 이후로 미룸.

## 3. 정형 접근 경로 (표 이름 고정 — 다른 말로 바꾸어 쓰지 않음)

방식은 **표 조회(SQL 읽기 전용)** 로 고정하고, 대상은 ②의 저장소 6개 범위로 한정함.

| 대상 | 조회 목적 | 연결 키 | 접근 금지 항목 | 근거 출처 |
|---|---|---|---|---|
| 회원·취향 저장소(DB1) — 취향 프로파일 | K-1 취향 코드 가중치 · K-2 근거 태그의 `취향` 성분 | 회원 ID | 이메일 · 닉네임 · 결제 수단 | `US:UFR-MBR-020#처리결과`, `US:UFR-REC-010#검증요구사항` |
| 회원·취향 저장소(DB1) — 알레르기·식이제한 | K-1 하드필터 조건 취득 | 회원 ID | **외부 전송 전 항목 전체**(F-1 참조. 읽기는 필터 단계 내부로 한정) | `US:UFR-MBR-040#검증요구사항` |
| 식당 캐시 저장소(DB4) | K-1 반경 후보 목록 · 폐업 제외 · 도보 소요시간 | 좌표 + 반경, 식당 ID | 없음(전 항목 허용) | `ES:규제표#식품위생법`, `US:UFR-REC-060#검증요구사항` |
| 식사기록·피드백 저장소(DB3) | K-1 최근 7일 이력 · K-3 30일 집계 · K-4 콜드스타트 감지(피드백 5건 미만) | 회원 ID + 날짜 범위 | 없음(전 항목 허용) | `US:UFR-REC-010#검증요구사항`, `US:UFR-REC-110#검증요구사항` |
| 추천 이력 저장소(DB2) | K-1 최근 3일 동일 식당 제외 · K-2 근거·태그 사후 대조 | 회원 ID, 추천 ID | 없음(전 항목 허용) | `US:UFR-REC-010#검증요구사항`, `US:UFR-REC-020#입력요구사항` |
| 구독·결제 저장소(DB5) | K-3 이력 조회 기간 판정(무료 30일 / 프리미엄 무제한) | 회원 ID | 결제 수단 원문 · 카드 번호 | `US:UFR-REC-110#검증요구사항`, `BM:2-가격계층#프리미엄` |
| 코드 매핑 표(K-5 용어사전) | 음식 카테고리 코드 · 알레르기 항목명 ↔ 식재료 매핑 | 코드값 | 없음(전 항목 허용) | `설계판단`(② TB-2 통과 항목 `취향 카테고리 코드`) |
| 직군 클러스터 Prior 표 | K-4 콜드스타트 기본 확률 | 직군 코드 + 지역 코드 | `[확인필요: 직군 데이터 수집 경로]` | `US:UFR-REC-030#검증요구사항` |

**쓰기 금지 규칙** — 위 경로 전부 **읽기 전용 계정**만 씀. `INSERT` · `UPDATE` · `DELETE`를 막음.  
기록·갱신은 조회 경로가 아니라 각 서비스의 쓰기 경로에서 하며 ⑤의 접근 경로 목록에 넣지 않음.  
**행 수 상한** — 1회 응답 행 수 상한을 반드시 걺. 무료 플랜은 `30일` 범위가 원문 인용값이라 상한이  
자연히 생김(`BM:2-가격계층#무료`). 프리미엄은 무제한 이력이므로 상한 숫자가 따로 필요하나 원문에  
값이 없음 → `[확인필요: 이력 조회 1회 응답 행 수 상한]`. 지어내지 않음(가이드 7절 부분 통과, 17절 참조).

### 마지막 열 각주

`설계판단` 2행의 판단 근거임 — 코드 매핑 표는 ②가 TB-2 통과 형태를 `코드값`으로 못 박은 결과  
필연적으로 생기는 표임. 원문에 표 이름은 없으나 ② 3절 판정 없이는 경계를 넘길 수 없음.

## 4. 비정형 접근 경로 구분 (표 이름 고정)

후보 방식 4종을 전부 1행씩 두고 채택·미채택을 밝힘. 미채택 행을 지우면 버린 근거가 사라짐.

| 접근 경로 | 사용 질문 유형 | 대상 문서 | 선택 근거 | 근거 출처 |
|---|---|---|---|---|
| 용어사전·온톨로지(코드 매핑 표) — **채택** | K-5 낱말을 코드로 1:1 고정 | 음식 카테고리 코드 목록 · 알레르기 항목명 ↔ 식재료 매핑 표 | 알레르기 판정을 확률에 맡길 수 없음. ① Q-3 `위반 0건`은 결정론 매칭만으로 달성 가능함 | `US:UFR-MBR-040#검증요구사항`, ① 4절 Q-3 |
| 벡터 RAG(뜻이 가까운 문단을 찾아옴) — **미채택** | 해당 없음 | 식당·메뉴 설명 텍스트 · 외부 리뷰 | 자유 문장을 치는 화면이 MVP에 없음. 온보딩 입력은 카드 좋아요/싫어요 이진값, 피드백은 좋아요/별로 + 맛·양·속도 키워드뿐이라 문장 원천이 없음 | `US:UFR-MBR-020#입력요구사항`, `US:UFR-REC-090#입력요구사항` |
| GraphRAG(개체를 선으로 이어 두고 그 선을 따라감) — **미채택** | 해당 없음 | 식당–메뉴–식재료–알레르겐 관계 | 강점 구간은 실재하나 원료 데이터 부재 + 구축 비용이 14주 계획 밖임(2절 트레이드오프) | `US:스프린트계획#MVP기준`, `[확인필요: 식당 식재료·알레르겐 정보 원천]` |

## 5. 알레르기 하드필터가 경로 설계로 강제되는가 (자문 의견 반영)

자문 의견 — "알레르기 하드필터를 LLM 바깥 결정론 단계로 못 박는 강제 규칙이 가이드에 없음".  
②는 이미 필터를 TB-2 **앞**에 배치함(② 3절·5절 사유 2). ⑤에서 **경로 설계로도 강제되는지** 점검함.

| 점검 항목 | 강제되나 | 무엇이 강제하나 |
|---|---|---|
| LLM이 알레르기 항목명을 볼 수 없는가 | **강제됨** | C-1(LLM 커넥터) **입력 규격에 알레르기 필드가 아예 없음**. 스키마에 칸이 없으면 값을 넣을 경로가 없음(7절) |
| LLM이 필터를 대신 수행할 수 없는가 | **강제됨** | 같은 이유. 판정 근거가 되는 식재료 정보가 입력에 없으므로 LLM은 판정 자체가 불가능함 |
| 필터가 **실제로 실행됐는지** 확인되는가 | **강제 안 됨(공백)** | 입출력 키 이름만으로는 `후보 식당 목록`이 필터 통과분인지 원본인지 구분되지 않음 |
| 필터 규칙 버전이 추적되는가 | **강제 안 됨(공백)** | 사전(K-5)이 갱신되면 같은 입력에 다른 결과가 나오는데 어느 사전으로 걸렀는지 남지 않음 |

**⑤가 메우는 장치 2개(`신설`)** — C-1 입력 규격에 아래 2개 키를 둠. ③·④의 키를 고치는 것이 아니라  
커넥터 입력에 칸을 더하는 것임.

| 키명·타입 | 뜻 | 검사 규칙 |
|---|---|---|
| `filter_applied: boolean` | 하드필터 단계를 실제로 지났는지 | `false`면 C-1 호출을 거부함. 사람이 아니라 커넥터가 막음 |
| `filter_ruleset_version: string` | 어느 사전으로 걸렀는지 | 값이 없으면 거부. 추천 이력 저장소(DB2)에 함께 남겨 사후 대조에 씀 |

이 2개는 원문에 없는 **신설** 항목임. 가이드에 이 칸이 없어 ⑤가 직접 만든 것이며, 공백 사실을  
18절 `가이드 적용 기록`에 적음.

**C-1 반영(2026-08-06)** — ③이 A-1 출력에 `filter_applied: bool 필수 `공유``를 이미 두고 있었음  
(③ 4-1 `입출력 형식`). ⑤와 서로 보지 않은 상태에서 **같은 장치에 독립 수렴**함. ③ A-2의 중단 조건 ②도  
`filter_applied`가 true가 아니면 LLM 호출을 하지 않고 즉시 중단으로 못 박음. 따라서 이 2개 키의  
**값 주인은 ③ A-1 출력**이며, ⑤는 C-1 입력 규격에서 그 값을 받아 쓰는 쪽임(7절 표기 갱신).

### 오류율이 곧 추천 실패율이 되는 경로 (지목 2건)

| # | 경로 | 어떻게 실패로 번지나 | 무엇이 깨지나 |
|---|---|---|---|
| 1 | **식재료 정보 오류 → 알레르기 하드필터 위반** | 원천이 식재료를 주지 않거나 틀리면 필터는 "걸러야 할 것"을 못 알아봄. 이때 코드는 정상 동작하고 로그도 정상으로 남으므로 **위반이 조용히 지나감** | ① G-3 `위반 0건` · ① Q-3 안전성. 되돌릴 수 없는 피해임 |

그래서 `[확인필요: 식당 식재료·알레르겐 정보 원천]`은 이 설계서 전체에서 가장 무거운 미확정임.

### 커넥터 검증 기준 — 순서가 틀리면 인자가 다 맞아도 0점

지표 성질은 `A08 ToolCallAccuracy`를 그대로 씀. 이 지표는 **인자 정확도에 순서 정렬 여부(1 또는 0)를

|---|---|---|

| 병렬 허용 구간 | C-2와 C-3은 서로 결과를 쓰지 않으므로 유연 순서 모드 허용 | 두 호출 사이에 의존이 없음 |

**기대 호출 시퀀스의 값은 ④가 소유함.** ⑤는 채점 방식만 정하고 ④가 확정한 순서를 그대로 기대값으로  
받아 씀. ②가 못 박은 "필터는 TB-2 앞"이라는 제약만 ⑤가 인용함(② 5절 사유 2).

## 8. 민감 필드 분류표 (표 이름 고정)

②의 TB-2 미통과 4종을 전부 행으로 두고, 각 행의 변환 지점을 `TB-n`으로 인용함.

## 11. 골든셋 요약 (가이드 4절 (2))

정답을 먼저 만들고 검색을 고침. 순서가 반대면 고쳤는지 알 수 없음.  
**총 24문항**이며 질문 유형 5종을 섞음.

### 분포

| 문항 ID | 대응 질문 유형 | 문항 수 | 무엇을 묻나 |
|---|---|---|---|
| GS-1 ~ GS-6 | K-1 주변 후보 선별(일반) | 6 | 반경·최근 3일 제외·취향 가중 정렬이 기대 목록과 맞는지 |
| GS-7 ~ GS-10 | K-1 주변 후보 선별(**알레르기 보유 프로파일**) | 4 | 금지 식재료 포함 식당이 후보에 남아 있는지. 페일세이프 동작 포함 |
| GS-11 ~ GS-16 | K-2 왜 이 메뉴인가(**Q-2 채점**) | 6 | 근거 문장의 컨텍스트 태그가 **실제 입력값과 일치**하는지 |
| GS-17 ~ GS-20 | K-3 인사이트 집계 | 4 | 카테고리 Top 5 · 주간 패턴 · 만족도 추이 숫자가 정답과 완전 일치하는지 |

### 만드는 법 — 문의 로그가 없는 경우의 대체 절차

가이드 4절은 "실제 문의 로그에서 자주 나온 순으로 뽑음"이라 하나 런치픽은 **미출시 서비스라 로그가 없음**.  
대체 절차를 씀(`설계판단`).

1. `US:PainPoint추적` 10행을 빈도 순 후보 목록으로 씀(여정 단계별 실제 관찰 결과임)
2. 각 UFR의 `[검증 요구사항]` 항목을 문항 1개로 1:1 변환함 — 검증 요구사항이 곧 정답 조건임
3. 문항마다 `질문 / 정답 / 근거 문서·행`을 적음. 근거 없는 문항은 버림
4. 2명이 따로 풀어 답이 갈리면 버림
5. 클로즈드 베타 100명(`BM:6-GTM#Pre-launch`) 시작 후 실제 로그로 문항을 교체함

### 정답 판정 방법과 합격선

| 문항군 | 정답 판정 방법 | 합격선 | 값 성격 | 근거 출처 |
|---|---|---|---|---|
| GS-1 ~ GS-6 | 기대 식당 ID 집합과 실제 후보 집합 비교. 순서는 상위 3개까지만 봄 | 정답 포함률 90% 이상 | `신설`(원문에 값 없음) | `US:UFR-REC-010#검증요구사항` |
| GS-7 ~ GS-10 | 금지 식재료 포함 식당이 후보에 **1건이라도 있으면 불합격** | **위반 0건 = 100% 통과** | 원문 인용 | ① 3절 G-3, `US:UFR-MBR-040#검증요구사항` |
| GS-11 ~ GS-16 | 근거·스코어 동반 여부 + 근거의 `context_tags`를 그 요청의 실제 입력값과 대조 | 동반 노출률 **100%** · 태그 일치율 **95% 이상** | 동반 노출률은 ① G-2 인용 · 태그 일치율은 ① Q-2의 `추정` 값을 그대로 인용 | ① 3절 G-2, ① 4절 Q-2 |
| GS-17 ~ GS-20 | 같은 조건으로 손계산한 숫자와 완전 일치 | **100%**(숫자는 결정론이므로 부분 점수 없음) | `설계판단` | `US:UFR-REC-120#검증요구사항` |
| GS-21 ~ GS-23 | 콜드스타트 감지 여부 · 후보 3개 채움 · 안내 문구 표시 3항목 모두 만족 | 100% | 원문 인용(감지 기준 5건) | `US:UFR-REC-030#검증요구사항` |
| GS-24 | 사전 미등록 낱말에 임의 매칭이 일어나면 불합격 | 임의 매칭 0건 | `설계판단` | ① 4절 Q-3 |
| 커넥터 호출 | `ToolCallAccuracy`(엄격 순서) — 순서 틀리면 0점 | 1.0 | `신설`(A08 지표 성질 적용) | 7절 검증 기준 |

**Q-2 채점 문항이 이 골든셋의 핵심임** — GS-11 ~ GS-16은 근거 문장이 그럴듯한지를 보지 않음.  
`context_tags`에 `날씨`가 적혀 있으면 그 요청에 실제로 날씨 코드가 입력됐는지를 확인함.  
태그가 입력에 없는 것을 말하면 불합격임. 이것이 ① Q-2 `태그 일치율`을 실제로 재는 방법임.

**태그 일치율 95%는 ①의 `추정` 값임.** ⑤가 새로 정하지 않고 그대로 인용하며, ①의  
`[확인필요: 근거 태그 일치율 목표]`가 닫히면 같이 갱신함.

## 18. 가이드 적용 기록
