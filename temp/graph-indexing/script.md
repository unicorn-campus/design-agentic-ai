## 슬라이드 1 — 그래프DB 인덱싱 과정: 벡터DB와 비교

- 리드문: 벡터DB 인덱싱 가운데에 'LLM이 글을 노드와 관계로 바꿔 그래프로 저장하는 단계'가 끼어든 것임

### 구간 머리표 3개 (세로 칸 위) · 두 줄 배치

| 구간 | 머리표 | 벡터DB 줄 | 그래프DB 줄 |
|------|--------|-----------|-------------|
| A | 똑같음 | 로드(원본 읽기) → 정제·가명처리(실명 → 가명) → 청킹(글 자르기) | ① 로드 → ② 정제·가명처리 → ③ 청킹 |
| B | 그래프DB에만 있음: 글 → 노드와 관계 | (긴 화살표) 그래프 단계 없이 바로 임베딩 | ④ 엔티티·관계 추출 → 같은 이름 병합(보강) → ⑤ 지식 그래프 구축 → 사전요약(선택, 커뮤니티 요약) |
| C | 똑같음 | 임베딩(청크 → 벡터) → 적재(벡터DB로) | ⑥ 임베딩(청크 + 노드 설명) → ⑦ 적재(KG + 벡터) |

### 그래프DB 줄 아래 — 누가 하나 (단계별 필)

| 단계 | ① 로드 | ② 정제·가명처리 | ③ 청킹 | ④ 추출 | 병합 | ⑤ 구축 | 사전요약 | ⑥ 임베딩 | ⑦ 적재 |
|------|--------|----------------|--------|--------|------|--------|----------|----------|--------|
| 누가 | 코드 | 코드 | 코드 | LLM | 코드 + LLM | 코드 | 코드 + LLM | 임베딩 모델 | 코드 |

- 색: LLM(블루 채움) · 코드 + LLM(틴트 + 블루 테두리) · 임베딩 모델(네이비 채움) · 코드(흰 바탕)

### 그 아래 — 나오는 것

| 칸 | 나오는 것 |
|----|-----------|
| 로드 ~ 청킹 | 청크(글 조각) — 벡터DB와 같음 / 이름·연락처 같은 개인정보는 가명으로 |
| 추출 · 병합 | (A사) ─출시→ (B카드) / 같은 이름 합침, 설명은 LLM 요약 |
| 구축 · 사전요약 | 노드·관계 연결망(KG) 완성 / 묶기는 알고리즘, 요약은 LLM |
| 임베딩 · 적재 | 임베딩: 청크 + 노드 설명 / (관계 연결은 임베딩 안 함) / 적재: KG + 벡터 함께 저장 |

### 맨 아래 — 한눈에 비교 (카드 3개)

| 카드 | 벡터DB | 그래프DB |
|------|--------|----------|
| 글을 무엇으로 바꾸나 | 숫자 벡터 → 뜻이 비슷한 글 찾기 | 노드·관계 → 누가 누구와 이어지나 |
| 누가 바꾸나 | 임베딩 모델 → 빠르고 쌈 | LLM(추출·요약)까지 → 느리고 비쌈 |
| 무엇에 강한가 | 한 문단으로 끝나는 질문 | 여러 단계 연결 · 전체 경향 |

### 발표자 노트

- 그래프DB 인덱싱은 벡터DB 인덱싱과 앞뒤가 똑같음. 앞의 로드·정제·청킹, 뒤의 임베딩·적재는 그대로임
- 다른 점은 청킹과 임베딩 사이에 끼어드는 네 단계임. LLM이 청크마다 글을 읽고 사람·회사 같은 노드(엔티티)와  
  '근무한다' 같은 관계를 한 번의 호출로 함께 뽑음
- 같은 노드가 여러 청크에서 나오면 이름·종류가 같은 것을 코드로 하나로 합치고, 청크마다 따로 붙은 설명은  
  LLM이 한 줄로 요약함
- 지식 그래프 구축은 합친 노드·관계를 그래프로 엮는 일이라 코드가 함
- 사전요약은 Leiden 같은 알고리즘이 노드를 주제별로 묶고, 묶음마다 LLM이 요약을 씀.  
  '전체 경향' 질문을 위한 선택 단계임
- 즉 LLM은 추출과 요약(병합 설명 · 커뮤니티 요약)에만 씀
- '삼성'과 '삼성전자'처럼 이름이 다른 같은 대상을 합치는 일(엔티티 해소)은 기본 병합으로는 안 되며  
  따로 붙이는 작업임
- 임베딩은 그래프DB에서도 LLM이 아니라 벡터DB와 같은 임베딩 모델이 맡음. LLM은 글을 읽고 추출·요약하는 데만 씀  
  (MS GraphRAG 설정도 completion_models(gpt-4.1)와 embedding_models(text-embedding-3-large)를 따로 둠)
- 임베딩 대상은 청크와 노드 설명(사전요약을 했으면 커뮤니티 요약도)이고, 관계 연결 자체는 임베딩하지 않고  
  그래프 그대로 둠
- 마지막 적재에서 KG와 벡터를 함께 그래프DB에 저장함(Neo4j는 벡터를 노드 속성으로 두고 벡터 인덱스를 검).  
  검색할 때는 벡터로 비슷한 노드·청크를 먼저 찾고 KG의 관계를 따라 넓혀 감
- 정제 단계에서 이름·연락처 같은 개인정보를 가명으로 바꿔 두어야 LLM 추출과 그래프 노드에 실명이 남지 않음
