# 정제 및 가명 처리 슬라이드 설명 스크립트

## 제작 메모

전체 분량은 1장입니다. 16:9 화면과 Pretendard 글꼴을 사용합니다.  
표, 예시 상자, 연결선은 PowerPoint에서 직접 수정할 수 있는 표와 도형으로 구성합니다.

## 1. 정제 및 가명 처리

### 핵심 메시지

정제는 검색에 방해되는 반복·형식 정보를 줄이고, 가명 처리는 사람을 직접 알아보는 값을 목적에 맞는 표현으로 바꿉니다.

### 화면 구성

화면을 좌우 두 영역으로 나눕니다. 왼쪽에는 정제, 오른쪽에는 가명 처리를 배치합니다.  
각 영역은 대상과 방법을 표로 설명하고, 아래에는 처리 전후 가상 예시를 둡니다.

#### 왼쪽: 정제 대상과 방법

| 정제 대상 | 처리 방법 |
|---|---|
| 머리말·꼬리말 | 여러 페이지의 위·아래에서 반복되는 위치와 문구를 확인한 뒤 제거 |
| 페이지 번호 | 본문에서는 제거하고 `page`·`page_end`와 같은 출처 메타데이터로 유지 |
| 공백·빈 줄·제어문자 | 연속 공백과 빈 줄을 정규화하되 제목·조항·문단 구분자는 보존 |

처리 전후 가상 예시는 다음처럼 표시합니다.

`처리 전: 회원 표준약관 | 12쪽 | 제6조 이용정지 ... | - 12 -`  
`처리 후: 제6조 이용정지 ...`  
`메타데이터: page=12`

#### 오른쪽: 가명 처리 대상과 방법

| 가명 처리 대상 | 처리 방법 |
|---|---|
| 이름·회원 ID | 적용 범위 안에서 같은 대상에 같은 가명 ID 부여. 예: `고객_001` |
| 전화·이메일·고유번호 | 식별값을 유형 토큰이나 삭제 표기로 치환. 예: `[전화번호]` |
| 생년월일·상세주소 | 필요한 수준만 남도록 일반화. 예: `1992-04-18`을 `30대`로, `서울시 강남구`를 `서울시`로 변환 |

처리 전후 가상 예시는 다음처럼 표시합니다.

`처리 전: 김민지(M-87321), 010-1234-5678, 1992-04-18, 서울시 강남구`  
`처리 후: 고객_001, [전화번호], 30대, 서울시`  
`관계 유지: 다른 상담의 같은 사람도 고객_001`

두 예시 위에는 `설명용 가상 예시` 라벨을 표시합니다.

#### 하단 구현 구분 문구

슬라이드 하단에 연한 파란색 띠를 두고 다음 문구를 표시합니다.

`현재 코드: 본문 개인정보는 [삭제]·연령대로 치환하고, 회원·상담사는 SHA-256 기반 가명 ID를 메타데이터에 저장`

### 발표자 설명

정제는 검색에 필요하지 않은 반복 문구와 형식 노이즈를 줄이는 처리입니다. 머리말과 꼬리말은 위치만 보고 지우면
본문 제목을 잘못 제거할 수 있으므로, 페이지 위·아래의 위치와 여러 페이지에서의 반복 여부를 함께 확인합니다.
페이지 번호는 검색 본문에서 제거해도 출처 표시에 필요하므로 페이지 메타데이터로 유지합니다. 조항 제목과 문단 경계처럼
의미를 나누는 구조는 보존합니다.

가명 처리 방법은 사용 목적에 따라 구분합니다. `[전화번호]`와 같은 유형 토큰은 값의 종류를 남기지만 같은 사람인지까지
연결하지 않습니다. `고객_001`과 같은 가명 ID는 정한 적용 범위 안에서 같은 대상에 같은 값을 부여하므로 여러 기록의
관계를 유지할 수 있습니다. 생년월일과 상세주소는 검색에 필요한 수준만 남도록 연령대와 넓은 지역으로 일반화할 수 있습니다.

가명 ID를 만들 때에는 같은 값을 유지할 범위를 문서, 데이터셋, 시스템 가운데 어디까지로 할지 먼저 정합니다. 원문과
가명 ID의 매핑표나 비밀키를 사용한다면 본문과 분리하고 접근을 제한합니다. 가명 처리는 원문 식별 가능성을 낮추는
처리이며, 이 슬라이드는 법적 익명화 완료나 모든 개인정보의 검출을 보증하지 않습니다.

화면의 가명 처리 예시는 일반적인 설계 예시입니다. 현재 `vector-bm25` 코드는 상담의 명시 필드와 전화번호, 이메일,
카드번호, 회원번호 형식을 찾아 본문에서 `[삭제]`로 치환하고, 생년월일·나이는 연령대로 바꿉니다. 회원과 상담사는
원문 문자열의 SHA-256 앞 16자리를 사용한 안정 가명 ID를 메타데이터에 저장합니다. 이 값은 비밀키 기반 암호화나
익명성 보증이 아닙니다. 잔존 검사도 코드에 정의된 형식을 확인하는 보완 검사이며 모든 개인정보 유형을 검출하지는 않습니다.

정제 규칙이 필요한 구분자와 구조를 보존하면 청킹 전에 적용해도 본질적인 문제가 없습니다. 이 장에서는 처리 시점보다
무엇을 제거하고, 무엇을 가명 ID·유형 토큰·일반화 값으로 남길지를 구분하는 데 초점을 둡니다.
