## 장표 1. 인덱싱 워크플로우 구성안

- 제목: 인덱싱 워크플로우 구성안
- 리드문: 서브 워크플로우는 준비, 반영, 정리를 따로 제공하고, 언제 부를지와 게시는 오케스트레이터가 정함

**도형 구성**

1. 오케스트레이터 단계 띠(y 1.9 ~ 2.62): 네이비 배지 「오케스트레이터」 + 칩 5개
   ① 세대 ID 발급(gen-X) → ② 공통 단계(청킹 결과 파일 생성) → ③ 인덱스 구축(서브 워크플로우 호출) → ④ 검증(chunk_id 목록 비교)
   → ⑤ 게시(활성 세대 파일 교체, 네이비)
2. ③ 서브 워크플로우 상자(y 2.78 ~ 4.7): ③에서 내려오는 화살표, ④로 올라가는 화살표와 「준비 보고를 ④로」
   - 두 줄. 왼쪽 네이비 라벨 + 구간 라벨(준비는 다크, 반영은 블루, 정리는 다크) + 단계 칩. 두 줄의 구간 위치를 맞춤
   - KG 구축: 준비 K1 추출 단위 나누기, K2 엔티티와 관계 추출, K3 가지치기(결과 보관) /
     반영 K4 Neo4j 저장(새 청크 넣기), K5 병합(관련 엔티티만), K6 노드 설명 임베딩 / 정리 K7 옛 청크 지움(고아 엔티티 정리)
   - 검색엔진 인덱싱: 준비 S1 임베딩(바뀐 것만), S2 키워드 분석(사전과 별칭, 결과 보관) /
     반영 S3 검색엔진에 쓰기(card_chunks-gen-X) / 정리 없음(점선)
3. 모드별 호출 순서 두 줄(y 4.86 ~ 6.36)
   - 전체 재색인(순서 불필요): K1 ~ K7 와 S1 ~ S3 병렬(둘 다 새 세대에 씀) → ④ 검증 → ⑤ 게시
   - 증분 색인(순서 필요): 준비(병렬, K1 ~ K3, S1 ~ S2) → 반영 K4 ~ K6(KG에 새 청크 넣기) → 반영 S3(검색엔진 문서 교체)
     → 정리 K7(KG 옛 청크 지우기) → 기록 갱신(입력 지문 갱신)
4. 약속 카드 4개(y 6.52 ~ 7.92)
   - 서브 워크플로우는 인덱스 구축만 함(사용자 수정 제목): 준비, 반영, 정리만 제공. 활성 세대 파일은 안 바꿈
   - 활성 세대 파일은 하나: 검색기는 요청마다 한 번 읽고 같은 세대로 두 곳을 조회
   - 실패하면 게시 안 함: 준비 결과를 보관해 반영만 다시 실행
   - 별도 처리: 되돌리기와 옛 세대 정리는 흐름 밖에서 함
- "에이전트가 아닌 워크플로우(LLM은 K2 추출의 도구로만)"는 공간 때문에 발표자 노트로 옮김

**발표자 노트**

인덱싱은 오케스트레이터, KG 구축, 검색엔진 인덱싱 세 워크플로우로 나눕니다. 서브 워크플로우 두 개는 준비, 반영, 정리를 따로
부를 수 있게 만들고, 언제 무엇을 부를지는 오케스트레이터가 모드에 따라 정합니다. 서브 워크플로우는 활성 세대 파일을 바꾸지 않습니다.
준비는 아무 데도 쓰지 않고 계산만 해서 결과를 보관합니다. 반영은 Neo4j나 검색엔진에 씁니다. 정리는 KG에서 옛 청크와 근거를 잃은
엔티티를 지웁니다.
전체 재색인은 둘 다 새 세대에 쓰므로 게시 전까지 아무에게도 보이지 않습니다. 그래서 두 서브 워크플로우를 처음부터 끝까지 병렬로
돌리고, chunk_id 목록을 검증한 뒤 활성 세대 파일을 바꿉니다.
증분 색인은 지금 쓰는 세대에 바로 쓰므로 쓰는 순간 보입니다. 그래서 준비만 병렬로 하고, 반영은 KG에 새 청크 넣기,
검색엔진 문서 교체, KG 옛 청크 지우기 순서로 합니다. 그래프는 먼저 넣고 나중에 지워서, 바뀌는 동안에도 검색이 찾은 chunk_id가
그래프에 있게 합니다.
준비 결과를 보관하므로 반영에서 실패해도 오래 걸리는 계산을 다시 하지 않습니다. 되돌리기와 옛 세대 정리는 이 흐름과 따로 처리합니다.
세 워크플로우 모두 순서가 정해진 처리라 에이전트가 필요 없고, LLM은 K2 추출의 도구로만 씁니다.

## 사람 검토와 결정 반영(2026-10-19)

- 사용자가 PowerPoint에서 약속 1번 제목을 "서브 워크플로우는 인덱스 구축만 함"으로 고침 → `build.js`에 그대로 옮김
- 사용자 결정: 세대 전환의 이름표를 **활성 세대 파일** 하나로 함("이름표" 표현을 모두 바꿈)
  - 그래서 약속 1번 설명 "별칭과 Neo4j 활성 세대를 바꾸지 않음"은 "활성 세대 파일을 바꾸지 않음"으로 바꿈
  - 검색기는 파일에서 gen-X를 읽어 `card_chunks-gen-X` 인덱스와 Neo4j `generation = gen-X`를 직접 조회함
- 남은 일(사용자가 나중에 요청): 세대 전환을 오케스트레이터가 하므로 「④ 별칭 전환」 장표(`temp/alias-switch`)를 다시 만듦.
  「검색 엔진에 쓰기」 2장의 별칭 비교 카드와 콜아웃도 이 결정에 맞춰 함께 살펴봄
- 고치기 전 덱은 `워크플로우구성.before-rename.pptx`

## 사람 검토 2차 반영(2026-10-19)

- 사용자 지적: 두 서브 워크플로우를 병렬로 돌리면서 "증분 색인은 KG 먼저"라고 하면 어긋나 보임
  → 전체 재색인(새 세대, 병렬)과 증분 색인(활성 세대에 바로 씀, 순서 필요)을 구분해 적음.
  증분 색인 규칙은 "계산은 병렬, 반영은 K4 새 청크 넣기 → S3 검색엔진 교체 → KG 옛 청크 지우기"로 바꿈
- 사용자 요청 반영
  - ③ 단계 이름을 「인덱스 구축」으로 바꿈
  - ⑥ 되돌리기(옛 세대 정리 포함)를 흐름에서 빼고 "별도 처리"로 적음
  - 서브 워크플로우 단계에 번호를 붙임. 사용자 제안 `K-a` 대신 `K1 ~ K6`, `S1 ~ S3`을 씀
    (이유: `1-a`, `1-b`가 이미 아키텍처 방식 이름이라 `K-a`가 같은 계열로 읽힐 수 있고, 숫자가 순서를 바로 보여 줌)
  - "갈래" 대신 "KG 구축", "검색엔진 인덱싱"을 씀. "검색 인덱싱"은 "검색엔진 인덱싱"으로 바꿈. "(하위)"는 "(서브)"로 바꿈
- 남은 정리(나중에): 키워드 분석과 검색 엔진에 쓰기 장표는 검색엔진 인덱싱 단계를 ①②③으로 적고 있음.
  이 장표와 맞추려면 S1, S2, S3으로 바꿔야 함

## 사람 검토 3차 반영(2026-10-19)

- 사용자 지적: 증분 색인도 병렬로 구축할 수 있지 않은가, 그리고 지금 구성이 "계산은 병렬, 반영은 순서대로"를 지키는가
  → 2차 구성은 서브 워크플로우가 계산과 쓰기를 한 덩어리로 끝까지 해서, 증분 색인의 쓰기 순서를 보장하지 못했음(약속 카드에 글로만 적음)
- 고친 구조
  - 서브 워크플로우를 준비(쓰지 않고 계산만, 결과 보관), 반영(Neo4j 또는 검색엔진에 씀), 정리(KG 옛 청크와 고아 엔티티 지움)로
    나누고 진입점을 따로 둠. KG 구축에 K7(정리)을 새로 둠
  - 오케스트레이터가 모드에 따라 호출 순서를 정함: 전체 재색인은 통째로 병렬, 증분 색인은 준비만 병렬이고 반영과 정리는 순서대로
  - 증분 색인의 K5 병합은 그 문서와 관련된 엔티티로 범위를 좁힘
- 고치기 전 덱은 `워크플로우구성.before-phases.pptx`
