## 장표 1. 오케스트레이터 ① 세대 ID 발급과 ② 공통 단계

- 제목: 오케스트레이터 ① 세대 ID 발급, ② 공통 단계
- 리드문: 실행마다 세대 ID를 정하고, 원문을 개인정보 처리된 청크 파일 하나로 만들어 두 서브 워크플로우에 넘김

**도형 구성**

1. 왼쪽(x 0.557, w 6.9): 네이비 헤더 「① 세대 ID 발급과 사전 검사」
   - 세대 ID 모양: 세 칸 `gen-`(접두어) | `birthfix-20261018b`(실행 이름) | `-efeb65bd`(실행 이름 해시 8자리)
   - 카드 두 개: 같은 실행 이름이면 같은 세대 ID(중단돼도 같은 세대로 재개) / 두 서브 워크플로우의 공통 열쇠(card_chunks-gen-X, Neo4j gen-X)
   - 사전 검사 흐름: [원천 지문 수집(파일 SHA-256)] → [활성 세대 기록과 비교(원천, 정책, 프로필, 토큰화, 임베딩)]
     → [모두 같음: 실행 종료, 할 일 없음](다크) 또는 [하나라도 다름: ② 공통 단계로](블루). 캡션: 전체 재색인 요청이면 사전 검사를 건너뜀
2. 오른쪽(x 7.757, w 7.7): 블루 헤더 「② 공통 단계: 원문 → 청크 파일」
   - 흐름 칩 4개: 원천 문서(약관과 혜택 PDF, 상담 TXT) → 로드와 가명처리(회원 정보 → 가명 키) → 정제(표기 정리, 메타데이터 검증)
     → 청킹(문서별 분할 정책, 카드 경계, 머리말)
   - 결과 막대(네이비): prepared-chunks.json, 개인정보 처리된 청크만 저장 + SHA-256 → K1, S1에 넘김
   - 규칙 카드 3개: 원문은 남기지 않음 / 바뀌지 않은 문서는 재사용 / 실행 중 원천이 바뀌면 중단
   - chunk_id 규칙: `D1_27223010abe31291`(문서 키) | `_112f1e4abea05436`(본문 해시 16자리) | `_0000`(같은 본문 반복 번호)
     → 본문이 같으면 ID도 같아 두 서브 워크플로우가 같은 ID를 씀
   - 청크 한 건 필드 한 줄

**발표자 노트**

오케스트레이터의 첫 단계는 이번 실행의 세대 ID를 정하는 일입니다. 세대 ID는 실행 이름과 그 해시로 만들어서, 실행이 중간에 멈춰도
같은 이름으로 다시 돌리면 같은 세대로 이어서 만듭니다. 이 세대 ID가 검색엔진 인덱스 이름과 Neo4j 세대 값의 공통 열쇠가 됩니다.
본격적으로 일하기 전에 원천 파일의 지문을 모아 활성 세대 기록과 비교합니다. 원천, 처리 정책, 문서 프로필, 토큰화, 임베딩 설정이
모두 같으면 할 일이 없으므로 여기서 끝냅니다.
두 번째 단계는 원문을 청크 파일 하나로 만드는 일입니다. 원문을 읽으면서 회원 정보를 가명 키로 바꾸고, 정제하고, 문서별 규칙으로
청크를 나눕니다. 원문은 메모리에서만 다루고 개인정보 처리가 끝난 청크만 저장합니다. 바뀌지 않은 문서는 이전 세대의 처리된 청크를
그대로 씁니다. 청크 ID는 문서 키와 본문 해시로 만들어서 본문이 같으면 ID도 같습니다. 이 파일 하나를 두 서브 워크플로우가 함께 읽기
때문에 KG와 검색엔진 인덱스의 chunk_id가 어긋나지 않습니다.
