## 장표 1. K6이 필요한 이유: 그래프로 들어가는 두 입구

- 제목: KG 구축 K6이 필요한 이유
- 리드문: 검색엔진 인덱스(청크 입구)와 노드 설명 벡터 인덱스(엔티티 입구)는 놓치는 질문이 서로 달라, 함께 쓰면 정답에 가장 많이 닿음

**도형 구성**

1. 위 좌우 카드 2개(입구별):
   - 청크 입구 (검색엔진 인덱스): 흐름 「질문 → 검색용 청크 → 추출 단위 노드 → 그 청크의 엔티티 전부」.
     강점: 긴 본문이라 맥락이 있어 표현이 달라도 맞음 / 약점: 후보가 많음(청크 1개에 평균 11개), 말투가 비슷한 다른 문서 청크가 위로 옴
   - 엔티티 입구 (노드 설명 벡터 인덱스, K6): 흐름 「질문 → 엔티티 설명 벡터 → 그 엔티티」.
     강점: 사실 하나를 바로 짚음(후보 5개) / 약점: 설명 글이 짧아 맥락이 빠지면 놓침
2. 왼쪽 아래 막대 4개 「같은 질문 20개로 비교 (v0 표본: 청크 9개, 엔티티 82개)」: 청크 1개 11, 청크 2개 17, 엔티티 5개 15,
   함께(청크 2개 + 엔티티 5개) 19. 막대 옆에 평균 후보 수(함께는 「후보 25 이하」)
3. 오른쪽 아래 「서로 메운 예」 카드 2개(T02, C04)와 결론 카드(네이비): 청크 입구를 기본으로, 엔티티 입구를 보조로 → 엔티티 입구를 만드는 단계가 K6

**발표자 노트**

K6을 설명하기 전에 왜 필요한지부터 보겠습니다. 질문으로 그래프에 들어가는 길은 두 가지입니다. 하나는 검색엔진이 찾은 청크에서
그 청크의 엔티티로 들어가는 청크 입구이고, 다른 하나는 질문과 뜻이 가까운 엔티티를 바로 찾는 엔티티 입구입니다. K6은 이
엔티티 입구를 만드는 단계입니다.
같은 질문 20개로 비교해 보니 둘은 놓치는 질문이 달랐습니다. 할부 철회 기한을 구어체로 물으면 청크 입구는 말투가 비슷한 상담
청크를 먼저 가져와 놓쳤지만, 엔티티 입구는 철회 기한 노드를 1위로 찾았습니다. 반대로 영수증이 없는 고객 질문은 정답 노드의
설명 글에 영수증이란 말이 없어 엔티티 입구가 놓쳤고, 청크 입구는 맥락이 담긴 상담 청크로 찾았습니다.
그래서 둘을 함께 쓰면 20개 중 19개에 닿아 가장 많았습니다. 청크 입구를 기본으로 하고 엔티티 입구로 보조하는 것을 권합니다.
다만 표본이 작은 실험이라 전체 데이터에서는 숫자가 달라질 수 있습니다.

## 장표 2. K6 노드 설명 임베딩: 무엇을 어떻게 임베딩하나

- 제목: KG 구축 K6 노드 설명 임베딩
- 리드문: 엔티티마다 「라벨: 속성=값」 설명 글을 만들어 임베딩하고, 벡터 인덱스로 질문과 뜻이 가까운 노드를 찾게 함

**도형 구성**

1. 위 흐름 4칸(화살표):
   - ① 엔티티 노드: Proposal (content, decision, generation, run_id)
   - ② 설명 글 만들기: 「Proposal: content=그러면 주문 내역 화면으로 …, decision=수용」
   - ③ KURE-v2 임베딩: 768차원. 검색엔진 S1과 같은 모델
   - ④ 노드에 저장과 벡터 인덱스: embedding 속성, kg_entity_embedding (__Entity__, 코사인)
2. 왼쪽 아래 「실제 설명 글 (활성 세대)」 3줄: TermsDocument, Clause, Requirement
3. 오른쪽 아래 「어디에 쓰나: 질문으로 노드 찾기 (조회 예시)」: 질문 상자 → 찾은 노드 2개(점수) → 「찾은 노드에서 관계를 따라 그래프 탐색 시작」
4. 아래 규칙 카드 3개:
   - 엔티티만 임베딩: 추출 단위 노드는 빼고. 본문 검색은 검색엔진이 맡음
   - 관리용 속성은 뺌: generation, run_id는 설명 글에 넣지 않음. 속성은 이름순
   - 임베딩 없는 노드만: K5로 합친 뒤에 함. 증분 색인 때는 새 노드만

**발표자 노트**

K6은 K5까지 마친 엔티티에 뜻을 담은 벡터를 붙이는 단계입니다. 노드에는 문장이 따로 없기 때문에, 라벨과 속성을 「라벨: 속성=값」
꼴의 설명 글로 이어 붙여 만듭니다. 세대나 실행 표시 같은 관리용 속성은 뜻과 상관이 없어서 뺍니다. 이 글을 검색엔진과 같은
KURE-v2 모델로 임베딩해 노드에 저장하고, 엔티티 전체에 벡터 인덱스를 만듭니다.
이렇게 해 두면 질문 하나로 뜻이 가까운 노드를 바로 찾을 수 있습니다. 「할부 수수료는 언제 알려 주나요?」로 찾으면 할부 조항의
충족 조건 노드가 가장 먼저 나옵니다. 찾은 노드에서 관계를 따라가면 그래프 탐색이 시작됩니다.
추출 단위 노드는 임베딩하지 않습니다. 본문 검색은 검색엔진이 이미 맡고 있기 때문입니다. 그리고 임베딩은 합치기가 끝난 뒤에
하므로, 합쳐질 노드를 여러 번 임베딩하지 않습니다.

## 장표 3. K6 노드 설명 임베딩 코드와 결과

- 오른쪽 가운데 표 「벡터 인덱스 (SHOW VECTOR INDEXES)」: 이름, 라벨, 속성, 차원, 유사도, 상태

한 번에 임베딩해 노드마다 embedding 속성으로 저장합니다. 마지막으로 벡터 인덱스를 만드는데, 이미 있으면 그대로 둡니다.
