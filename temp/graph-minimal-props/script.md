## 슬라이드 1 — 그래프에는 ID와 최소 속성만 넣음

- 리드문: 그래프는 노드 탐색과 제목만 맡고, 비중·금액·원문은 원래 저장소에서 ID로 가져옴

### 왼쪽 — 최소 속성이란? (네이비 헤더 바)

- 정의(틴트 상자): 그래프 안에서 ① 노드 탐색과 ② 탐색된 노드의 제목에 꼭 필요한 정보만 넣은 것
- 비유(흰 상자): 지하철 노선도 — 역 이름·노선·환승 표시만 있어도 길은 찾음.  
  시간표·역 안 상가는 역(원래 저장소)에 가서 봄
- 넣을지 정하는 질문 3가지

| # | 질문 | 우리 예 | 판정 |
|---|------|---------|------|
| 1 | 노드 탐색에 쓰나? | 업종명=식비, 관계(대상·제공) | 넣음 |
| 2 | 탐색된 노드의 제목인가? | 상품명, 혜택명 | 넣음 |
| 3 | 자주 바뀌거나 크거나 민감한가? | 업종 비중, 카드 상태, 상담 원문 | 빼고 ID만 |

### 오른쪽 위 — 우리 시스템 예시: 무엇을 그래프에 넣나 (표)

| 노드 | 그래프에 넣는 것 (ID + 최소 속성) | 원래 자리에 두는 것 |
|------|----------------------------------|--------------------|
| 회원 | 회원 가명 ID, 고객군 | 가입일·연령대·연체 (정형 DB) |
| 카드 | 카드 ID | 카드 상태·발급일 (정형 DB) |
| 상품 | 상품 ID, 상품명 | 연회비 (정형 DB) |
| 혜택 | 혜택 ID, 혜택명 | 혜택률·한도·조건 문구 (벡터 DB) |
| 업종 | 업종명 (식비·주유 등 8개) | 없음 |
| 거래 | 넣지 않음 — 업종 비중은 SQL로 계산 | 거래 건별 금액 (정형 DB) |
| 상담 | 상담 ID, 상담일, 불만 주제, 조각 ID | 발언 원문 (벡터 DB) |

### 오른쪽 아래 — 질문 하나가 처리되는 순서 (4단계 도형)

- 예시 질문: "M-6001 회원이 많이 쓰는 업종에 혜택을 주는 카드는?"

| 단계 | 저장소 | 하는 일 | 넘기는 것 |
|------|--------|---------|-----------|
| ① 출발 노드 정하기 | 정형 DB | 업종 비중 계산 | 식비 |
| ② 노드 탐색 | 그래프 | 식비 → 혜택 → 상품 | ID·제목 |
| ③ 정확한 값 | 정형 DB | 상품 ID로 연회비 조회 | 연회비 |
| ④ 근거 문단 | 벡터 DB | 혜택 ID로 문단 찾기 | 혜택 문단 |

- 콜아웃: ID 하나로 세 저장소를 이음 → 값은 원래 자리에 한 번만 두고, 그래프는 노드 탐색과 제목만 맡음

### 발표자 노트

- ID만 넣으면 노드 하나를 지날 때마다 정형 DB를 다시 불러야 해서 여러 단계 탐색이 느려짐  
  → 노드 탐색에 쓰는 속성(업종명)과 탐색된 노드의 제목(상품명·혜택명)은 복제
- 전부 넣으면 동기화 부담과 민감정보 노출 범위가 커짐 → 자주 바뀌고 크고 민감한 값은 제외
- 업종 비중은 매달 바뀌는 집계값이라 SQL로 계산해 출발 노드만 정함.  
  회원-업종 관계는 "비슷한 회원 찾기" 질문을 쓸 때만 월 1회 배치로 만듦
- 업종과 잇는 대상은 발급 카드가 아니라 상품(64종)이며, 사이에 혜택 노드를 둠
