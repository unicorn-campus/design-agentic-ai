# 이탈 위험 방지 사례로 배우는 이벤트 모델링

고객이 상담사에게 “연회비가 부담돼서 해지하려고요”라고 말합니다.  
상담사는 고객의 이용 현황과 관련 자료를 살펴보고, 고객에게 제안할 내용을 준비해야 합니다.  
이 과정을 AI가 돕는다면 어떤 화면이 필요하고, 어떤 작업을 거쳐 어떤 기록을 남겨야 할까요?

이 가이드는 그 질문에 하나씩 답하면서 이벤트 모델을 만드는 과정을 안내합니다.  
처음에는 기록할 사실을 모으고, 그다음 시간 순서와 화면을 붙입니다.  
이어서 작업 요청과 데이터를 연결하면, 처음의 메모가 조금씩 구체적인 설계로 발전합니다.

예시는 Event Modeling의 공식 7단계를 따릅니다. 시작 전에 범위를 정하고, 마지막에는 빠진 연결을 점검합니다.  
그림에 나오는 화면과 데이터는 설명을 위한 설계 예시입니다. 실제 시스템의 실행 화면은 아닙니다.

## 그림을 읽기 전에

처음부터 모든 용어를 외울 필요는 없습니다. 아래 세 가지만 구분하고 시작하면 됩니다.

- **레이어**는 같은 종류의 요소를 모아 놓는 영역입니다. 화면과 자동화, 커맨드와 읽기 모델, 이벤트를 구분합니다.  
- **스웜레인**은 업무영역을 구분합니다. 이 사례에서는 `상담 지원`과 `지식 관리`를 사용합니다.  
- **담당자 유형**은 누가 일을 하는지 나타냅니다. 규칙 기반 코드, 예측형 AI, 생성형 AI, Human의 네 가지로 표시합니다.

예를 들어 상담사가 초안을 확인하는 화면과 AI가 초안을 작성하는 작업은 모두 `상담 지원`에 속합니다.  
업무영역은 같지만, 사람이 확인하는 일은 Human이 맡고 초안을 만드는 일에는 생성형 AI와 코드가 참여합니다.  
이처럼 **어느 업무에 속하는지와 누가 수행하는지를 나누어 생각하면** 그림을 읽기 쉽습니다.

그림의 색도 구분을 돕습니다. 작업을 요청하는 커맨드는 파란색, 정보를 구성하는 읽기 모델은 초록색,  
일어난 사실을 남기는 이벤트는 주황색으로 표시합니다. 사양은 이 요소들이 어떻게 동작해야 하는지 설명하는 조건입니다.  
초반에는 필요한 카드부터 놓고, 레이어와 스웜레인은 모델이 구체화되는 과정에서 정리합니다.

## 준비. 이번에 어디까지 다룰지 정합니다

먼저 한 번의 상담을 떠올려 봅니다. 고객이 해지 의사를 밝히면 상담사가 문의를 접수하고,  
시스템은 고객 현황과 관련 근거를 모아 제안 초안을 만듭니다. 상담사가 그 초안을 확인하는 곳까지를 기본 범위로 잡겠습니다.

고객에게 실제로 제안하고 반응을 기록하는 과정은 그다음에 이어질 일입니다.  
이번에는 확장할 수 있는 구간으로 표시해 두고, 우선 초안 확인까지의 흐름에 집중합니다.

![기본 상담 흐름, 별도 색인 배치, 확장 범위를 나눈 그림](./images/event-modeling-guide/00-scope.png)

검색에 사용할 자료를 미리 준비하는 색인 배치도 필요합니다.  
다만 고객이 문의할 때마다 자료 전체를 다시 색인하지는 않습니다.  
색인 배치는 별도로 실행하고, 상담 중에는 이미 준비된 색인을 사용하도록 그립니다.

현재 예측형 AI는 연결되어 있지 않습니다. 따라서 이탈 확률이나 위험 등급을 만들어 넣지 않고,  
화면의 예측값에는 `확인 필요`라고 표시하겠습니다.

이후 예시는 같은 상담을 계속 따라갑니다. 상담 ID는 `S-104`, 가명 회원 ID는 `M-204`, 상담사는 `A-07`입니다.  
초안은 `DRAFT-01/v1`, 선정한 근거는 `R-01`로 부르겠습니다.  
금액과 문서 내용은 모두 가상 값이며, 실습의 D3 상담 이력도 합성 자료입니다.  
화면·반환 이력·확인 기록·CRM 연결은 이번에 설계하는 내용으로, 실제 구현 여부는 별도 확인이 필요합니다.

## 1단계. 나중에 기억해야 할 사실을 모읍니다

상담이 끝난 뒤 기록을 다시 본다고 생각해 보겠습니다.  
어떤 문의가 들어왔는지, 어떤 고객 현황을 참고했는지, 어떤 초안을 작성했는지 알아볼 수 있어야 합니다.  
이렇게 **나중에 추적할 필요가 있는 사실**을 이벤트 후보로 적습니다.

카드에는 “상담이 시작되었음”, “근거가 선정되었음”처럼 이미 일어난 일로 표현합니다.  
지금은 순서를 맞추기보다, 기록할 만한 사실을 빠뜨리지 않고 찾는 데 집중합니다.

![기록할 이벤트를 선택·보류·제외로 나누어 모은 카드](./images/event-modeling-guide/01-events.png)

여기에는 초안을 작성한 사실뿐 아니라, 저장된 초안을 반환한 사실도 넣었습니다.  
상담사가 어떤 버전의 초안을 제공받았는지 추적하려는 목적입니다.  
같은 초안을 다시 조회하더라도 그 조회에 대한 반환 이력은 새로 남길 수 있습니다.  
캐시나 체크포인트에서 읽었는지보다, **그 반환 사실을 업무에서 기억할 필요가 있는지**가 판단 기준입니다.

초안을 반환한 것과 상담사가 확인한 것은 구분합니다.  
서버가 데이터를 보냈다고 해서 사람이 읽었다고 볼 수는 없으므로, 확인 버튼을 누른 기록을 별도로 남깁니다.  
그림에서는 반환을 `E-8`, 명시적 확인 입력의 기록을 `E-9`로 표시했습니다.

반대로 현재 일어날 수 없는 사실은 제외합니다. 예측 모델이 없으므로 “위험도가 산출되었음”은 넣지 않습니다.  
화면 새로고침처럼 기록 목적이 아직 분명하지 않은 후보는 잠시 보류해도 됩니다.

## 2단계. 모은 이벤트로 한 번의 상담 이야기를 만듭니다

이제 카드를 실제로 일어날 순서대로 놓습니다.  
상담이 시작되고, 고객 현황을 확보한 뒤, 근거를 선정하고 초안을 작성합니다.  
이후 상담사에게 초안을 반환하고, 상담사가 확인하면 그 사실을 남깁니다.

카드 사이에 선을 그으면서 앞에서 무엇이 준비되어야 하는지도 살펴봅니다.  
예를 들어 근거를 선정하려면 고객의 문의와 현황뿐 아니라, 검색할 수 있는 색인도 있어야 합니다.

![이벤트의 시간 순서와 별도 색인 배치, 초안 재조회를 표시한 그림](./images/event-modeling-guide/02-timeline.png)

그림 위쪽의 색인 발행은 상담과 별도 흐름으로 놓았습니다.  
상담에서는 이미 발행된 색인을 참조한다는 관계만 연결하면 됩니다.

초안을 다시 조회하는 경우도 생각해 봅니다.  
저장된 `DRAFT-01/v1`을 다시 반환했다면 반환 이벤트는 추가되지만, 초안 작성 이벤트가 다시 생기지는 않습니다.  
그림의 점선은 이 반복 조회를 나타냅니다.

아래쪽의 제안 확정·실제 안내·반응 기록은 이후에 확장할 흐름입니다.  
이벤트 ID는 카드를 구분하기 위한 이름이므로 번호가 발생 순서와 같을 필요는 없습니다.  
이 예시에서는 나중에 추가한 `E-8`, `E-9`가 확장 구간의 `E-5`보다 먼저 나타납니다.

## 3단계. 상담사가 사용할 화면을 먼저 그려 봅니다

이제 상담사의 입장에서 화면을 생각해 봅니다.  
문의를 접수할 때 무엇을 입력해야 할까요? 고객 현황을 볼 때는 어떤 정보가 필요할까요?  
제안 초안을 검토하려면 결론만으로 충분할지, 근거와 출처도 함께 보여야 할지 살펴봅니다.

아래 그림은 그 질문에 답하면서 만든 간단한 화면 시안입니다.  
정교한 디자인보다 입력칸, 표시할 값, 버튼을 구체적으로 적는 것이 중요합니다.

![문의 접수, 고객 현황, 초안 검토 화면과 자동화의 시작 조건](./images/event-modeling-guide/03-storyboard.png)

문의 접수 화면에서는 회원과 문의 내용을 입력하고 상담을 시작합니다.  
고객 현황 화면에서는 사용액과 함께 기준월·기준일을 보여 줍니다.  
초안 검토 화면 `U-3`에는 결론, 근거와 출처, 예측값, 주의사항, 확인 버튼을 배치했습니다.

이 단계의 관심은 **“상담사에게 무엇을 보여 줄까?”**입니다.  
아직 각 값을 어디서 가져와 어떻게 구성할지 모두 정할 필요는 없습니다.  
그 연결은 5단계에서 읽기 모델을 정의하면서 구체화합니다. 그때 사용하는 U-3도 바로 이 화면입니다.

사람이 버튼을 누르지 않아도 진행할 작업은 자동화로 표시합니다.  
예를 들어 상담이 시작되었는데 현황이 없으면 현황 조회를 시작하고,  
근거가 준비되었는데 초안이 없으면 초안 작성을 시작하도록 조건을 적습니다.

## 4단계. 화면과 자동화가 어떤 작업을 요청할지 정합니다

화면을 그렸다면 이제 버튼을 누르거나 자동화 조건이 충족되었을 때 무엇을 요청할지 정합니다.  
그 요청을 나타내는 카드가 **커맨드**입니다.

문의 접수 화면의 시작 버튼은 “상담을 시작하라”라는 요청으로 연결합니다.  
초안 작성 자동화는 “초안을 작성하라”라는 요청을 보냅니다.  
각 요청에는 처리에 필요한 정보를 적고, 성공했을 때 남길 이벤트를 연결합니다.

![상담 시작, 초안 작성, 확인 기록의 요청과 결과를 연결한 그림](./images/event-modeling-guide/04-commands.png)

가운데의 초안 작성 요청을 보면 고객 현황, 선정 근거 `R-01`, 예측 모델의 미연결 상태가 입력됩니다.  
생성형 AI는 이 자료를 바탕으로 문장을 만들고, 규칙 기반 코드는 결과를 검증하고 채택한 초안을 저장합니다.  
이 일이 끝나면 “초안이 작성되었음”이라는 이벤트를 남깁니다.

여기서 요청자와 처리 담당자가 항상 같지는 않습니다.  
상담사가 확인 버튼을 누르는 것은 Human의 행동이지만, 그 입력을 검증하고 저장하는 일은 코드가 맡습니다.  
그림에 담당자 유형을 표시하는 이유도 이 역할을 구분하기 위해서입니다.

**요청에서 결과까지 하나의 동작을 설명하는 카드와 연결을 슬라이스라고 부릅니다.**  
그림에서는 상담 시작, 초안 작성, 확인 기록이 각각 하나의 변경 슬라이스입니다.

## 5단계. 읽기 모델을 정의하고, 구상한 화면에 데이터를 연결합니다

3단계에서 “무엇을 보여 줄까?”를 정했다면, 이제는 **“그 값을 어디에서 가져와 어떻게 구성할까?”**를 정합니다.  
새 화면을 만드는 것이 아니라, 앞에서 그린 U-3 초안 검토 화면을 다시 펼쳐 놓고 각 항목의 출처를 찾는 과정입니다.

예를 들어 초안 화면에 필요한 정보는 다음과 같이 가져올 수 있습니다.

- 결론과 주의사항은 저장된 초안에서 가져옵니다.  
- 근거와 출처는 초안에 붙어 있는 근거 ID로 선정 기록을 찾아 연결합니다.  
- 예측값은 미연결 상태를 확인해 `확인 필요`라는 문구로 구성합니다.

이처럼 화면에 필요한 정보를 모아 반환하는 구조가 **읽기 모델**입니다.  
이 예시에서는 `V-3 제안 초안 조회`가 그 역할을 맡습니다.

![저장된 초안과 근거를 읽기 모델로 구성해 같은 U-3 화면에 연결한 그림](./images/event-modeling-guide/05-read-models.png)

읽기 모델을 정의하다 보면 화면에서 빠진 부분을 발견할 수 있습니다.  
사용액만으로는 어느 달의 값인지 알 수 없고, 초안 내용만으로는 어떤 버전인지 구분하기 어렵습니다.  
이런 경우 기준월이나 초안 버전을 보완하고, 자료가 없을 때 어떤 문구를 보여 줄지도 정합니다.  
이미 3단계에서 필요한 항목을 갖췄다면 화면은 유지하고 데이터 연결만 확정해도 됩니다.

즉, **3단계에서 화면을 구상하고, 5단계에서 읽기 모델을 정의하면서 같은 화면을 보완합니다.**  
그림에 같은 화면이 다시 나오는 이유는 앞에서 만든 결과에 데이터의 출처를 연결하기 때문입니다.

그림 아래쪽은 초안 데이터와 별도로 남기는 이력입니다.  
서버의 응답 전송 완료를 확인하면 반환 이력 요청 `C-5`를 통해 `E-8`을 남깁니다.  
그 후 상담사가 확인 버튼을 누르면 `C-6`을 통해 `E-9`를 남깁니다.

저장된 초안을 읽는 일, 서버가 데이터를 반환하는 일, 사람이 확인 의사를 남기는 일은 서로 다릅니다.  
따라서 반환 기록만 보고 확인까지 끝났다고 표시하지는 않습니다.  
반환 이력의 저장 위치나 전송 완료를 확인하는 구체적인 방법은 실제 구현 단계에서 정합니다.

## 6단계. 관련된 카드를 업무영역별로 묶습니다

지금까지는 필요한 사실과 작업을 찾고 연결하는 데 집중했습니다.  
이제 모델을 조금 떨어져서 보면서, 어떤 카드들이 같은 업무영역에 속하는지 정리합니다.

원문을 준비하고 색인을 발행하는 일은 `지식 관리`로 묶을 수 있습니다.  
고객 현황을 조회하고 근거를 선정해 초안을 만드는 일은 `상담 지원`에 속합니다.  
이렇게 업무영역을 나누어 배치한 영역이 스웜레인입니다.

![대표 카드를 지식 관리와 상담 지원 스웜레인에 배치한 모델](./images/event-modeling-guide/06-swimlanes.png)

그림에서는 레이어마다 지식 관리와 상담 지원을 구분했습니다.  
위쪽에는 화면과 자동화, 가운데에는 커맨드와 읽기 모델, 아래쪽에는 이벤트가 놓입니다.  
각 카드가 어떤 종류인지는 레이어로, 어느 업무에 속하는지는 스웜레인으로 읽으면 됩니다.

상담 지원 안에는 Human이 사용하는 화면도 있고 생성형 AI와 코드가 함께 처리하는 작업도 있습니다.  
담당자 유형이 달라졌다고 업무영역까지 나눌 필요는 없습니다.  
마찬가지로 DB나 LLM API를 호출한다는 이유만으로 각각 별도 스웜레인을 만들지는 않습니다.

이 그림은 배치를 살펴보기 위해 대표 카드만 모은 것입니다.  
초안 반환과 확인 기록은 앞 단계에서 정의한 연결을 그대로 이어서 배치할 수 있습니다.

## 7단계. 예시를 넣어 기대하는 동작을 설명합니다

카드와 연결선만으로는 세부 동작까지 모두 설명하기 어렵습니다.  
같은 요청이 두 번 들어오면 어떻게 할지, 자료가 없을 때 무엇을 반환할지 같은 조건을 더 정해야 합니다.  
이런 내용을 구체적인 예시로 적은 것이 **사양**입니다.

커맨드에는 “어떤 상황에서(Given), 무엇을 요청하면(When), 어떤 결과가 나와야 하는지(Then)”를 적습니다.  
읽기 모델은 이미 있는 정보를 보여 주므로 Given과 Then만으로 설명할 수도 있습니다.  
사양 하나는 커맨드 또는 읽기 모델 하나에 연결합니다.

![초안 작성, 반환 기록 재시도, 확인 여부 조회에 붙인 사양 예시](./images/event-modeling-guide/07-specifications.png)

왼쪽은 초안 작성이 성공하는 경우입니다.  
고객 현황과 근거가 준비되어 있으면 초안을 저장하되, 연결되지 않은 예측 모델의 수치를 만들지는 않습니다.

가운데는 반환 이력 기록을 재시도하는 경우입니다.  
요청 `Q-301`의 반환 기록이 이미 있다면, 같은 기록 요청을 다시 처리해도 이벤트는 한 건으로 유지해야 합니다.  
기존 초안 내용도 그대로이므로 초안 작성 이벤트를 추가하지 않습니다.

오른쪽은 반환 기록은 있지만 확인 기록은 없는 경우입니다.  
읽기 모델은 이 상태를 그대로 보여 주어야 합니다. 사람이 확인했다고 추정해서는 안 됩니다.

이처럼 성공뿐 아니라 재시도와 예외도 적어 두면 구현할 때 판단할 기준이 생깁니다.  
응답 전송이 실패했을 때 반환 완료 이벤트를 남기지 않는 조건이나,  
근거를 찾지 못했을 때 초안 작성을 멈추는 조건도 같은 방법으로 추가할 수 있습니다.

## 마무리. 화면의 값이 어디에서 왔는지 되짚어 봅니다

마지막에는 화면에서 출발해 연결을 거꾸로 따라가 봅니다.  
상담사가 보는 결론, 근거, 출처가 어떤 읽기 모델을 거쳐 어떤 기록에서 왔는지 확인하는 것입니다.  
이 과정에서 연결되지 않는 값이 발견되면, 빠진 데이터나 아직 정하지 않은 규칙이 있다는 뜻입니다.

![화면의 근거, 예측 안내, 확인 여부를 원천 기록까지 거슬러 확인한 그림](./images/event-modeling-guide/08-completeness.png)

초안의 근거를 따라가면 선정 기록과 문서 출처에 도달해야 합니다.  
예측값의 `확인 필요`는 예측 결과가 아니라 모델 미연결 상태에서 나온 표시여야 합니다.  
확인 여부는 반환 기록이 아니라 상담사의 확인 입력을 근거로 판단해야 합니다.

여기까지 연결되면 무엇을 만들고 어떤 정보를 남겨야 할지 설명할 수 있는 모델이 갖춰집니다.  
다만 이것은 설계의 연결을 확인한 결과입니다.  
실제 서비스에 적용하려면 가상 데이터를 바꾸고, 저장 방식과 처리 규칙을 확정한 뒤 구현과 기능 시험을 진행해야 합니다.
