# 이탈 위험 방지 사례로 따라 하는 Event Modeling 작성 가이드

이 문서는 [기존 이탈 위험 방지 예시](./이탈위험방지-이벤트모델링.md)를 학습용 설계로 다시 그리는 순서임.  
공식 Event Modeling의 7단계를 뼈대로 삼고, 시작 전 범위 정리와 마지막 점검을 덧붙임.  
각 단계의 예시는 설계 연습 결과이며, 통합 서비스의 구현·동작 확인 결과가 아님.

## 먼저 알아둘 것

이 사례의 목표는 해지 문의를 받은 상담사가 고객 현황과 확인된 근거를 보고 제안 초안을 검토하는 것임.  
정형 조회·지식 검색 등 개별 실습 기능과, 이 문서의 전체 상담 흐름을 통합 실행하는 일은 별개임.  
기존 문서의 상담사 화면·제안 확정·고객 안내·CRM 기록·고객 반응 기록은 설계 가정임.  
예측 모델은 미연결이며, 이탈 확률이나 위험 등급을 산출하지 않음. 예측값 표기는 `확인 필요`임.  
실습의 D3 상담 이력은 합성 자료이며, 실제 고객 데이터가 아님.

| 말 | 뜻 | 이 문서의 예 |  
|---|---|---|  
| 사건·이벤트 | 이미 일어나서 기록하기로 한 업무 사실 | `상담이 시작되었음` |  
| 커맨드 | 상태를 바꾸려는 요청 | `상담을 시작하라` |  
| 읽기 모델·뷰 | 이미 있는 정보를 화면 목적에 맞게 읽어 만든 값 | `고객 현황 카드`용 현황 조회 |  
| 화면·자동화 | 사람 또는 자동 작업이 흐름을 시작하는 자리 | 상담사의 접수 화면, 색인 주기 실행 |  
| 층 | 요소의 종류를 구분하는 배치 영역 | 화면·자동화, 커맨드·읽기 모델, 이벤트 |  
| 스윔레인·줄 | 같은 층 안에서 역할 또는 책임을 구분한 가로줄 | `상담사`, `상담 세션` |  
| 업무 단계 | 시간 흐름에서 어느 일을 하는지 나타내는 구간 | 문의 접수, 현황 확인 |  
| 슬라이스 | 입력부터 결과까지 한 번에 검토할 수 있는 작은 연결 | 접수 화면 → 커맨드 → 상담 시작 사건 |  
| 사양 | 연결이 맞는지 예시 값으로 확인하는 조건 | Given·When·Then |

이 가이드에서는 **3개 배치 영역과 별도 사양**으로 그림을 읽음.  
상단에는 사람의 화면과 자동화를, 가운데에는 커맨드와 읽기 모델을, 하단에는 이벤트를 배치함.  
이는 이 사례를 쉽게 읽기 위한 작성 규칙이며, Event Modeling 전체의 고정된 층 수라는 뜻은 아님.  
하나의 업무 단계에 여러 슬라이스가 들어갈 수 있으며, 모든 단계에 모든 종류의 카드를 채울 필요는 없음.  
스윔레인은 카드가 놓인 **가로줄 전체**, `상담 세션`은 그 줄의 **이름**임.

## 준비. 한 장에 담을 이야기 정하기 — 이 가이드의 교육용 추가 단계

**목적:** 서로 다른 시점에 일어나는 일을 하나의 상담 절차로 오해하지 않도록 범위 확정.

**할 일**

1. 시작을 `고객의 해지 문의를 상담사가 접수함`으로, 끝을 `상담사가 초안을 검토함`으로 적기.  
2. 사전 준비인 `색인 배치`는 상담 흐름의 왼쪽에 별도 흐름으로 그리기.  
3. `제안 확정 → 고객 안내 → 반응 기록`은 확장 구간이자 설계 가정으로 표시하기.  
4. 현재 없는 기능을 적되, 연결된 것으로 그리지 않기. 이 사례에서는 예측 모델이 해당함.  
5. 각 카드에 `실습 근거`, `설계 제안`, `미확인` 중 해당 표시를 붙이기.

**이 예시의 작성 결과**

```text
사전 흐름: D1·D2·합성 D3 준비 → 색인 배치 → 사용 가능한 색인
상담 흐름: 문의 접수 → 현황 확인 → 근거 선정 → 초안 작성 → 상담사 검토
확장 흐름: 확정 → 실제 안내 → 반응 기록 〔모두 설계 가정〕
미연결: 예측 모델 → 위험 등급 없음 → 화면에는 '확인 필요'
```

**완료 기준:** 상담 중 실행되는 일과 사전 준비가 구분되고, 가정·미연결 항목에 표시가 있음.

## 1단계. 먼저 사건 후보 모으기 — 공식 1단계: Brain Storming

**목적:** 어떤 업무 사실을 기억해야 다음 일을 설명할 수 있는지 발굴.

**할 일**

1. 실제로 일어난 뒤 과거형으로 말할 수 있는 사실을 카드 하나에 하나씩 적기.  
2. `누가`, `어떤 상담에서`, `무엇을`, `언제` 알아야 하는지 카드 옆에 적기.  
3. 단순 화면 열기·조회 호출·API 응답은 일단 후보와 분리하기.  
4. 후보가 저장될지 불명확하면 `기록 여부 확인 필요`로 표시하기.

**이 예시의 작성 결과**

| 후보 | 판정 | 이유 |  
|---|---|---|  
| 상담이 시작되었음 | 사건 제안 | 새 상담 세션을 남기는 업무 사실 |  
| 고객 현황이 확보되었음 | 조건부 사건 제안 | 상담별 현황 스냅샷을 기록할 때만 사건 |  
| 근거가 선정되었음 | 조건부 사건 제안 | 채택한 출처를 상담 기록으로 남길 때만 사건 |  
| 제안 초안이 작성되었음 | 사건 제안 | 초안과 출처 연결을 보존할 때의 업무 사실 |  
| 고객 현황 카드가 열렸음 | 읽기 행위 | 화면 표시만으로 업무 상태 변경 없음 |  
| DB 응답이 반환되었음 | 기술 응답 | 업무 사실로 기록할지 확인되지 않음 |  
| LLM 응답이 반환되었음 | 기술 응답 | 검증·채택 전 응답이며 업무 사건과 다름 |  
| 위험도가 산출되었음 | 제외 | 예측 모델 미연결로 실제 산출 없음 |

`고객 현황이 확보되었음`과 `근거가 선정되었음`은 이 가이드가 제안하는 **기록 계약**임.  
이후 예시는 상담별 현황과 선정 근거를 기록하는 안을 선택해 진행함.  
실제 설계에서 저장하지 않기로 결정하면 해당 사건과 이를 전제로 한 사양을 함께 수정함.  
기존 문서에 적힌 `조회되었음`, `반환되었음`이 곧바로 저장된 사건이라는 뜻은 아님.

**완료 기준:** 사건 후보마다 저장할 업무 사실인지 판정되고, 미확인 후보가 확정 사실처럼 쓰이지 않음.

## 2단계. 사건을 시간순으로 놓기 — 공식 2단계: The Plot

**목적:** 사건의 앞뒤 관계로 상담 이야기의 뼈대 구성.

**할 일**

1. 상담 흐름의 사건을 왼쪽에서 오른쪽으로 놓기.  
2. 각 사건이 앞 사건의 무엇을 필요로 하는지 선으로 표시하기.  
3. 사전 색인 배치는 별도의 시간선에 놓고, 근거 검색이 이를 읽는 지점만 연결하기.  
4. 아직 사건인지 결정되지 않은 카드는 점선 또는 `제안` 꼬리표로 남기기.

**이 예시의 작성 결과**

```text
사전: [I-1 색인이 발행되었음: 기록 계약 제안]
                         ↓ 사용 가능한 근거의 조건
상담: [E-1 상담 시작] → [E-2 현황 확보] → [E-3 근거 선정] → [E-4 초안 작성]
      ※ 모두 학습용 기록 계약 제안이며, 예측값은 미연결 상태를 반영함.
확장: [E-5 제안 확정: 가정] → [E-6 제안 안내: 가정] → [E-7 반응 기록: 가정]
```

사전 색인이 준비되었다는 뜻은 **매 상담마다 색인을 다시 만든다**는 뜻이 아님.  
`E-2`, `E-3`, `E-4`는 각 결과를 상담 기록으로 저장한다는 설계 선택이 있을 때 사건으로 유지함.  
`E-5` 확정은 내부 결정, `E-6` 안내는 고객에게 실제 전달된 사실이므로 별도 사건으로 분리함.

**완료 기준:** 핵심 사건의 순서와 필요한 선행 조건이 보이고, 배치와 상담의 시간선이 분리됨.

## 3단계. 사람이 보는 화면 놓기 — 공식 3단계: The Story Board

**목적:** 입력과 출력이 사용자에게 어디서 보이는지 표시.

**할 일**

1. 사건 위쪽에 작은 화면 조각을 배치하고, 각 칸에 화면의 목적을 적기.  
2. 입력값과 출력값을 실제 필드 이름으로 적기. 그림을 정교하게 그릴 필요는 없음.  
3. 역할이 다르면 화면 영역에 역할별 줄을 만들기.  
4. 자동 처리에는 화면 대신 `톱니` 카드를 상단에 놓기.  
5. 현재 실습에 없는 화면은 `설계 가정`으로 표시하기.

**이 예시의 작성 결과**

| 상단 줄 | 화면·자동화 카드 | 보이는 값 또는 시작 조건 |  
|---|---|---|  
| 고객 | 해지 문의 발화 | `연회비가 부담돼서 해지하려고요` |  
| 상담사 | 문의 접수 화면〔가정〕 | 회원 가명 ID, 문의 내용, 시작 버튼 |  
| 상담사 | 고객 현황 카드〔가정〕 | 상품, 월별 사용액, 연체 지표, 기준일 |  
| 상담사 | 근거 목록〔가정〕 | 출처, 근거 문장, 적용 기준일 |  
| 상담사 | 초안 검토 화면〔가정〕 | 결론, 근거, 출처, 예측값, 주의사항 |  
| 자동화 | 색인 주기 실행 | 새 원문 준비, 직전 작업 완료 여부 |

**완료 기준:** 화면 필드마다 값의 출처를 물을 수 있고, 자동화가 사람 화면과 구별됨.

## 4단계. 상태를 바꾸는 입력 연결 — 공식 4단계: Identify Inputs

**목적:** 누가 어떤 의도로 상태를 바꾸는지 명확히 하기.

**할 일**

1. `사람 또는 자동화 → 커맨드 → 기록될 사건` 순서로 선을 긋기.  
2. 커맨드에 필요한 입력값과 성공 조건을 적기.  
3. 단순 조회에는 상태 변경 커맨드를 억지로 만들지 않기.  
4. 자동화는 조건을 읽고 같은 커맨드를 호출하는 행동 주체로 그리기.

**이 예시의 작성 결과 — 변경 슬라이스 1개**

```text
상담사 문의 접수 화면〔가정〕
  └─ 시작 버튼: 상담을 시작하라(session_id, member_pseudo_id, inquiry)
       └─ E-1 상담이 시작되었음(session_id, member_pseudo_id, inquiry, occurred_at)
```

예시 값은 `session_id=S-104`, `member_pseudo_id=M-204`, 문의는 `연회비가 부담돼서 해지하려고요`임.  
`member_pseudo_id`는 실제 고객을 바로 드러내지 않는 예시 식별자임. 이 데이터 구조는 설계 제안임.

**자동화 연결 예시**

```text
E-1 상담 시작 → 처리 대기 목록 읽기 모델 → 상담 현황 조회 자동화
            → 현황을 확보하라(S-104, M-204) → E-2 현황 확보〔기록 선택 시〕
```

자동화 조건은 `상담 시작됨 AND 현황 확보 기록 없음 AND 종료 상태 아님`으로 제안함.  
조회 실패 시 성공 사건을 만들지 않고, 제한된 재시도 뒤 실패 종료·담당자 확인 상태로 전환하는 규칙을 제안함.  
그래야 처리 대기 목록의 한 항목이 실패 때문에 영원히 남지 않음.  
실제 프로그램이 이 자동화를 수행한다는 뜻은 아님.

**다음 자동화도 같은 방식으로 연결**

| 읽기 모델이 보여 주는 할 일 | 실행할 커맨드 | 완료·종료 판단 |  
|---|---|---|  
| E-2 존재, 사용 가능한 색인 존재, 근거 처리 미완료 | 근거를 선정하라 | E-3 또는 근거 없음·실패 종료 |  
| E-2·E-3 존재, 예측 연결 상태 확인, 초안 미작성 | 초안을 작성하라 | E-4 또는 검증 실패 종료 |

할 일은 상담 ID와 작업 종류로 구분하고, 완료된 항목은 다시 처리하지 않는 규칙을 제안함.  
초안 작성 조건의 `예측 연결 상태 확인`은 예측 성공을 뜻하지 않음.  
이 사례에서는 미연결 설정을 확인해 예측 수치 없이 진행하고, 그 사유를 초안에 담음.

**완료 기준:** 각 변경 사건의 시작 주체와 커맨드가 연결되고, 조회와 상태 변경이 구별됨.

## 5단계. 보여 줄 값을 읽기 모델로 연결 — 공식 5단계: Identify Outputs

**목적:** 화면의 숫자·문구가 어디에서 왔는지 추적.

**할 일**

1. 각 화면 필드에서 거꾸로 필요한 읽기 모델과 원천 자료를 찾기.  
2. 기록된 사건을 쓰는지, 외부 시스템을 그때 조회하는지 구분하기.  
3. 자료가 없을 때의 표시 문구도 입력 데이터처럼 적기.  
4. 값을 읽기만 하는 슬라이스에는 새 커맨드나 사건을 넣지 않기.

**이 예시의 작성 결과 — 조회 슬라이스 1개**

```text
E-2 현황 확보〔상담별 스냅샷 기록을 선택한 경우〕
  └─ 고객 현황 읽기 모델(session_id=S-104)
       └─ 상담사 고객 현황 카드: 2026-08 사용액 420,000원 / 기준일 2026-08-31
```

현황을 저장하지 않는 선택에서는 `cardlab 조회 → 고객 현황 읽기 모델 → 현황 카드`로 그림.  
이 경우 `cardlab`의 조회 응답을 자동으로 이벤트 카드로 만들지 않음.  
두 방식 중 어느 것을 쓸지 확정 전이라면 `기록 여부 결정 필요`로 표시함.

| 화면 값 | 원천·읽기 모델 제안 | 확인할 점 |  
|---|---|---|  
| 보유 상품·사용액·연체 지표·기준일 | `cardlab` 현황 조회 또는 E-2 스냅샷 | 기준일과 자료 없음 구분 |  
| 근거 문장·출처 | 색인 검색 결과와 E-3 선정 기록 | 출처 원문 연결과 접근 권한 |  
| 결론·주의사항 | 검증 후 보존한 E-4 초안 | 근거 없는 문장 제외 |  
| 예측값 | 고정 표시 `확인 필요` | 예측 모델 미연결 표시 |

**카드에 적을 데이터 예시**

아래 값은 연결 연습을 위한 가상 값이며, DB 조회 결과나 실제 문서의 인용이 아님.  
카드의 이름만 적지 않고 이런 값을 넣어야 다음 카드가 필요한 정보를 받는지 확인 가능함.

| 사건 | 주요 데이터 예시 |  
|---|---|  
| E-1 상담 시작 | 상담 `S-104`, 가명 회원 `M-204`, 문의 `연회비 부담`, 발생 시각 |  
| E-2 현황 확보 | 상담 `S-104`, 기준월 `2026-08`, 사용액 `420000`, 기준일 `2026-08-31` |  
| E-2 현황 확보 | 연체 지표 `값 없음`, 현황 출처 `승인 거래 집계`, 예측 연결 상태 `미연결` |  
| E-3 근거 선정 | 상담 `S-104`, 근거 `R-01`, 가상 문서 `D2-DEMO`, 색인 버전 `IDX-DEMO-01` |  
| E-3 근거 선정 | 가상 근거 요지 `연회비 조건 확인 필요`, 원문 위치 `데모 2절`, 검증 결과 `통과` |  
| E-4 초안 작성 | 상담 `S-104`, 초안 `DRAFT-01`, 결론, 근거 ID `[R-01]`, 주의사항 |  
| E-4 초안 작성 | 예측 수치 `값 없음`, 예측 사유 `모델 미연결` |

`제안 초안` 읽기 모델은 E-4와 E-3을 연결해 결론·근거·출처·예측값·주의사항을 구성함.  
예를 들어 `연회비 조건 확인 필요`라는 결론 옆에 `R-01 / D2-DEMO 데모 2절`을 표시함.  
예측 안내 문구 `확인 필요`의 근거는 **미연결 상태**이며, 예측 수치의 근거가 생겼다는 뜻은 아님.  
실제 카드에는 위 가상 값 대신 확인한 데이터·문서 위치·검증 기준을 넣어야 함.

**완료 기준:** 화면의 모든 값에 원천이 있고, 없는 자료를 실제 산출값처럼 보이게 하지 않음.

## 6단계. 책임별 사건 줄 나누기 — 공식 6단계: Apply Conway's Law

**목적:** 사건을 책임질 영역을 나누고, 경계를 건너는 정보를 드러내기.

**할 일**

1. 지금까지 발굴한 사건을 먼저 보고, 독립적으로 관리할 책임 영역을 정하기.  
2. 사건 층에 책임 영역별 가로줄을 만들기. 화면 층에는 필요할 때 역할별 줄을 만들기.  
3. DB·API 호출 대상이라는 이유만으로 사건 줄을 추가하지 않기.  
4. 다른 시스템의 응답은 우리 업무 사실로 기록하기로 했는지 확인하기.

**이 예시의 작성 결과**

| 사건 줄 이름 | 넣는 사건 | 판단 근거 |  
|---|---|---|  
| 상담 세션 | E-1 ~ E-7 중 기록하기로 한 사건 | 상담 한 건의 업무 상태 책임 |  
| 지식 색인 | I-1 색인 발행〔기록 계약 제안〕 | 사전 배치의 버전·발행 상태 책임 |

`cardlab`, 지식 저장소, LLM API는 이 그림에서 데이터 또는 호출 경계로 표현 가능함.  
해당 시스템이 별도 사건을 발행하고 그 사건을 모델링해야 할 때만 사건 줄 추가를 검토함.  
예측 모델은 미연결이므로 사건 줄을 비워 두는 대신 `미연결` 주석으로 표현 가능함.  
CRM은 확장 가정이며, 통합 여부와 기록 계약을 정하기 전에는 사건 줄을 확정하지 않음.

아래 짧은 표의 `줄 이름`은 스윔레인의 **이름**이며, 그 이름을 단 가로줄이 스윔레인임.  
열은 업무 단계임. `E-2` 등이 사건 카드이고, 각 열 자체가 슬라이스 하나라는 뜻은 아님.

| 사건 줄 | 사전 배치 | 문의 접수 | 현황·근거 | 초안 | 확장 구간 |  
|---|---|---|---|---|---|  
| 지식 색인 | I-1〔제안〕 | | | | |  
| 상담 세션 | | E-1 | E-2·E-3〔제안〕 | E-4〔제안〕 | E-5·E-6·E-7〔가정〕 |

**완료 기준:** 각 사건이 책임질 줄에 놓이고, 구성요소 목록을 줄 목록으로 그대로 옮기지 않음.

## 7단계. 한 연결마다 사양 붙이기 — 공식 7단계: Elaborate Scenarios

**목적:** 기대하는 결과와 예외를 실제 값으로 검토할 수 있게 하기.

**할 일**

1. 사양 하나를 커맨드 하나 또는 읽기 모델 하나에 연결하기.  
2. 변경은 `Given → When → Then`, 읽기는 `Given → Then`으로 적기.  
3. 성공뿐 아니라 자료 없음·근거 없음·연결 실패도 적기.  
4. 사양의 결과가 사건인지 화면 표시인지 각각 명시하기.

**이 예시의 작성 결과 — 커맨드 사양**

| 대상 | Given | When | Then |  
|---|---|---|---|  
| 상담을 시작하라 | 인증된 `M-204`, 문의 내용 존재 | `S-104` 시작 요청 | E-1에 회원·문의·발생 시각 기록 |  
| 현황을 확보하라 | E-1 존재, E-2 없음 | 대기 목록의 `S-104` 처리 | 기준일 포함 현황 확보 후 E-2 기록 제안 |  
| 현황을 확보하라 | E-1 존재, `cardlab` 조회 실패 | 대기 목록의 `S-104` 처리 | E-2 미기록, 오류 표시·재시도 대상으로 남김 |  
| 근거를 선정하라 | 문의와 사용 가능한 색인 존재 | 근거 검증 수행 | 출처가 확인된 근거만 E-3에 기록 제안 |  
| 근거를 선정하라 | 검색 결과 0건 또는 검증 통과 0건 | 근거 검증 수행 | `근거 없음` 종료 상태 기록 제안, 자동화 할 일 종료 |  
| 초안을 작성하라 | E-2·E-3 존재, 예측 모델 미연결 | 초안 생성 요청 | 근거를 붙인 E-4 기록 제안, 예측값 `확인 필요` |  
| 초안을 작성하라 | 근거 없음 종료 상태 | 초안 생성 요청 | 근거 있는 유지 제안 생성 중단, 상담사 확인으로 전환 |

**이 예시의 작성 결과 — 읽기 모델 사양**

읽기 모델이 반환한 값과 상태를 화면에서 표시함. 화면 배치 검사는 별도로 수행 가능함.

| 대상 | Given | Then |  
|---|---|---|  
| 고객 현황 읽기 모델 | `S-104`, 2026-08 사용액 420,000원, 기준일 2026-08-31 | 월·금액·기준일을 반환 |  
| 고객 현황 읽기 모델 | 월별 사용액 자료 없음 | 값 없음 상태 반환. `0원`으로 대체 금지 |  
| 제안 초안 읽기 모델 | 출처가 확인된 E-3과 이를 참조한 E-4 존재 | 결론·근거·출처의 연결을 반환 |  
| 제안 초안 읽기 모델 | 예측 모델 미연결 | `확인 필요`와 미연결 사유 반환. 확률·등급 반환 금지 |

`근거 없음`도 작업의 결과임. 이 상태는 아직 구현된 사건이 아니라 이 가이드의 종료 계약 제안임.  
근거 선정 자동화는 `E-3 기록` 또는 `근거 없음 종료` 중 하나를 확인한 뒤 해당 할 일을 목록에서 제거함.  
현황 확보 실패도 정해진 재시도 횟수 뒤 `실패 종료·담당자 확인`으로 바뀌도록 제안함.  
이 종료 상태를 어떻게 저장할지는 실제 설계에서 결정할 항목임.

제안 확정과 실제 고객 안내를 그릴 때는 커맨드와 사건도 분리함.  
`제안을 확정하라 → E-5 제안이 확정되었음`은 상담사의 결정 기록임.  
`제안을 안내하라 → E-6 제안이 안내되었음`은 전달 확인 후의 기록 제안임.  
고객 반응도 안내 사실과 별개이며, 이 세 과정의 화면·CRM 연결은 모두 설계 가정임.

**완료 기준:** 사양마다 대상이 하나로 특정되고, 성공·실패·자료 없음·미연결의 결과가 구별됨.

## 마무리. 빠진 연결 확인 — 공식 설명의 Completeness Check 적용

다음은 이 가이드의 마지막 교육용 점검임. 사건과 화면 사이 정보의 출발점·도착점을 확인하는 방식은  
공식 Event Modeling의 완결성 점검에 근거함.

| 점검 질문 | 이 예시의 확인 결과 |  
|---|---|  
| 화면의 모든 숫자와 문구에 원천이 있는가? | 사용액은 기준일 있는 현황, 예측값은 `확인 필요` 고정 |  
| 커맨드가 성공할 때 기록할 사실이 명확한가? | E-1 ~ E-4의 기록 계약을 예시로 정의. 실제 적용 여부는 별도 결정 |  
| 단순 API 응답을 사건으로 오인하지 않았는가? | DB·LLM 응답은 채택·기록 결정 전 기술 응답 |  
| 자동화가 무엇을 보고 언제 실행하는가? | E-1 있고 E-2 없는 처리 대기 목록 제안 |  
| 사전 배치와 상담 실행을 구분했는가? | I-1은 별도 시간선, 상담은 사용 가능한 색인만 참조 |  
| 확정·안내·반응을 분리했는가? | E-5·E-6·E-7로 구분, 모두 확장 가정 |  
| 미연결 영역을 없는 그대로 표시했는가? | 위험 모델 미연결, 확률·등급 없음 |

새 사례에 재사용할 때는 다음 순서로 점검 가능함.

1. 시작·끝·사전 준비·미구현 기능 표시.  
2. 저장할 업무 사실만 사건 후보로 선택.  
3. 사건을 시간순으로 배치하고 화면을 위에 놓기.  
4. 변경은 `화면·자동화 → 커맨드 → 사건`, 조회는 `원천 → 읽기 모델 → 화면`으로 연결.  
5. 책임별 사건 줄을 만들고, 각 커맨드·읽기 모델에 구체 사양 연결.  
6. 화면의 모든 값과 예외 문구의 원천 확인.

기존 예시와 이 가이드의 주요 차이는 `네 층`을 절대 규칙으로 보지 않는 점, 자동화를 상단 행동 주체로  
놓는 점, API·DB 응답과 저장할 업무 사건을 구분하는 점, 확정과 실제 안내를 나누는 점임.  
이는 기존 설계의 구현 상태를 바꾸는 작업이 아니라, 사건 선정과 그리기 순서를 배우기 위한 재구성임.
