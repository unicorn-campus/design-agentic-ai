# 신용카드사 Help Desk 이벤트 스토밍

## 0. 범위

교육용으로 정확히 3개 워크플로우만 모델링함.  
이벤트는 과거형, 커맨드는 명령형, 정책은 실행 조건과 금지 조건이 보이도록 작성함.

| 워크플로우 ID | 유형 | 시작 조건 | 종료 결과 |
|---|---|---|---|
| WF-01 | 동기 | 고객 문의 제출 | 근거 포함 답변 또는 상담사 인계 |
| WF-02 | 배치 | 매일 02:00 | FAQ 후보 승인 대기 |
| WF-03 | 이벤트 | 상담 종료 이벤트 | CRM 요약 저장과 설문 발송 |

## 1. WF-01 동기 고객 문의

### 흐름

| 순서 | 액터·시스템 | 이벤트 스토밍 요소 | 데이터·정책 |
|---|---|---|---|
| 1 | 고객 | `[커맨드] 고객 문의 접수` | 문의 본문, 채널, 고객 세션 |
| 2 | 상담 오케스트레이션 | `[이벤트] 문의가 분류됨` | 유형, 위험 등급, 조회 범위 |
| 3 | 지식 검색 | `[이벤트] 승인된 답변 근거가 검색됨` | 문서 ID, 버전, 근거 구간 |
| 4 | 카드·거래 조회 API | `[이벤트] 고객 상태가 조회됨` | 인증 후 최소 필드 반환 |
| 5 | 상담 오케스트레이션 | `[이벤트] 답변 초안이 생성됨` | 근거·조회 결과 검사 |
| 6A | 고객 | `[이벤트] 근거 포함 답변이 제공됨` | 신뢰도 0.80 이상이며 민감 조치가 아님 |
| 6B | 상담사 | `[이벤트] 문의가 상담사에게 인계됨` | 낮은 신뢰도·민감 문의 |

### 정책·실패·복구

- `POL-01`, `POL-02`, `POL-03`, `POL-04`, `POL-07` 적용
- 고객 첫 답변 p95 5초 목표와 전체 실행 15초 하드 타임아웃 적용
- 카드·거래 읽기 조회는 3초 타임아웃, 지수 백오프와 지터를 둔 최대 2회 재시도 적용
- 조회 실패 시 상태를 추측하지 않고 조회 실패 사실과 상담사 연결 선택지를 제공
- 답변 생성은 최대 2회로 제한하며, 두 번째 실패 시 상담사 인계
- 같은 `inquiryId`를 다시 받으면 기존 티켓과 결과를 재사용하는 멱등 처리
- 상태: `접수됨 → 분류됨 → 조회됨 → 답변됨/인계됨/처리실패됨`

## 2. WF-02 상담 지식 개선 배치

### 흐름

| 순서 | 액터·시스템 | 이벤트 스토밍 요소 | 데이터·정책 |
|---|---|---|---|
| 1 | 배치 스케줄러 | `[커맨드] 전일 상담 분석 시작` | 배치 기준일, 실행 ID |
| 2 | 상담 분석 | `[이벤트] 전일 상담 이력이 마스킹됨` | 마스킹된 상담 결과 |
| 3 | 상담 분석 | `[이벤트] 반복 문의와 오답 후보가 탐지됨` | 빈도·재문의율·수정률 |
| 4 | FAQ 후보 생성 | `[이벤트] FAQ 개선 후보가 생성됨` | 질문·초안·근거·영향도 |
| 5 | 품질 검사 | `[이벤트] 후보 검증이 완료됨` | 근거·중복·금지 정보 검사 |
| 6 | 운영자 검토함 | `[이벤트] FAQ 개선 후보가 승인 대기됨` | 자동 게시 금지 |

### 정책·실패·복구

- `POL-01`, `POL-05`, `POL-06`, `POL-07` 적용
- `기준일자+데이터버전`을 실행 키로 사용하고 후보 내용 해시로 중복 후보 생성을 방지함
- 단계별 체크포인트를 저장하고 일시 오류는 최대 2회 재시도함
- 06:00까지 완료하지 못하면 운영자에게 경고하고 마지막 성공 단계부터 재개함
- 데이터가 기준 건수 100건 미만이면 후보를 만들지 않고 데이터 부족 상태로 종료함
- 일부 파티션만 분석된 경우 성공으로 기록하지 않고 부분 실패 상태로 저장함
- 상태: `예약됨 → 분석중 → 후보생성됨 → 승인대기/후보없음/부분실패/실패됨`

## 3. WF-03 상담 종료 후처리

### 흐름

| 순서 | 액터·시스템 | 이벤트 스토밍 요소 | 데이터·정책 |
|---|---|---|---|
| 1 | 상담 채널 | `[이벤트] 상담이 종료됨` | 상담 ID, 고객 ID 토큰, 대화 위치 |
| 2 | 후처리 오케스트레이션 | `[커맨드] 상담 후처리 시작` | 상담 ID를 멱등 키로 사용 |
| 3 | 상담 요약 | `[이벤트] 상담 요약이 생성됨` | 사유·확인·안내·후속 조치 |
| 4 | 개인정보 보호 | `[이벤트] 상담 요약이 마스킹됨` | 민감정보 원문 제거 |
| 5A | 상담사 | `[이벤트] 상담 요약이 확인됨` | 낮은 신뢰도·민감 상담 |
| 5B | CRM | `[이벤트] 상담 요약이 저장됨` | 마스킹 검사를 통과한 요약만 저장 |
| 6 | 설문 알림 | `[이벤트] 만족도 설문이 발송됨` | 고객 수신 동의와 채널 정책 확인 |

### 정책·실패·복구

- `POL-01`, `POL-04`, `POL-06` 적용
- `eventId`와 `eventId+작업종류`를 단계별 멱등 키로 사용하여 저장·발송 중복을 방지함
- 상담 종료 이벤트는 `eventId`, 상담 ID, 종료 시각, 스키마 버전을 포함함
- 요약 10초, CRM 5초, 설문 발송 요청 5초의 단계별 하드 타임아웃 적용
- CRM 저장과 설문 발송은 각각 최대 3회 재시도함
- 계속 실패하면 실패 보관함에 저장하고 운영자에게 알림
- CRM 저장 실패와 설문 발송 실패를 분리하여 이미 성공한 작업을 되돌리지 않음
- 상담 종료 후 p95 60초 안에 CRM 저장 완료 목표
- 상태: `종료수신됨 → 요약됨 → 마스킹됨 → 저장됨 → 설문요청됨/검토대기/실패됨`
