# 설계서 ⑤ 지식/도구 — 작성 가이드

## 1. 이 설계서가 답하는 질문

**"이 담당자는 무엇을 근거로 답하는가."**  
질문마다 답을 어디서 가져올지, 민감한 값을 어디서 가릴지 못 박는 문서임.

**이걸 안 하면 나는 사고 3줄**

- 집계 질문을 문서 검색에 던져 숫자가 매번 달라짐. 시연에서 무너짐
- 고객 이름·전화가 가려지지 않은 채 외부 모델로 나감. 되돌릴 수 없음
- ⑦ 배포가 저장소를 못 정해 배포 설계가 멈춤

**앞뒤 연결도**

```mermaid
flowchart LR
  P2["② 논리아키텍처"] -->|HARD 민감라벨(SL)| P5
  P3["③ 패턴/시퀀스"] <-->|C-2 경로↔규격| P5["⑤ 지식/도구"]
  P4["④ 역할계약서"] <-->|C-1 필드↔권한| P5
  P5 -->|HARD 저장소| P7["⑦ 배포"]
```

용어 — `HARD`는 앞이 없으면 못 채움. `C-1`·`C-2`는 서로 보며 한 번 되돌리는 관계임.  
③ 패턴/시퀀스·④ 역할계약서는 ⑤ 지식/도구보다 **먼저** 쓰므로 ⑤ 지식/도구는 두 산출물의 값을 받아 맞추는 쪽임 — 새 이름을 지어내지 않음.

## 2. 시작 전 판정

**순서를 뒤집음.** 스택을 먼저 늘어놓지 않고 `질문 3개 → 경로 판정 → 버린 대안 1줄` 순으로 함.

**1단계 — 질문 3개 적기(5분).** 사용자가 실제로 칠 문장 그대로 적음.  
유저스토리의 `[검증 요구사항]` 조회형 항목에서 베끼면 빠름.

**"3개"는 판정 기준 개수가 아니라 표본 질문 개수임.** 아래 표는 질문 1개마다 처음부터 끝까지 통과시켜 경로를 정함.  
질문 유형이 단순한 앱은 3개로 충분하나, 문의 유형이 5종 이상으로 다양하면 5~10개로 늘림 — 개수만 늘고 절차는 같음.

**2단계 — 질문마다 위에서부터 예/아니오로 내려감.**

| 물음 | 예 | 아니오 |
|------|----|--------|
| 답이 조건에 맞는 **목록**인가(반경·필터·정렬) | **정형 조회**(검색 아님) | 다음 줄 |
| 답이 **개수·합계·추이**인가 | **NL2SQL** | 다음 줄 |
| 답이 문서 1~2군데 문장인가 | **벡터 RAG** | 다음 줄 |
| 관계를 2번 이상 건너가야 하나 | **GraphRAG** | 다음 줄 |
| 사내 코드·용어를 1:1로 고정해야 하나 | **용어사전·온톨로지** | `[확인필요]` |
| 이 판정이 틀리면 **되돌릴 수 없나** | 고른 경로 **앞에** 결정론 단계를 따로 둠 | 그대로 진행 |

용어 — NL2SQL은 말을 SQL로 바꿔 표를 조회함. 벡터 RAG는 뜻이 가까운 문단을 찾아옴.  
GraphRAG는 개체를 선으로 이어 그 선을 따라감.

**첫 줄이 왜 맨 위인가** — 데이터가 대부분 표인 앱은 답이 `목록`임. 이 줄이 없으면  
넷 다 아니오가 되어 전부 `[확인필요]`로 떨어짐.

**마지막 줄은 경로를 바꾸지 않음.** 알레르기·투약 판정은 확률에 맡기지 않음.  
결정론 단계를 앞에 두고 **LLM 입력 규격에서 그 필드를 지움.** 칸이 없으면 값이 갈 길이 없음.

**3단계 — 버린 대안 1줄.** "GraphRAG는 비용 때문에 뺌"처럼 남겨야 다시 판단 가능함.  
**멈춤 신호** — 표본 질문이 한 경로로만 몰리면 잘못 뽑은 것임. 다시 뽑은 뒤 시작함.

**이 판정은 최종 확정이 아님.** 표본 3~10개로 잡은 방향은 3절 골든셋(20~30문항)으로 다시 검증함.  
골든셋 통과율이 낮으면 이 절로 되돌아와 판정을 다시 함 — 3단계의 버린 대안 1줄이 재판단의 근거가 됨.

**비정형 경로 선택·정의 — 방식별 필수 스펙**  
"정형 접근 경로"는 표 이름·필터·상한까지 구체값을 적지만, 비정형 경로는 선택 근거만 적고 실제 구성은 비워두기 쉬움.  
채택한 방식마다 아래 스펙을 채움. 미채택 방식은 `해당 없음`으로 적음.

| 채택 방식 | 필수 스펙 필드 | 없으면 생기는 사고 |
|-----------|----------------|-------------------|
| 벡터 RAG | 인덱스명 · 문서 범위·기준일 · 청킹 단위/크기/중첩 · 임베딩 모델명·버전 · 검색방식·top-k·리랭킹 여부 · 메타데이터 필터 키 | 재색인 때 값이 달라져 이전 평가와 비교 불가함 · 권한 경계를 못 걸러 못 볼 문서가 근거로 인용됨 |
| GraphRAG | 노드 타입 목록 · 관계(엣지) 타입·방향 · 노드 고유키 규칙 · 추출·검수 방법 · 최대 홉 수·결과 상한 · 커뮤니티 요약 사용 여부 | 부정 관계(`선택 안 함`)가 뭉개져 정반대 답이 나옴 · 재적재 때 노드가 중복으로 계속 불어남 |
| 온톨로지·용어사전 | 사전 파일 위치·형식 · 대표어·동의어 목록 · 적용 지점(질의 확장/검색 후/출력 표기) · 1:N 충돌 처리 규칙 · 미등록어 처리 규칙 · 갱신 주체·주기 | 코드가 두 뜻일 때 오류 없이 조용히 틀림 · 신규 코드 미반영을 검색 품질 문제로 오진함 |

메타데이터 필터 키는 ④ 역할계약서에 있는 이름을 인용만 함 — ⑤ 지식/도구가 새 이름을 짓지 않음(G-12).

**접근 제한 3종의 경계** — 이름이 비슷해 헷갈리기 쉬움. `정형 접근 금지 컬럼`(표.열, 아예 조회 안 함) ·  
`메타데이터 필터 키`(위 표, 비정형 문서 중 못 볼 것을 걸러냄) · `민감 필드 변환 지점`(아래 표, 조회는 되나 값을 가림)  
— 셋은 막는 층이 다름. 하나로 합쳐 적지 않음.

**G-10 확정** — Mock 구분 목록은 ⑤ 지식/도구에 두되 값의 주인은 ② 논리아키텍처임. ⑤ 지식/도구는 커넥터 단위로 펼쳐 적고,  
값이 다르면 ② 논리아키텍처를 따르고 다르다는 사실만 1행 남김.

**소유 방향이 서로 반대임** — 필드 ID는 **⑤ 지식/도구**가, 키 이름은 **④ 역할계약서**가 가짐(G-12).  
단계 간 **키 집합 식별자**는 ④ 역할계약서보다 먼저 쓰는 **③ 패턴/시퀀스**가 가짐 — 셋이 각자 다른 층을 소유함.  
③ 패턴/시퀀스·④ 역할계약서의 키가 이상해도 ⑤ 지식/도구에서 고치지 않고 `정합 확인 필요` 칸에만 적음.

**사용 주체 칸** — 같은 외부 시스템을 요청 경로와 배치 경로가 함께 씀. 안 적으면  
④ 역할계약서는 요청 경로에 넣고 ⑦ 배포는 접속 정보를 둘 곳을 못 정함.

**원천 오류율 칸 — 2단으로 물음**  
검색을 손봐도 원본이 틀리면 답도 틀림. 순서가 있음.

**1단 그 원천이 실제로 있나** — 아니오면 오류율이 아니라 `경로 불가`임.  
없는 원천에 오류율을 채우려다 막히는 것이 가장 흔한 사고임.  
**2단 오류율을 쟀나** — 경로별로 `원천 오류율 / 측정 방법 / 측정일` 3칸을 더함.  
못 쟀으면 `[확인필요]`로 둠. 짐작한 숫자를 쓰지 않음.  
캐시를 거치면 `갱신 지연` 1칸을 더함 — 실제 오류율에 지연분이 얹힘.

**골든셋 20~30문항**  
정답을 먼저 만들고 검색을 고침. 순서가 반대면 고쳤는지 알 수 없음.  
만드는 법 — 문의 로그에서 자주 나온 순으로 뽑음 → 유형 4종을 고르게 섞음 →  
문항마다 `질문 / 정답 / 근거 문서·행`을 적음 → 2명이 따로 풀어 답이 갈리면 버림.

**로그가 없는 신규 서비스** — 미출시면 로그가 0건임. 대신 유저스토리의  
`[검증 요구사항]` 1항목을 문항 1개로 바꿈. 그것이 곧 정답 조건임.  
Pain Point 표를 빈도 순 후보로 쓰고, 베타 뒤 실제 로그로 바꿈.

**비율 목표는 표본 수를 먼저 셈** — 목표가 `95%`면 필요 표본은 `1 ÷ (1 − 0.95) = 20`개임.  
6문항(태그 18개)이면 눈금이 5.56%p라 `17/18 = 94.4%`가 불합격임. 합격선이 사실상 100%가 됨.  
① 목표/품질 카드의 비율 목표마다 이 산식으로 문항 수를 정함.

> **경고** — 공개 실습 데이터 BookSQL은 `CC BY-NC-SA 4.0` 비상업 라이선스임.
> 유상 교육·사내 과제에 원본을 그대로 쓰지 않음. **자기 도메인 30문항**으로 대체함.

**되돌리기 왕복 1회로 끝내는 규칙**

순서 — `⑤ 지식/도구의 필드 초안 → ④ 역할계약서의 권한 배정 → ⑤ 지식/도구의 변환 지점 확정 →`  
`③ 패턴/시퀀스의 커넥터 규격 되돌림 확인(C-2) → 종료`.  
③ 패턴/시퀀스는 ⑤ 지식/도구보다 먼저 쓰였으므로 마지막 칸은 **새로 쓰는 것이 아니라 이미 쓰인 값과 맞추는 확인**임.  
④ 역할계약서가 ⑤ 지식/도구에 없던 필드를 찾으면 ⑤ 지식/도구가 번호를 **뒤에** 더함. 기존 번호를 다시 매기지 않음.  
중단 기준 3가지 — 왕복 2회째 / 같은 칸 세 번째 수정 / 30분 초과.  
하나라도 걸리면 멈추고 `[확인필요]`로 남긴 뒤 넘어감.

## 4. 예시

### 4-1. KT 개통 자동화 — 한 줄기 완주

> 출처는 강사의 `oss/docs/plan/`임. **열 수 없어도 됨.** 볼 것은 **판단 경로**임.

**줄기의 시작** — 핵심 문제 2번 `데이터 정합성 오류 25~30% 재작업`(`think/비즈니스모델.md` 26행).  
이 25~30%가 그대로 검색 실패율이 됨.

**질문 3개와 판정**

| 사용자가 치는 문장 | 유형 | 경로 | 버린 대안 |
|--------------------|------|------|----------|
| "이번 달 검증 실패 몇 건?" | 집계 | NL2SQL | RAG — 숫자가 흔들림 |
| "이 Oracle 코드의 원부 코드는?" | 용어 고정 | 코드 매핑 표 조회 | RAG — 1:1이라 불필요 |
| "이 건은 왜 떨어졌나?" | 해석 | 벡터 RAG | NL2SQL — 사유가 문장임 |

근거 — 코드 매핑은 `design/userstory.md` UFR-DATA-010, 실패 사유는 UFR-DATA-030임.

**GraphRAG는 뺌** — "불일치가 어느 단계에서 생겼나"는 관계 추적이 맞으나 구축 비용이  
MVP 3개월을 넘김. 2차로 미루고 1줄 기록함.

**원천 오류율 칸** — 오류율 25~30%는 기획서에 있음(같은 문서 20행). 코드 매핑 표  
자체의 오류율은 없음 → `[확인필요]`. 1단(존재 여부)은 통과했으므로 2단만 비움.

**골든셋** — 실패 사유 상위 유형에서 30문항. 집계 10 / 코드 조회 10 / 해석 10.

**민감 필드** — 고객 이름·전화·주소. 마스킹은 NFR-SYS-020, 3년 보존·파기는 NFR-SYS-080 인용.  
변환 지점은 ② 논리아키텍처의 경계 식별자로 적음. 이 줄기가 ③ 패턴/시퀀스 1단계와 ⑦ 배포의 저장소 2개로 넘어감.

### 4-2. 마이데이터 금융상품 추천

K은행 사회초년생 과제임(`케이스:O-1`~`O-3`). 기획 산출물이 없어 수치가 추정임.  
**실제 과제에서는 추정값을 쓰지 않고 `[확인필요]`로 되물음.**

**한 도메인에서 경로가 세 갈래로 갈림** (출처 `케이스:3-2`)

| 사용자가 치는 문장 | 유형 | 경로 | 판정 이유 |
|--------------------|------|------|----------|
| "내 자산이면 어떤 상품?" | 필터·정렬 | **NL2SQL** | 정형 테이블이 본체임 |
| "중도해지 수수료는?" | 사실 조회 | **벡터 RAG** | 약관 한 대목이면 끝남 |
| "나와 비슷한 사람이 고른 상품은?" | 관계 | **GraphRAG** | 세그먼트→제안서→선택→상품 3홉 |

"마이데이터니까 GraphRAG"가 아님. **이 질문이 관계를 따라가야 해서** GraphRAG임.

**4-1과 판단이 뒤집힘** — 여기는 "함께 제시된 상품" 같은 동시 등장·부정 관계 질문이  
실제로 있음. 벡터로는 원리적으로 불가함(B01 §1.4).

**⑤ 지식/도구가 정할 것은 노드와 관계 그 자체임** — 세그먼트·자산·제안서·상품·기관을 노드로,  
`추천`·`선택함/선택 안 함`을 관계로 둘지 정함. 라벨을 짐작하지 않음.

**민감 필드 분류표가 빌 것 같지만 비지 않음** — 입력은 익명임(`케이스:R-1`). 그런데  
**과거 제안서를 근거로 쓰는 순간 남의 자산 정보가 출력 경로로 들어옴**(`케이스:3-2` V-1).  
그래서 3행이 남음 — 익명화가 끝나는 지점 / 금액·기관명 조합의 재식별 위험 /  
인용되는 타인 자산 항목임. 입력 쪽 마스킹만으로는 못 막음.

**골든셋** — 자기 도메인 30문항 원칙은 그대로임. 채점에 근거 표기율 **100%(추정, M-4)**,  
부적합 상품 포함률 **0%(추정, M-5)**.

## 5. 자주 틀리는 5가지

| # | 양상 | 원인 | 대책 |
|---|------|------|------|
| 1 | 전부 벡터 RAG로 밀어붙임 | 한 경로로 통일하면 편함 | 2절 판정표를 질문마다 다시 돌림 |
| 2 | 평가 없이 청킹·모델부터 손댐 | 눈에 보이는 게 그것뿐임 | 골든셋 30문항 먼저 |
| 3 | 원천 오류율을 안 재고 검색만 고침 | 원본은 남의 일로 봄 | 3절 `원천 오류율 칸` 2단을 표에 추가 |
| 4 | C-1·C-2를 끝없이 왕복함 | 종료 기준이 없음 | 3절 `되돌리기 왕복 1회로 끝내는 규칙`의 중단 기준 3가지 |
| 5 | NL2SQL에 상한이 없음 | 조회니까 안전하다고 봄 | 읽기 전용 계정·행 수 상한 |

**1번 보충** — 개수·합계는 벡터 검색이 원리적으로 못 답함(B01 §4.2).

**2번 보충** — Ragas 사례는 같은 모델·99문항에서 프롬프트만 3판 고쳐 정확도가  
**2.02% → 60.61% → 70.71%**로 올랐음(A09). 모델 교체 전에 고칠 것이 남았다는 증거임.

**5번 보충** — INSERT·UPDATE·DELETE를 막고 읽기 전용 계정만 씀.

## 6. 제출 전 자가 점검표

- [ ] 정형 접근 경로 표에 데이터 행이 1행 이상 있고 `정형 접근 금지 컬럼` 공란이 0건임
      (막을 것이 없으면 `없음(전 항목 허용)`)
- [ ] 비정형 경로 표의 행 수 = **후보 방식 수**(채택·미채택 표기 포함)
- [ ] 채택한 비정형 방식마다 스펙 칸이 채워져 있음(벡터 RAG=인덱스·청킹·임베딩 모델, GraphRAG=노드·관계 타입, 용어사전=파일 위치·매핑 규칙).
      미채택 방식은 `해당 없음`
- [ ] 커넥터 입출력 키가 ④ 역할계약서 4절의 이름과 어긋난 건수 0건
- [ ] ② 논리아키텍처의 `경계 미통과 항목`이 커넥터 입출력 키에 **하나도 없음**(마스킹 처리가 아니라 키 자체를 뺐는지 확인)
- [ ] 경로마다 `버린 대안` 1줄이 있음
- [ ] 커넥터 표의 입력·출력·Mock 구분 3칸에 공란이 0건임
- [ ] 민감 필드 표 행 수 ≥ 민감정보 목록 행 수
- [ ] `변환 수행 지점` 칸 전부에 ② 논리아키텍처의 경계 식별자 문자열이 들어감
- [ ] 보존 기간·삭제 주기 숫자를 기획 자료에서 인용했고 출처를 적음
- [ ] 원천 오류율 칸이 있고, 못 쟀으면 `[확인필요]`로 적혀 있음
- [ ] 골든셋 문항 수가 20 이상이고 유형 4종이 섞여 있음
- [ ] 쓰기 SQL 금지가 문장으로 있고, 행 수 상한이 숫자이거나 `[확인필요]`로 되물어진 상태임
- [ ] `[확인필요]` 전부가 말미 미확정 항목 표에 1행씩 있음
