## 2. 상세 — 아키텍처 기술 표준 (클로니 검증)

### V-1 ATAM 6요소 — **불일치**

원문: `CMU/SEI-2000-TR-004`(`.temp/atam.pdf`로 확보, 245KB).

**Figure 7 문서화 템플릿의 실제 항목**은 아래 5개임.

```
Scenario / Attribute / Environment / Stimulus / Response
(+ Architectural Decisions · Risk · Sensitivity · Tradeoff · Reasoning · Architecture diagram)
```

문자열 검사 결과임.

| 찾은 말 | 횟수 |
|---------|------|
| `source of stimulus` | **0회** |
| `six-part` · `six part` | **0회** |
| `artifact` | 4회 — 전부 `architectural artifacts`라는 일반 명사임 |
| `response measure` | 2회 — 개념으로 언급되나 **템플릿 항목이 아님** |

**따라서 `references/recommend-materials.md` 부록 B의 아래 서술은 원문과 다름.**

> 품질속성 시나리오 6요소(`source·stimulus·artifact·environment·response·response measure`)의 원전

6요소 형식은 ATAM 보고서가 아니라 **다른 문헌에서 정립된 것으로 보임.**
부록 B가 "v1에서 제외"로 내려 둔 `Bass 외(2021) Software Architecture in Practice`가
실제 출처일 가능성이 있으나 **원문을 확보하지 않았으므로 단정하지 않음.**

다만 A05(AgentArcEval) 판독에서 **논문에는 6요소가 실재함**을 확인했음
(`Source`·`Stimulus`·`Environment`·`Artefact`·`Response`·`Response measure`).
즉 **6요소 자체는 실재하나 그 출처가 ATAM 2000 보고서는 아님.**

### V-2 9단계 — **불일치(이름만 같음)**

ATAM도 9단계임. 그런데 **내용이 전혀 다름.**

| ATAM 9단계(원문 425 ~ 440행) | 커리큘럼 9단계 |
|---------------------------|---------------|
| 1 Present the ATAM | 1 목표·품질속성 |
| 2 Present business drivers | 2 시스템 경계 |
| 3 Present architecture | 3 단일·멀티 판정 |
| 4 Identify architectural approaches | 4 역할 계약 |
| 5 Generate quality attribute utility tree | 5 조직구조·패턴 선정 |
| 6 Analyze architectural approaches | 6 상호작용·상태 |
| 7 Brainstorm and prioritize scenarios | 7 지식·도구 |
| 8 Analyze architectural approaches | 8 가드레일·관측·평가 |
| 9 Present results | 9 배치·비용 |

ATAM 9단계는 **평가 워크숍 진행 절차**임(누가 무엇을 발표하고 언제 투표하는지).
커리큘럼 9단계는 **설계 산출물 생성 순서**임. 목적이 다름.
**둘 다 "9단계"라 부르면 근거가 있는 것처럼 읽히므로 혼동을 부름.**

### V-7 ISO/IEC/IEEE 42010 — **부분 확인**

공식 커뮤니티 사이트(`iso-architecture.org`)에서 확인함. ISO 본문은 유료라 미확보임.

> This International Standard specifies architecture viewpoints, architecture frameworks
> and architecture description languages for use in architecture descriptions.

- `viewpoint`·`concern`·`stakeholder` 개념 규정은 **맞음**
- 판본은 **`ISO/IEC/IEEE 42010:2011`**임(사이트가 최신판으로 표기).
  `recommend-materials.md` 부록 B의 `2011 또는 2022, 판본 확정 필요`에 대한 답임
- 다만 커리큘럼이 말한 `산출물이 충분한지 판정하는 기준`은 표준의 문구가 아니라 **해석**임

### V-8·V-9 C4 · arc42 — **부분 확인 / 확인**

- **C4**(`c4model.com`) — `software system · container · component · code` 4계층 추상화와
  다이어그램 표기법임. **다이어그램 언어이지 충분성 판정 기준이 아님**
- **arc42**(`arc42.org`) — **12섹션 템플릿**. "무엇을 문서화해야 하는가"에 답함.
  커리큘럼이 문서화 골격 근거로 든 것은 타당함

## 3. 상세 — 에이전트 지향 방법론 (플로니 검증)

원문 `Gaia`(ACM TOSEM 2003, 54쪽)를 확보해 대조함.

### V-3 역할에 권한 포함 — **확인**

> These are represented by two main attribute classes, respectively:
> (i) permissions and (ii) responsibilities. — Gaia §4.1.3

EMAS 2025 논문도 재확인함 — `GAIA emphasizes that roles encompass responsibilities,
protocols, and permissions.`

**단서 하나** — Gaia의 `permission`은 **자원 접근·소비 한도**(`reads`/`changes`)를 뜻함.
LLM 에이전트의 **도구 실행 권한**과 의미가 같지 않음. 가이드에서 이 차이를 밝혀야 함.

### V-4 뼈대 순서 — **불일치**

Gaia §4의 실제 순서임.

```
환경 모델 → 예비 역할 → 예비 상호작용 → 조직 규칙 → 조직구조
→ 역할·상호작용 모델 완성 → 에이전트 모델 → 서비스 모델
```

차이 2가지임.

- 시작점이 **목표가 아니라 환경 모델**임(목표 지향은 Tropos 계열 특징이나 미검증)
- 조직구조 결정이 역할·상호작용을 **되먹임으로 다시 고침**. 커리큘럼은 일방향 나열임

### V-5 배치를 독립 산출물로 — **불일치**

> Gaia does not directly deal with implementation issues. The outcome of the Gaia process
> is a detailed but technology-neutral specification. — Gaia §4

마지막 산출물은 **서비스 모델**이며 배치 산출물이 없음. 커리큘럼 주장과 **정반대**임.

### V-6 FIPA — **불일치**

`fipa.org` 표준 목록(SC00001·23·26 ~ 37·61·67 ~ 85)은 Abstract Architecture · ACL ·
Contract Net 등 **통신 규격**임. 설계 절차 뼈대가 없음.
사이트가 스스로 `FIPA is currently not active`라고 표기함.

### 반대 방향 증거 1건

EMAS 2025 논문이 이렇게 적음.

> we find little to no evidence that these new platforms build on established AOSE methodologies.

즉 **최근 LLM 에이전트 플랫폼이 기존 AOSE 방법론 위에 세워졌다는 증거가 거의 없다**는
학계 관찰임. 계보 주장과 반대 방향임.

### V-10 Azure 오케스트레이션 패턴 — **부분 확인** (플로니)

**출처 표기 자체가 결함임.** 커리큘럼 문구 `Microsoft Azure 오케스트레이션 패턴`만으로는
아래 3종 중 어느 것인지 지목할 수 없음.

| 후보 | 제목 |
|------|------|
| A(최유력) | **AI agent orchestration patterns** — Azure Architecture Center |
| B | Cloud Design Patterns — Azure Architecture Center |
| C | Semantic Kernel Agent Orchestration |

C가 A를 상위 출처로 되짚고(`refer to the AI agent orchestration patterns`) A가 B와의 관계를
별도 절로 구분하므로 **A로 수렴함**. 원문 상호참조로 확정한 지목이며 임의 선택이 아님.

A를 대상으로 대조한 결과임.

| 커리큘럼 주장 | 판정 | 원문 근거 |
|-------------|------|----------|
| 오케스트레이션 패턴 선택 | **확인** | 패턴 5종(`Sequential`·`Concurrent`·`Group chat`·`Handoff`·`Magentic`)과 `Choose a pattern` 비교표, 패턴별 `When to use`/`When to avoid` |
| 상태·메모리 설계 | **확인** | `Context and state management` 절 — `persist shared state externally rather than relying only on in-memory context` |
| **도구 계약** | **불일치** | `tool contract`·`tool schema` 등 도구 명세 지침 **0회**. MCP를 1줄 언급할 뿐임 |
| 가드레일·관측·복원력 | **확인** | Reliability(타임아웃·재시도·점진적 성능저하) · Security(`content safety guardrails at multiple points`) · `Observability and testing` · `Human participation` |

덧붙여 원문이 **"단일부터 시작하라"**를 명시함 — `If a single agent can reliably solve your
scenario, consider adopting that approach.` ④ 가이드의 `단일이 기본값`과 같은 취지임.

### V-11 AWS Well-Architected Agentic AI Lens — **확인(실재)** (클로니)

## 6. 이 검증이 교육에 주는 것

결함을 찾은 것이 아니라 **가르칠 거리를 찾은 것으로 봄.**

- 수강생이 설계서에 `근거 출처`를 적을 때, **"어디서 봤다"와 "원문에 있다"는 다름**을 보여주는 실물 사례임
- 2층에서 4건이 어긋났다는 사실 자체가 **"인용은 확인하고 쓴다"**는 규칙의 필요성을 증명함
- 가이드 5절 예시가 `추정`·`[확인필요]` 태그를 강조하는 이유와 같은 맥락임
