# AI 앱 아키텍처 설계 가이드 7종

작성: 2026-08-06 · 팀: design-agentic-ai · 토론·통합: 클로니(오케스트레이터)

AI 앱의 아키텍처를 **설계 산출물 7종**으로 만들 때 손에 들고 읽는 가이드임.
`prompts/architecture/`의 작성 프롬프트를 **사람이 판단할 수 있는 순서로 다시 쓴 것**임.

---

## 프롬프트와 가이드는 무엇이 다른가

| | 프롬프트 `prompts/architecture/` | **가이드 `guides/`(이 폴더)** |
|---|---|---|
| 받는 쪽 | AI 코딩 도구 | **사람** |
| 형식 | `{변수}` 치환 템플릿 · MUST / 완료조건 | 판단 순서 · 예시 · 함정 |
| 순서 | 규격을 빠짐없이 훑는 순서 | **사람이 실제로 판단하는 순서** |
| 쓰는 때 | 산출물을 자동 생성할 때 | **직접 설계할 때, 생성 결과를 검토할 때** |

가이드는 프롬프트의 해설이 아님. 두 가지를 더 함.

1. **순서를 뒤집음** — 프롬프트 ⑤는 `스택 → 경로` 순으로 시킴.
   사람은 `질문 유형 뽑기 → 경로 판정 → 버린 대안 기록` 순으로 판단하므로 가이드는 사람 순서를 따름
2. **프롬프트에 없는 칸을 메움** — 규격에 빠져 있어 설계자가 직접 채워야 하는 항목을 각 가이드 4절에 둠

## 먼저 정할 것 — 어느 모드로 쓰나

가이드는 두 가지 쓰임이 있고, **읽는 순서와 시간이 다름.** 시작 전에 한쪽을 고름.

| 모드 | 누가 | 어떻게 씀 |
|------|------|----------|
| **직접 작성** | KT 3일 과정 | 2절 판정 → 3절로 칸 채움 → 7절 점검. 5절 예시는 막힐 때만 봄 |
| **생성 후 검토** | 신한카드 10주 과정 | AI로 산출물을 만든 뒤 **6절 함정**과 **7절 점검표**로 검토함 |

7건을 다 읽으면 **약 140분**임. 3일 과정에서는 전부 읽지 않음.
**최소 경로**는 각 가이드의 `2절 판정 → 3절 표 → 7절 점검표` 3개 절임(1건당 약 7분).

## 산출물 1건은 무엇으로 이뤄지나

가이드 3절은 **칸(열) 채우는 법**이고, 아래가 **표(문서 목차)**임.
이 목록이 곧 제출물 목차이며, 7절 자가 점검표가 검사하는 대상임.

| 설계서 | 본문 표 | 말미 부속 표(0건이어도 `0건`으로 적음) |
|--------|---------|--------------------------------------|
| ① | 성공 기준(3행) · 우선 품질속성(3행) · 개선 전 기준선 | 제외 지표 · 미대응 Pain Point · 대조 기록 · 미확정 항목 |
| ② | 전체 관계도 · 내부 구성도 · 외부 서비스 목록 · 후행 소비처 | 구성요소 대조 표 · 노드·간선 근거 대조표 · 대조 기록 · 미확정 항목 |
| ③ | 판정 근거(3줄) · 에이전트별 계약 7칸 · 후행 소비처 | 대조 기록 · 미확정 항목 |
| ⑤ | 정형 접근 경로 · 비정형 경로 · 커넥터 · 민감 필드 분류 · 골든셋 요약 | 대조 기록 · 미확정 항목 |
| ④ | 패턴 비교 · 시퀀스 도식 · 단계 표 · 상태 스키마 · 타임아웃·재시도 · 변경요청 | 대조 기록 · 미확정 항목 |
| ⑥ | 가드레일 · 마스킹 · 관측 기록 · 품질 측정 · 비용 상한 | 대조 기록 · 미확정 항목 |
| ⑦ | 배포 단위 · 포트 · 비밀값 · 저장소 배치 · 되돌리기 | 대조 기록 · 미확정 항목 |

**부속 표 4종의 열은 7종이 똑같이 씀.**

| 부속 표 | 열 구성 |
|---------|--------|
| 제외 지표 | 지표 / 분류(공동 책임·책임 밖) / 탈락 테스트 번호 / 목표값 / 근거 출처 |
| 미대응 Pain Point | 기획서의 Pain Point / 이번 범위에서 안 다루는 이유 / 언제 다루나 |
| 대조 기록 | 기획 항목 ID / 반영 여부(반영·부분반영·범위외·미반영) / 반영 위치 / 사유 |
| 미확정 항목 | `[확인필요]` 태그 / 무엇이 없나 / 누구에게 되묻나 / 안 오면 무엇이 막히나 |

문서 1건 = 마크다운 파일 1개임. 파일명은 `설계서{번호}-{산출물명}.md`로 함.

## 근거 출처 표기법 — 모든 표의 마지막 열

형식은 `{약칭}:{항목 ID}#{하위}`임. 약칭은 아래 7개만 씀. 새로 만들지 않음.

| 약칭 | 무엇의 줄임말 | 우리 과제에서 그것은 | 예 |
|------|--------------|--------------------|-----|
| BM | 비즈니스 모델 | 린 캔버스·핵심 지표가 적힌 기획 문서 | `BM:8-KeyMetrics#고객가치1` |
| US | 유저스토리 | 기능(UFR)·비기능(NFR) 요구가 적힌 설계 문서 | `US:NFR-SYS-020#마스킹` |
| ES | 이벤트스토밍 | 업무 흐름 도식 파일 | `ES:02#참여자` |
| PR | 프로젝트 개요 | 과제 정의서·제안 자료 | `PR:3#To-Be흐름` |
| KT | 교육 커리큘럼 | 과제가 요구하는 점검 항목 표 | `KT:7-3#추천근거추적` |
| 케이스 | `_shared/마이데이터-케이스.md` | 5-2 예시 전용 근거 | `케이스:R-2` |
| 설계판단 | 원문 근거가 없고 팀이 정한 것 | — | `설계판단` |

`UFR`은 기능 요구, `NFR`은 비기능 요구, `AFR`은 공통·부가 요구를 뜻함.
원문에 값이 없으면 지어내지 않고 `[확인필요: 무엇]`으로 남기고 미확정 항목 표에 1행 적음.

## 프롬프트에 없어 가이드가 메운 것

토론에서 팀원 3명이 각자 담당 프롬프트를 읽고 지목한 항목임.
**이걸 안 채우면 설계가 뚫린다**고 판단한 것들임.

| 가이드 | 메운 항목 | 왜 |
|--------|----------|-----|
| ③ | 단일·멀티 **판정 사다리** | 프롬프트는 "3줄 판정 근거"만 요구함. 결론 칸일 뿐 판단법이 없음 |
| ④ | **상태 필드 소유권 규칙** | 병렬 분기에서 두 노드가 같은 필드를 쓰면 덮어쓰기로 값이 사라짐 |
| ④ | **반복 상한과 소진 시 착지 노드** | 표에 칸 자체가 없음. "실패 시 재계획"이 무한 왕복이 됨 |
| ④ | **재시도 포함 최악값 합계** | 타임아웃 합계 검증이 성공 경로만 더해 예산을 통과시킴 |
| ⑤ | **원천 데이터 오류율 칸** | 기획서의 정합성 오류 25 ~ 30%가 그대로 검색 실패율이 됨 |
| ⑤ | **골든셋 20 ~ 30문항 만드는 법** | 평가 없이 청킹·모델부터 손대는 순서 오류를 막음 |
| ⑥ | **관측 기록을 마스킹 대상 표의 행으로** | 출력 직전 1회만 가리면 관측 기록·오류 로그에 원문이 남음 |
| ⑦ | **비밀값 위반 예시 3종** | 이미지 레이어 · 설정 파일 평문 · 로그 출력 |

## 실제 기획 자료에서 찾은 것

예시는 **KT 개통 자동화 플랫폼** 기획 자료(`~/workspace/oss/docs/plan/`)로 통일함.

작성 중 실제로 발견한 사항임.

| 발견 | 내용 |
|------|------|
| **재시도 중첩이 기획 자료에 이미 있음** | `userstory.md` 679행 `5회 재처리 실패 시 DLQ 저장` + `es/08-*.puml` 109 ~ 110행 `DLQ 자동 재시도 3회` → 같은 낱말 `재시도`가 두 계층에 쓰여 **한 건이 최대 15회 처리**됨. 값 충돌이 아니라 계층 차이임. ④는 예산 관점, ⑥은 관측 기록 관점으로 나눠 다룸 |

| **원천 오류율이 곧 검색 실패율** | `비즈니스모델.md` 8절 정합성 오류 25 ~ 30%. ⑤에서 경로를 고르기 전에 원천 품질을 재야 함 |

## 이 가이드의 근거는 어디까지 확인된 것인가

근거가 **3층**이고 층마다 확인 수준이 다름. 전문은
[_shared/근거-계보-검증.md](_shared/근거-계보-검증.md)임.

| 층 | 무엇 | 확인 상태 |
|----|------|----------|
| 1 | 아티클 11종(A01 ~ A10 · B01) | **원문 직접 판독함.** 각 가이드 8절에 2 ~ 5종씩 걸림 |
| 2 | 방법론·표준 계보(Gaia · FIPA · ATAM · ISO 42010 · C4 · arc42) | **검증함 — 9건 중 확인 3 · 부분 확인 2 · 불일치 4** |
| 3 | 2절 판정 트리 · 6절 함정 5가지 · 좋은 예/나쁜 예 | **팀의 실무 판단.** 출처 없음 |

**"국제 표준에 근거한 설계 가이드"라고 소개하면 과장임.** 정확히는 아래임.

> 1차 출처 11종을 직접 판독해 근거를 걸었고, 방법론·표준은 **개념을 참조해 재구성**했으며,
> 나머지는 팀의 실무 판단임.

2층 검증에서 나온 불일치 4건임.

| 커리큘럼 주장 | 원문 확인 결과 |
|-------------|--------------|
| ATAM이 품질속성 시나리오 **6요소**의 원전 | 원문 템플릿은 **5항목**. `source of stimulus` 0회 |
| 9단계가 3개 계열을 **접합한 절차** | ATAM에도 9단계가 있으나 **내용이 전혀 다름**(평가 워크숍 진행 절차임) |
| `목표 → … → 배치` 뼈대 · **배치를 독립 산출물**로 | Gaia는 **환경 모델**로 시작하고, 구현·배치를 **명시적으로 범위 밖**이라 선언함 |
| **FIPA**가 설계 방법론 계보에 속함 | FIPA 표준은 **통신 프로토콜**임. 설계 절차 없음 |

확인된 것도 있음 — **역할 정의에 `permissions`를 포함하는 규칙은 Gaia 원전에 실재함**
(단 Gaia의 권한은 *자원 접근권*이라 LLM 도구 실행 권한과 뜻이 다름).
arc42 12섹션 템플릿, ISO 42010의 viewpoint·concern 규정도 확인됨.
