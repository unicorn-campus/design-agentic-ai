# AI 앱 아키텍처 설계 가이드 7종

작성: 2026-08-06 · 팀: design-agentic-ai · 토론·통합: 클로니(오케스트레이터)

AI 앱의 아키텍처를 **설계 산출물 7종**으로 만들 때 손에 들고 읽는 가이드임.
`prompts/design/`의 작성 프롬프트를 **사람이 판단할 수 있는 순서로 다시 쓴 것**임.

---

## 프롬프트와 가이드는 무엇이 다른가

| | 프롬프트 `prompts/design/` | **가이드 `guides/`(이 폴더)** |
|---|---|---|
| 받는 쪽 | AI 코딩 도구 | **사람** |
| 형식 | `{변수}` 치환 템플릿 · MUST / 완료조건 | 판단 순서 · 판정표 · 점검표 |
| 순서 | 규격을 빠짐없이 훑는 순서 | **사람이 실제로 판단하는 순서** |
| 쓰는 때 | 산출물을 자동 생성할 때 | **직접 설계할 때, 생성 결과를 검토할 때** |

가이드는 프롬프트의 해설이 아님. 두 가지를 더 함.

1. **판단 순서를 정함** — ⑤ 지식/도구는 `질문 유형 뽑기 → 경로 판정 → 버린 대안 기록` 순으로 판단함.
   프롬프트는 이 순서를 가이드에서 받아 씀(2026-08-08 프롬프트 재작성으로 두 문서가 같은 순서가 됨)
2. **프롬프트에 없는 칸을 메움** — 규격에 빠져 있어 설계자가 직접 채워야 하는 항목을 각 가이드 3절에 함께 둠

## 시작 전에 반드시 채울 것 — 프로젝트 파라미터 12종

**가이드보다 먼저 여는 파일이 있음.** `prompts/design/_shared/프로젝트정보.md`임.
여기에 프로젝트별 값을 채우지 않으면 **⑦ 배포의 비밀값 도출이 시작 지점에서 막힘.**

| 변수 | 무엇인가 | 없으면 막히는 곳 |
|------|---------|----------------|
| `V-07 {기술 스택}` 6행 | 모델 벤더 · 정형 접근 · 비정형 접근 · 도구 연결 규격 · 오케스트레이션·패키징 · 관측·기록 | **⑦ 배포 비밀값 목록** · ⑤ 지식/도구 접근 방식 후보 · ④ 역할계약서 사용 모델 |
| `V-06 {민감정보 목록}` | 정보 유형 · 대상 필드 · 검사 방식 · 검사 기준 | ⑤ 지식/도구 민감 필드 분류표 · ⑥ 가드레일/관측 출력측 검사 정규식 |
| `V-08 {코드베이스 구성요소 목록}` | 구성요소명 · 제공 여부 · 구성 성격 | ⑦ 배포 비귀속 행 판정 |
| `V-09 {범위 제외 목록}` | 제외 항목 · 차단 위치 | **반영 대조표 2종 중 1종이 규격 미충족이 됨** |
| `V-10 {규제·안전 점검 항목}` | 점검 항목 · 계열 · 반영 산출물 · 반영 지점 | ③ 패턴/시퀀스 사전 조건 확인 · ⑥ 가드레일/관측 차단 규칙 |

나머지 7종(프로젝트 프로파일 · 케이스 정의 · 최종 산출물 · 데이터 원천 · 비용 예산 상한 ·
기획 산출물 경로 · 출력 루트 경로)은 같은 파일 3절 기입란에 있음.

**주의 2가지 — 실제 테스트에서 확인한 것임**

| # | 주의 |
|---|------|
| 1 | **채워진 값을 그대로 믿지 않음.** 런치픽 사례에서 `{데이터 원천·비정형}`에 `원재료·알레르겐 표시`가 적혀 있었으나 **오분류**였음. 기획 산출물 원문 7곳을 전수 확인한 결과 전부 사용자 입력 쪽이고 식당 원재료 데이터의 원천은 없었음. 그 위에 안전 목표를 세우면 존재하지 않는 데이터 위에 설계가 서게 됨 |
| 2 | **`계열 0건` 표기를 그대로 믿지 않음.** 같은 사례에서 `자동 확정 금지`·`출력 측 노출 검사`를 0건으로 적었으나 **둘 다 해당했음.** 그대로 따랐다면 ⑥ 가드레일/관측의 출력측 검사 절을 통째로 지웠을 것임. 모델이 만든 문장은 입력 검사로 막을 수 없고 화면으로 나감 |

파라미터가 `프로젝트 확정 필요`로 남아 있으면 프롬프트 경로는 **실행이 차단됨**(같은 파일 1절 차단 규칙).
가이드 경로는 차단 장치가 없으므로 **사람이 이 표를 직접 확인함.**

## 먼저 정할 것 — 어느 모드로 쓰나

가이드는 두 가지 쓰임이 있고, **읽는 순서와 시간이 다름.** 시작 전에 한쪽을 고름.

| 모드 | 누가 | 어떻게 씀 |
|------|------|----------|
| **직접 작성** | KT 3일 과정 | 2절 판정 → 3절로 설계항목 채움 → 4절 점검 |
| **생성 후 검토** | 신한카드 10주 과정 | AI로 산출물을 만든 뒤 **3절 `무엇을 적나`**와 **4절 점검표**로 대조함 |

7건을 다 읽으면 **약 90분**임(2026-08-08 예시·함정 절 삭제로 줄었음).
**최소 경로**는 각 가이드의 `2절 판정 → 3절 표 → 4절 점검표` 3개 절임(1건당 약 6분).

순으로 가는 것과 같음. **흐름을 먼저 확정해야 그 단계를 누가 맡고(④ 역할계약서) 무슨 지식이 필요한지(⑤ 지식/도구) 정해짐.**

`prompts/design/README.md` 3절 「쓰는 순서」임.

시간이 없으면 위 **최소 경로**만 읽음.

## 산출물 1건은 무엇으로 이뤄지나

가이드 3절은 **설계항목(열) 채우는 법**이고, 아래가 **표(문서 목차)**임.
이 목록이 곧 제출물 목차이며, 4절 자가 점검표가 검사하는 대상임.

| 설계서 | 본문 표 | 말미 부속 표(0건이어도 `0건`으로 적음) |
|--------|---------|--------------------------------------|
| ① 목표/품질 카드 | 성공 기준(3행) · 우선 품질속성(3행) · 개선 전 기준선 | 제외 지표 · 미대응 Pain Point · 대조 기록 · 미확정 항목 |
| ② 논리아키텍처 | 전체 관계도 · 내부 구성도 · 외부 서비스 목록 · 후행 소비처 | 구성요소 대조 표 · 노드·간선 근거 대조표 · 대조 기록 · 미확정 항목 |
| ③ 패턴/시퀀스 | 패턴 비교 · 시퀀스 도식 · 단계 표 · 상태 스키마 · 타임아웃·재시도 · 변경요청 | 대조 기록 · 미확정 항목 |
| ④ 역할계약서 | 판정 근거(3줄) · 담당자별 계약(3절 설계항목 전부) · 후행 소비처 | 대조 기록 · 미확정 항목 |
| ⑤ 지식/도구 | 정형 접근 경로 · 비정형 경로 · 커넥터 · 민감 필드 분류 · 골든셋 요약 | 대조 기록 · 미확정 항목 |
| ⑥ 가드레일/관측 | 가드레일 · 마스킹 · 관측 기록 · 품질 측정 · 비용 상한 | 대조 기록 · 미확정 항목 |
| ⑦ 배포 | 배포 단위 · 포트 · 비밀값 · 저장소 배치 · 되돌리기 | 대조 기록 · 미확정 항목 |

**부속 표 4종의 열 구성** — 7종이 똑같이 씀.

| 부속 표 | 열 구성 |
|---------|--------|
| 제외 지표 | 지표 / 분류(공동 책임·책임 밖) / 탈락 테스트 번호 / 목표값 / 근거 출처 |
| 미대응 Pain Point | 기획서의 Pain Point / 이번 범위에서 안 다루는 이유 / 언제 다루나 |
| 대조 기록 | 기획 항목 ID / 반영 여부(반영·부분반영·범위외·미반영) / 반영 위치 / 사유 |
| 미확정 항목 | `[확인필요]` 태그 / 무엇이 없나 / 누구에게 되묻나 / 안 오면 무엇이 막히나 |

문서 1건 = 마크다운 파일 1개임. **파일명은 프롬프트 규격과 같게 아래 7개를 씀.**

```
01-목표품질속성카드.md   02-논리아키텍처.md   04-에이전트역할계약서.md   03-패턴시퀀스설계.md
05-지식도구설계.md       06-가드레일관측설계.md   07-배포설계.md
```

7종이 다 끝나면 **`00-반영대조표.md` 1건을 더 만듦.** 점검 항목 반영 대조표와
제외 범위 미포함 대조표 2종이 들어가며, 행은 파라미터 `V-10`·`V-09`에서 나옴.
**대응 프롬프트는 없음** — `prompts/design/`은 가이드 01 ~ 07과 1:1인 7건뿐이라 이 1건은 사람이 직접 씀.

## 근거 출처 표기법 — 모든 표의 마지막 열

형식은 `{약칭}:{항목 ID}#{하위}`임. 약칭은 아래 5개만 씀. 새로 만들지 않음.
**규제·안전 점검 항목의 근거도 이 5개에서 찾음** — 탐색 순서는  
`US NFR 컴플라이언스 → ES 규제 반영표 → 없으면 [확인필요]`임.  
**교육 커리큘럼은 설계 입력이 아니므로 근거로 쓰지 않음**(2026-08-08 `KT` 약칭 폐지).

| 약칭 | 무엇의 줄임말 | 우리 과제에서 그것은 | 예 |
|------|--------------|--------------------|-----|
| BM | 비즈니스 모델 | 린 캔버스·핵심 지표가 적힌 기획 문서 | `BM:8-KeyMetrics#고객가치1` |
| US | 유저스토리 | 기능(UFR)·비기능(NFR) 요구가 적힌 설계 문서 | `US:NFR-SYS-020#마스킹` |
| ES | 이벤트스토밍 | 업무 흐름 도식 파일 | `ES:02#참여자` |
| PR | 프로젝트 개요 | 과제 정의서·제안 자료 | `PR:3#To-Be흐름` |
| 설계판단 | 원문 근거가 없고 팀이 정한 것 | — | `설계판단` |

`UFR`은 기능 요구, `NFR`은 비기능 요구, `AFR`은 공통·부가 요구를 뜻함.
원문에 값이 없으면 지어내지 않고 `[확인필요: 무엇]`으로 남기고 미확정 항목 표에 1행 적음.

**`근거 출처` 열은 본문 표에만 둠.** 부속 표 4종(제외 지표 · 미대응 Pain Point · 대조 기록 · 미확정 항목)은
위 `부속 표 4종의 열 구성`을 그대로 쓰며 `근거 출처` 열을 두지 않음.
프롬프트의 `모든 표 마지막 열은 근거 출처` 규칙과 부딪히는 자리이므로 이 문장으로 가름.

**선행 설계서를 인용할 때** — ④ 역할계약서가 ① 목표/품질 카드의 `G-3`, ② 논리아키텍처의 `TB-2`를 인용하는 것처럼 앞 산출물의 값을 쓸 일이 잦음.
새 약칭을 만들지 않고 **그 값의 원문 ID를 쓰고, 원문에 없는 판단이면 `설계판단`에 괄호로 출처를 병기**함
(예: `설계판단`(② 논리아키텍처 TB-2 통과 항목 표)).

**표 행은 120자 제약에서 제외됨.** 표 행은 줄바꿈이 안 되므로 계약 표·태그 표의 행이 120자를 넘김.
산문과 목록만 120자 이내로 지킴. 실제 작성에서 4명이 같은 지적을 했음.

## 가이드 1건의 구성 (5절 고정)

| 절 | 무엇이 있나 |
|----|-----------|
| 1 | 이 설계서가 답하는 질문 · **안 하면 나는 사고 3가지** · 앞뒤 연결도 |
| 2 | **시작 전 판정** — 5분 안에 끝나는 결정 트리 |
| 3 | **설계항목 작성법** — `무엇을 적나 / 어디서 가져오나 / 예시`. `무엇을 적나`는 **규격 한 줄(형태·비면·주인·대조) + 대시 불렛**임. 프롬프트에 없어 직접 메워야 하는 항목도 여기 함께 둠 |
| 4 | 제출 전 자가 점검표 |
| 5 | 다음으로 넘기는 값과 근거 자료 |

## 실제 설계에서 새로 확정한 소유 관계 3건

런치픽 설계 테스트에서 **④ 역할계약서와 ⑤ 지식/도구가 같은 기호를 서로 다른 뜻으로 쓰는 일이 실제로 일어남.**
소유자를 정해 두지 않으면 뒤 산출물(③ 패턴/시퀀스·⑥ 가드레일/관측)이 어느 표를 인용해야 할지 모름.

| ID | 미결 | 확정 | 근거 |
|----|------|------|------|
| G-11 | 민감 필드 ID(`F-n`)를 ④ 역할계약서·⑤ 지식/도구 중 누가 소유하나 | **⑤ 지식/도구 8절 소유 · ④ 역할계약서는 인용만.** ④ 역할계약서에만 있는 필드는 ⑤ 지식/도구가 **뒤에 번호를 더함**(기존 번호 재부여 금지) | ⑤ 지식/도구가 민감 필드 분류표를 필수 출력으로 가짐. 실제로 `④ 역할계약서 F-2 = 식이 유형` / `⑤ 지식/도구 F-2 = 정확 좌표`로 갈렸음 |
| G-12 | 입출력 **키 이름**을 ④ 역할계약서·⑤ 지식/도구 중 누가 소유하나 | **④ 역할계약서의 입출력 형식 칸이 소유 · ⑤ 지식/도구 커넥터 규격이 맞춤.** ③ 패턴/시퀀스는 `키 집합 식별자`까지만 소유함 | ④ 역할계약서에 `키 이름의 단일 출처` 선언이 이미 있음. 실제 작성에서 4건이 어긋났음(당시 순서는 ④ 역할계약서가 앞이었음) |
| G-13 | 커넥터의 범위 | **외부 시스템 접근만 커넥터임.** 내부 저장소는 `커넥터 아님`으로 구분해 적음 | 내부 저장소는 ⑤ 지식/도구 정형 접근 경로 표의 대상임. 구분이 없어 ④ 역할계약서가 저장소 접근 수단 이름을 ⑤ 지식/도구에 되물었음 |

`G-11`과 `G-12`가 **서로 반대 방향**임에 주의함 — 필드 ID는 ⑤ 지식/도구가, 키 이름은 ④ 역할계약서가 소유함.
근거가 각각 다름(분류표 소유 ↔ 계약서의 선언).

## 이 가이드의 근거는 어디까지 확인된 것인가

근거가 **3층**이고 층마다 확인 수준이 다름. 전문은
[_shared/근거-계보-검증.md](_shared/근거-계보-검증.md)임.

| 층 | 무엇 | 확인 상태 |
|----|------|----------|
| 1 | 아티클 11종(A01 ~ A10 · B01) | **원문 직접 판독함.** 각 가이드 5절에 2 ~ 5종씩 걸림 |
| 2 | 방법론·표준 계보(Gaia · FIPA · ATAM · ISO 42010 · C4 · arc42 · Azure · AWS Lens) | **검증함 — 11건 중 확인 4 · 부분 확인 4 · 불일치 5** |
| 3 | 2절 판정 트리 · 3절 `무엇을 적나`와 `예시` | **팀의 실무 판단.** 출처 없음 |

**"국제 표준에 근거한 설계 가이드"라고 소개하면 과장임.** 정확히는 아래임.

> 1차 출처 11종을 직접 판독해 근거를 걸었고, 방법론·표준은 **개념을 참조해 재구성**했으며,
> 나머지는 팀의 실무 판단임.

2층 검증에서 나온 불일치 5건임.

| 커리큘럼 주장 | 원문 확인 결과 |
|-------------|--------------|
| ATAM이 품질속성 시나리오 **6요소**의 원전 | 원문 템플릿은 **5항목**. `source of stimulus` 0회 |
| 9단계가 3개 계열을 **접합한 절차** | ATAM에도 9단계가 있으나 **내용이 전혀 다름**(평가 워크숍 진행 절차임) |
| `목표 → … → 배치` 뼈대 · **배치를 독립 산출물**로 | Gaia는 **환경 모델**로 시작하고, 구현·배치를 **명시적으로 범위 밖**이라 선언함 |
| **FIPA**가 설계 방법론 계보에 속함 | FIPA 표준은 **통신 프로토콜**임. 설계 절차 없음 |
| Azure 문서에서 **도구 계약**을 가져옴 | `tool contract`·`tool schema` **0회**. 게다가 어느 Azure 문서인지 **특정 불가**(후보 3종) |

확인된 것도 있음 — **역할 정의에 `permissions`를 포함하는 규칙은 Gaia 원전에 실재함**
(단 Gaia의 권한은 *자원 접근권*이라 LLM 도구 실행 권한과 뜻이 다름).
arc42 12섹션 템플릿, ISO 42010의 viewpoint·concern 규정도 확인됨.

| 3 | **자가 점검표가 칸의 존재·개수만 보고 칸 사이의 모순을 통과시킴** | ④ 역할계약서에서 `사용 모델`에 모델이 있는데 `사용 도구`에 그 모델을 부르는 도구가 없는 모순이 **3판까지 10개 항목을 모두 통과**했음. ③ 패턴/시퀀스·⑤ 지식/도구·⑦ 배포도 같은 종류를 각각 기록함 |

**규격을 재는 방법 자체가 정해져 있지 않았음** — 완료조건 ⓐ가 `4,000 ~ 7,500자(개행 제외)`인데
**재는 명령이 없었음.** 이번에 클로니가 `tr -d '\n'`으로 재어 3종을 `초과`로 판정했고 팀이 분량을
줄였는데, 커넥니가 원인을 찾아냈음 — **파일이 윈도우 줄바꿈(CRLF)이라 `\r`가 1자로 세어져
줄 수만큼 부풀려진 것**임. 다시 재니 **7종 모두 처음부터 규격 안**이었음.
필요 없는 축소를 한 것이며 잘못 판정한 쪽이 클로니임. 재는 명령과 개행 고정을
[_shared/가이드-공통규격.md](_shared/가이드-공통규격.md) 8절 ⓐ에 넣었음.
