# 하이브리드 AI 노드별 강의 스크립트 v2

## 사용 원칙

- 원본 4장 Indexer workflow 이미지와 원본 9장 Retriever workflow 이미지를 그대로 유지함.
- 각 workflow 이미지 다음에 실제 노드 이름을 제목에 넣은 상세 슬라이드를 배치함.
- 원본 이미지의 `check_query`는 현행 `check_search_readiness`의 이전 표기임을 상세 페이지에서 설명함.
- 원본 이미지의 `0.70` 표기는 이미지를 수정하지 않고 유지함. 현행 기본값 `0.86`은 상세 페이지에서 교정함.
- 원본 슬라이드의 핵심 코드 블록은 삭제하지 않고 상세 페이지에 재배치함.
- 원본 코드가 현행 코드와 다르면 원본 코드와 현행 코드의 차이를 같은 페이지에 표시함.

# Indexer 8개 노드

## select_sources | 원문 파일 선택

- 입력: `input_path`, 문서 선택값 `doc`, 상담 구간 `segment`
- 처리: 입력 폴더에서 D1 약관 PDF, D2 혜택 PDF, D3 상담 TXT의 파일명 규칙을 확인하고 요청 범위만 선택함.
- 출력: 절대 경로 목록 `sources`
- 다음 단계/분기: 한 건 이상이면 `extract`로 이동함. 0건이면 `status=error`로 종료함.
- 원본 핵심 코드 유지:

```python
selected = [
    {약관 파일 경로},
    {혜택 파일 경로},
    {상담 파일 경로},
]
```

- 현행 코드 근거:

```python
is_d1 = path.name.startswith("D1_") and path.suffix.lower() == ".pdf"
is_d2 = path.name.startswith("D2_") and path.suffix.lower() == ".pdf"
match = re.fullmatch(r"D3_S(0[1-6])_.*_상담이력_합성\.txt", path.name)
```

- 차이: 원본은 개념 배열을 보여 주고, 현행 코드는 파일명·확장자·상담 구간까지 실제로 검사함.
- 발표 대본: 첫 노드는 검색에 넣을 원문을 고르는 문지기입니다. 약관·혜택·상담 파일의 규칙을 확인하고,
  선택 결과가 없으면 빈 색인을 만들지 않고 바로 오류로 종료합니다.
- 소스: `hybrid-ai-lab/vector/indexer/app/application/graph.py`

## extract | 텍스트와 메타데이터 추출

- 입력: `sources`
- 처리: 파일 SHA-256을 기록하고, PDF는 `pdf_reader`, 상담 TXT는 `parse_consultations`로 처리함.
- 출력: `documents`, 추출 보고 `reports`, 원본 지문 `fingerprints`
- 다음 단계/분기: 정상 처리 후 `apply_profile`로 이동함.
- 원본 핵심 코드 유지:

```python
documents = [
    {Document 객체},
    ...,
]
```

- 현행 코드 근거:

```python
if path.suffix.lower() == ".pdf":
    extracted, report = self.pdf_reader.read(path, remove_margins=True)
else:
    extracted = parse_consultations(self.file_store.read_text(path), path.name)
```

- 차이: 원본의 `Document 객체` 설명은 유지하되, `doc_type`은 별도 `Type` 필드가 아니라
  `Document.metadata["doc_type"]`에 저장됨을 표시함.
- 발표 대본: 서로 다른 원문을 본문과 메타데이터를 가진 같은 Document 구조로 바꾸는 단계입니다.
  PDF와 상담 기록은 정제 규칙이 다르지만, 다음 노드부터는 같은 계약으로 처리할 수 있습니다.
- 소스: `hybrid-ai-lab/vector/indexer/app/application/graph.py`

## extract | PDF 좌표 기반 추출

- 입력: PDF 경로와 `remove_margins=True`
- 처리: 글자와 좌표를 수집하고 반복 머리말·꼬리말, 페이지 번호, 표 영역을 분리함.
- 출력: 페이지별 `Document`와 제거 줄·표·경고를 담은 추출 보고서
- 다음 단계/분기: `extract` 노드 안에서 결과를 모아 `documents`와 `reports`에 추가함.
- 원본 핵심 코드 유지:

```python
for block in page.get_text("dict")["blocks"]:
    for line in block.get("lines", []):
        text = "".join(span["text"] for span in line["spans"]).strip()
        if text:
            result.append((tuple(line["bbox"]), text))
```

- 현행 코드 근거:

```python
return rectangle[3] < height * 0.055 or rectangle[1] > height * 0.95
```

- 차이: 원본 설명의 상단 5%는 현행 코드에서 5.5%임. 반복 문구는 두 페이지 이상 나타날 때 제거함.
- 발표 대본: PDF는 글자만 읽으면 제목·표·꼬리말의 위치를 잃습니다. 그래서 좌표를 함께 읽고,
  반복되는 가장자리 문구는 제거하며 표는 마크다운 구조로 보존합니다.
- 소스: `hybrid-ai-lab/vector/indexer/app/infrastructure/pdf_reader.py`

## extract | 상담 텍스트 분리와 가명화

- 입력: 상담 TXT 본문과 원본 파일명
- 처리: `[상담ID]` 머리글로 상담을 나누고, 식별 정보를 삭제·가명화·일반화함.
- 출력: 상담별 `Document` 목록
- 다음 단계/분기: 필수 식별값이 없거나 개인정보가 남으면 오류임. 통과하면 `apply_profile` 대상이 됨.
- 원본 핵심 코드 유지:

```python
text = PHONE.sub("[삭제]", text)
text = EMAIL.sub("[삭제]", text)
text = PAN.sub("[삭제]", text)
text = MEMBER.sub(lambda match: to_pseudo(match.group(0)), text)
```

- 현행 코드 근거:

```python
metadata.update(
    member_pseudo_id=to_pseudo(member),
    agent_pseudo_id=to_pseudo(intake["상담사명"], "a"),
    age_band=age_band,
)
_assert_pseudonymized(content, metadata)
```

- 차이: 원본 삭제 정규식은 유지함. 현행 코드는 회원과 상담사에 서로 다른 가명 ID를 부여하고,
  결과 전체를 다시 검사하는 단계까지 포함함.
- 발표 대본: 상담 기록은 검색 품질보다 개인정보 보호가 먼저입니다. 삭제와 가명화를 수행한 뒤에도
  전화·이메일·카드번호·원본 회원 ID가 남아 있는지 한 번 더 검사합니다.
- 소스: `hybrid-ai-lab/vector/indexer/app/domain/consultations.py`

## apply_profile | 문서 관리 프로필 적용

- 입력: `documents`, 원문별 `profiles`
- 처리: `source`와 일치하는 프로필을 찾아 담당 부서·공개 등급 등의 고정 메타데이터를 적용함.
- 출력: 프로필이 반영된 `documents`
- 다음 단계/분기: `validate_metadata`로 이동함.
- 원본 핵심 코드 유지:

```text
원문 파일별 담당부서, 공개 등급 등을 각 문서 메타데이터에 Overwrite 함
```

- 현행 코드 근거:

```python
documents = [
    apply_profile(document, profiles.get(document.metadata.get("source", ""), {}))
    for document in state["documents"]
]
```

- 차이: 원본의 `Overwrite` 개념을 유지함. 현행 `apply_profile`은 금지 키 덮어쓰기를 차단하는 검증도 수행함.
- 발표 대본: 추출된 값만 믿지 않고 원문 파일별 관리 정책을 다시 적용합니다. 담당 부서와 공개 등급처럼
  검색 권한에 영향을 주는 값은 이 단계에서 정본으로 맞춥니다.
- 소스: `hybrid-ai-lab/vector/indexer/app/application/graph.py`,
  `hybrid-ai-lab/vector/indexer/app/domain/validation.py`

## validate_metadata | 메타데이터와 개인정보 검증

- 입력: `documents`, 메타데이터 `schema`, `output_path`
- 처리: 본문·공통 필수키·유형별 필수키·허용값·상담 가명화 상태를 검사하고 중간 결과를 저장함.
- 출력: `validation`과 `documents.jsonl`, `manifest.json`, `report.json`, `validation.json`
- 다음 단계/분기: `invalid=0`이면 `chunk`, 한 건 이상이면 오류 종료함.
- 원본 핵심 코드 유지:

```text
- 공통 필수 키/값 존재
- 본문 내용 존재
- 허용하는 값만 존재
- 문서유형 별 필수키/값 존재
- 상담문서 가명화 미비 체크
```

- 현행 코드 근거:

```python
validation = validate_documents(state["documents"], enums)
self.file_store.save_jsonl(output / "documents.jsonl", rows)
self.file_store.save_json(output / "validation.json", validation)
```

- 차이: 원본의 `document.jsonl` 표기는 현행 파일명 `documents.jsonl`로 교정함.
- 발표 대본: 검색 색인에 잘못된 문서가 들어가기 전 마지막 품질 관문입니다. 하나라도 유효하지 않으면
  청킹으로 넘기지 않고 오류와 근거 파일을 남깁니다.
- 소스: `hybrid-ai-lab/vector/indexer/app/application/graph.py`,
  `hybrid-ai-lab/vector/indexer/app/domain/validation.py`

## chunk | 문서 유형별 의미 단위 청킹

- 입력: 검증된 `documents`, 청크 크기·겹침·대화 턴 설정
- 처리: D1은 조항, D2는 카드·혜택·표, D3는 상담별 대화 턴 단위로 준비한 뒤 필요한 크기로 나눔.
- 출력: `chunks`, `reviews`, `exceptions`, `skipped`, `input_units`
- 다음 단계/분기: 일반 실행은 `embed`로 이동함. `dry_run` 또는 오류이면 종료함.
- 원본 핵심 코드 유지:

```text
- 약관, 혜택 문서: 청킹 사이즈만큼 나누고 Overlap 사이즈만큼 중복
- 상담문서: 지정된 대화 턴 수만큼 문서 조각을 나눔
```

- 현행 코드 근거:

```python
if unit["key"] == "D3":
    created = chunk_by_turn(unit["text"], unit["meta"], turns_per_chunk=turns_per_chunk)
else:
    created = chunk_by_clause(unit["text"], unit["meta"], max_chars=max_chars)
```

- 차이: 원본의 고정 길이 설명을 유지하되, 현행은 먼저 조항·혜택·대화 턴의 의미 경계를 보존함.
- 발표 대본: 청킹은 글자를 기계적으로 자르는 일이 아닙니다. 약관 조항, 카드 혜택, 상담 대화라는
  의미 단위를 먼저 지킨 뒤 너무 긴 경우에만 다시 나눕니다.
- 소스: `hybrid-ai-lab/vector/indexer/app/domain/chunking.py`,
  `hybrid-ai-lab/vector/indexer/app/application/graph.py`

## embed | 변경된 청크만 임베딩

- 입력: `chunks`, 이전 `index_manifest.json`, 임베딩 서명, 청킹 설정, `full_reindex`
- 처리: 본문·메타데이터 해시를 비교해 변경 청크를 고르고, 배치 단위로 정규화 임베딩을 생성함.
- 출력: `pending_ids`, `skipped_ids`, 벡터 파일 경로, 실패 목록
- 다음 단계/분기: `upsert`로 이동함. 일시 오류는 최대 3회 시도함.
- 원본 핵심 코드 유지:

```python
def embed(self, texts, *, kind="passage"):
    model = self._load()
    values = model.encode(
        texts,
        batch_size=self.batch_size,
        normalize_embeddings=True,
    )
    return values.tolist()
```

- 현행 코드 근거:

```python
if prior.get("text_sha256") == text_digest \
        and prior.get("metadata_sha256") == metadata_digest:
    skipped_ids.append(chunk_id)
else:
    pending_ids.append(chunk_id)
```

- 차이: 원본의 배치 임베딩 코드를 유지함. 현행은 본문뿐 아니라 메타데이터가 바뀌어도 재임베딩함.
- 발표 대본: 매번 전체 문서를 다시 계산하지 않고 바뀐 청크만 찾습니다. 본문과 메타데이터 중
  하나라도 달라지면 검색 내용이나 권한이 달라질 수 있으므로 새 벡터를 만듭니다.
- 소스: `hybrid-ai-lab/vector/indexer/app/infrastructure/embedder.py`,
  `hybrid-ai-lab/vector/indexer/app/application/graph.py`

## upsert | 벡터 DB 저장과 갱신

- 입력: `pending_ids`, 생성 벡터, 청크 본문, 메타데이터
- 처리: 메타데이터를 저장 가능한 값으로 정리하고 Chroma 컬렉션에 ID 기준으로 추가·갱신함.
- 출력: `ok_ids`, `failed`, 저장 전 건수 `count_before`
- 다음 단계/분기: `finalize_index`로 이동함. 일시 오류는 최대 3회 시도함.
- 원본 핵심 코드 유지:

```python
self._collection.upsert(
    ids=ids,
    documents=texts,
    embeddings=embeddings,
    metadatas=clean,
)
```

- 현행 코드 근거:

```python
metadata_with_id = {**metadata, "chunk_id": chunk_id}
clean_metadata = sanitize_metadata(metadata_with_id)
```

- 차이: 원본 코드와 현행 저장 계약이 같음. 현행은 기존 ID 목록을 고려해 예상 최종 건수도 계산함.
- 발표 대본: `upsert`는 같은 ID가 없으면 추가하고 있으면 갱신하는 저장 방식입니다. 본문·벡터·메타데이터를
  한 청크 ID로 묶어 저장하고, 성공과 실패를 따로 기록합니다.
- 소스: `hybrid-ai-lab/vector/indexer/app/infrastructure/chroma_store.py`,
  `hybrid-ai-lab/vector/indexer/app/application/graph.py`

## finalize_index | 벡터 검증과 BM25 세대 발행

- 입력: 저장 성공·실패 목록, 저장 전 건수, 벡터 DB 설명, 검증 청크
- 처리: 실제 건수·예상 건수·임베딩 차원을 확인하고 manifest와 BM25S 세대를 발행함.
- 출력: `count_after`, `accounting_ok`, `embedding_dimension`, `index_manifest.json`, 활성 BM25 세대
- 다음 단계/분기: 건수 불일치는 오류임. 일부 실패는 종료 코드 3, 검토 대상은 2, 완전 성공은 0으로 종료함.
- 원본 핵심 코드 유지:

```text
- 인덱싱 대상 문서 수와 벡터 DB의 실제 건수 비교
- BM25S 새 버전 생성
- 카드명 자동 사전 구성
- OOV 후보 저장
- 활성 인덱스 버전 정보 생성
```

- 현행 코드 근거:

```python
count_after = int(description.get("count", self.vector_store.count()))
accounting_ok = count_after == expected
search_index = publish_search_index(...)
```

- 차이: 원본 개념을 유지함. 현행은 모든 세대 파일을 먼저 완성하고 `active_index.json`을 마지막에 교체함.
- 발표 대본: 마지막 노드는 저장이 끝났다고 바로 성공 처리하지 않습니다. 벡터 건수와 임베딩 정보를 확인하고,
  키워드 검색 색인까지 완성된 새 세대로 안전하게 발행합니다.
- 소스: `hybrid-ai-lab/vector/indexer/app/application/graph.py`,
  `hybrid-ai-lab/vector/indexer/app/infrastructure/lexical_index.py`

# Retriever 13개 노드

## check_search_readiness | 검색 준비 상태 확인

- 원본 별칭: 원본 workflow 이미지의 `check_query`가 현행 이 노드에 해당함.
- 입력: `query`, `top_k`, `role`, `mode`, `dry_run`
- 처리: 질문·결과 수·역할·모드를 검사하고, 벡터 컬렉션 건수·임베딩 서명·차원을 확인함.
- 출력: `index_info`, `validation_errors`, 필요 시 `status`와 `exit_code`

## assess_transform_gate | 질문 변환 검토 관문

- 입력: `transform_mode`, 원 질문 벡터 Top1 점수, `TRANSFORM_GATE_THRESHOLD`
- 처리: 캐시나 LLM을 부르지 않고 질문 변환 검토가 필요한지만 점수로 판정함.
- 출력: `transform_review_required`, `route_action`, `transformed_queries`
- 다음 단계/분기: `off` 또는 점수 0.86 이상은 변환 없이 원 질문 경로로 이동함.
  `auto`에서 0.86 미만이거나 결과가 없으면 `plan_query_transform`으로 이동함.
- 원본 핵심 코드 유지:

```python
if top_vector_score is not None and top_vector_score >= gate_threshold:
    return {
        "route_action": "gate_pass",
        "transform_review_required": False,
        "transformed_queries": [],
    }
return {"transform_review_required": True}
```

- 현행 코드 근거:

```python
"TRANSFORM_MODE": "off"
"TRANSFORM_GATE_THRESHOLD": 0.86
```

- 차이: 원본 workflow 이미지의 `Score < 0.7` 표기는 이미지 안에서 유지함. 상세 설명에서는 현행 기본값
  `0.86`과 기본 모드 `off`를 명시하며, 0.86 미만은 변환 확정이 아니라 검토 시작 조건이라고 설명함.
- 발표 대본: 질문 변환 기본값은 꺼짐이며, 자동 모드일 때만 0.86 관문을 봅니다. 낮은 점수는
  질문을 바로 바꾸라는 뜻이 아니라 라우터에게 유지·확인·변환 중 무엇이 좋은지 물어보라는 뜻입니다.

- 원본 핵심 코드 유지:


```python
    valid_count = len(queries) == 3
elif technique == "decomposition":
```

## fuse_scores | 벡터와 BM25 점수 융합

- 입력: `vector_hits`, BM25 점수, 전체 BM25 청크, 0.6·0.4 가중치
- 처리: 두 후보의 ID 합집합을 만들고 누락 점수를 0으로 포함해 각각 0 ~ 1로 정규화한 뒤 가중합함.
- 출력: 융합 후보 `candidates`와 `baseline_hits`
- 다음 단계/분기: `complete_original_results`로 이동함.
- 원본 핵심 코드 유지:

```python
normalized_vector = normalize(vector_by_id, candidate_ids)
normalized_bm25 = normalize(bm25_scores, candidate_ids)
score = weight_bm25 * normalized_bm25[chunk_id] \
    + weight_vector * normalized_vector[chunk_id]
```

- 현행 코드 근거:

```python
candidate_ids = set(vector_by_id) | bm25_candidate_ids
```

- 차이: 원본 가중합 코드는 현행과 같음. 상세 페이지에는 한쪽에 없는 후보도 0을 넣어 정규화함을 추가함.
- 발표 대본: 두 검색 점수는 단위가 달라 그대로 더할 수 없습니다. 같은 후보 집합에서 각 점수를
  0부터 1로 맞춘 뒤 벡터 0.6, BM25 0.4로 합칩니다.

## merge_queries | 원 질문과 변환 질문 RRF 병합

- 입력: `baseline_hits`, `transformed_hit_groups`, 변환 기법, RRF 설정, `top_k`
- 처리: 각 그룹의 순위에 가중치를 적용해 청크 ID별 RRF 점수를 누적함.
- 출력: 최종 `hits`, `merge_weights`, `decomposition_coverage_applied`
- 다음 단계/분기: 정상은 답변 관문 뒤 `build_prompt` 또는 종료임. 리랭킹 실패 시 대체 경로로도 사용함.
- 원본 핵심 코드 유지:

```python
for position, hit in enumerate(hits, start=1):
    item = merged.setdefault(
        hit.chunk_id,
        {"hit": hit, "rrf_score": 0.0, "source_ranks": {}},
    )
    item["rrf_score"] += weight / (rrf_k + position)
```

- 현행 코드 근거:

```python
weight = decomposition_original_weight \
    if technique == "decomposition" else original_weight
each_weight = (1.0 - weight) / len(transformed_hit_groups)
```

- 차이: 원본 코드는 유지함. 현행 RRF 상수는 60, 일반 원 질문 가중치는 0.5, decomposition은 0.1임.
- 발표 대본: 질문별 검색 점수의 크기 대신 각 그룹에서의 순위를 합칩니다. 같은 청크가 여러 질문에서
  높은 순위에 등장할수록 RRF 점수가 누적되어 최종 순위가 올라갑니다.
- 소스: `hybrid-ai-lab/vector/retriever/app/domain/query_transform.py`,
  `hybrid-ai-lab/vector/retriever/app/application/graph.py`

## rerank | 질문별 Cross-Encoder 재정렬

- 입력: 원 질문·변환 질문과 각 후보군, 변환 기법, `top_k`
- 처리: 각 질문과 해당 후보 본문을 Cross-Encoder로 다시 점수화하고 그룹 내부 순위를 재정렬함.
- 출력: 최종 `hits`, `rerank_failed`, 필요 시 `warnings`
- 다음 단계/분기: 성공은 답변 관문 뒤 `build_prompt` 또는 종료임. 변환 검색 리랭킹 실패는 `merge_queries`로 대체함.
- 원본 핵심 코드 유지:

```python
raw = model.predict(
    [(query, text) for text in texts],
    activation_fn=torch.nn.Sigmoid(),
    show_progress_bar=False,
)
```

- 현행 코드 근거:

```python
scores = reranker.score(query, [hit.text for hit in hits]) if hits else []
updated.sort(key=lambda hit: (-float(hit.rerank_score), -hit.score, hit.chunk_id))
```

- 차이: 원본 Cross-Encoder 코드를 유지함. 현행은 모델 실패 시 전체 검색을 실패시키지 않고 대체 결과를 사용함.
- 발표 대본: 벡터와 BM25는 후보를 넓게 찾고, 리랭커는 질문과 각 문서를 함께 읽어 순서를 다시 정합니다.
  모델이 실패해도 직전 결과나 RRF 병합으로 돌아가므로 검색 전체가 중단되지 않습니다.
- 소스: `hybrid-ai-lab/vector/retriever/app/infrastructure/reranker.py`,
  `hybrid-ai-lab/vector/retriever/app/application/graph.py`

## rerank | 일반 변환 질문의 최종 병합

- 입력: 원 질문과 rewrite·multi·HyDE·step-back 질문의 리랭킹 결과
- 처리: 각 그룹의 리랭커 점수 크기를 직접 더하지 않고, 새로 정해진 순위를 가중 RRF로 합침.
- 출력: RRF 순으로 정렬된 상위 `top_n` hits
- 다음 단계/분기: `rerank` 노드의 성공 결과로 답변 관문에 전달함.
- 원본 핵심 코드 유지:

```text
각 후보군 내부 순위 확정
→ 그룹별 가중치와 순위로 RRF 계산
→ chunk_id 기준 누적
→ 상위 top_n 반환
```

- 현행 코드 근거:

```python
return [
    item["hit"]
    for item in weighted_rrf(reranked_lists, rrf_k=rrf_k)[:top_n]
]
```

- 차이: 원본 설명과 현행 계약이 같음. 리랭커의 절대 점수보다 질문별 순위를 최종 병합에 사용함.
- 발표 대본: 각 질문의 리랭커 점수는 질문마다 분포가 다를 수 있습니다. 그래서 일반 변환에서는
  점수 자체를 더하지 않고 그룹 내부에서 새로 정한 순위를 RRF로 합칩니다.
- 소스: `hybrid-ai-lab/vector/retriever/app/domain/query_transform.py`

## rerank | decomposition 하위 질문 병합

- 입력: 원 질문 후보와 하위 질문별 리랭킹 후보, 하위 질문당 상위 3개
- 처리: 같은 청크의 최고 하위 질문 점수를 고르고 원 질문 점수를 보조 신호로 가중합함.
- 출력: 결합 점수 순 상위 `top_n` hits
- 다음 단계/분기: `rerank` 노드의 성공 결과로 답변 관문에 전달함.
- 원본 핵심 코드 유지:

```text
동일 청크는 하위 질문 리랭킹 점수 중 최댓값 선택
→ 하위 질문 점수 + 원 질문 점수를 가중 합산
→ 상위 top_n 반환
```

- 현행 코드 근거:

```python
merge_score = (
    0.9 * transformed_score
    + 0.1 * original_score
)
```

- 차이: 원본의 모호한 `각 변환 질문 점수 × 기여 가중치`를 현행 공식
  `0.9 × 최고 하위 질문 점수 + 0.1 × 원 질문 점수`로 구체화함.
- 발표 대본: 복합 질문은 각 하위 질문의 상위 후보가 사라지지 않게 먼저 확보합니다. 같은 청크가 여러
  하위 질문에 나오면 가장 높은 하위 점수를 중심으로 보고 원 질문 점수는 10%만 보조합니다.
- 소스: `hybrid-ai-lab/vector/retriever/app/domain/query_transform.py`

## build_prompt | 검색 근거 프롬프트 구성

- 입력: 최종 `hits`, 원 질문, `repair_hints`, `prompt_only`
- 처리: 시스템 지시와 검색 근거·사용자 질문·수정 지침을 분리하고 XML 태그로 데이터를 격리함.
- 출력: `system_prompt`, `user_prompt`, 호환용 `prompt`
- 다음 단계/분기: 일반 실행은 `generate_answer`, `prompt_only`는 종료함.
- 원본 핵심 코드 유지:

```python
for index, hit in enumerate(state.get("hits", []), start=1):
    blocks.append(
        f'<검색결과 순번="{index}">\n'
        f"<청크ID>{escape(str(hit.chunk_id))}</청크ID>\n"
        f"<위치>{escape(str(hit.location))}</위치>\n"
        f"<본문>{escape(str(hit.text))}</본문>\n"
        "</검색결과>"
    )
```

- 현행 코드 근거:

```xml
<검색결과목록>{evidence}</검색결과목록>
<사용자질문>{query}</사용자질문>
<수정지침>{hints}</수정지침>
```

- 차이: 원본의 `<검색결과 목록>` 표기를 현행 태그 `<검색결과목록>`으로 맞춤.
- 발표 대본: 모델에게 지시하는 문장과 검색에서 가져온 데이터를 명확히 분리합니다. 검색 근거마다
  순번·청크 ID·문서 유형·위치·본문을 넣어 다음 검증 단계가 원문을 다시 찾을 수 있게 합니다.
- 소스: `hybrid-ai-lab/vector/retriever/app/application/graph.py`

## generate_answer | 구조화 답변 생성

- 입력: `system_prompt`, `user_prompt`, 남은 LLM 호출 예산
- 처리: LLM을 구조화 출력 스키마로 실행해 결론·주의사항·근거 참조와 인용을 생성함.
- 출력: `raw_answer`, `llm_calls`, 실행 상태
- 다음 단계/분기: 생성 성공은 `verify_evidence`, 예산 소진은 `halted_by_limit`로 종료함.
- 원본 핵심 코드 유지:

```python
runnable = model.with_structured_output(schema, **kwargs)
output = runnable.invoke([
    ("system", system),
    ("human", user),
])
```

- 현행 코드 근거:

```text
AnswerDraft = conclusion + caution + evidence[{ref, quote}]
```

- 차이: 원본 구조화 호출 코드는 현행과 같음. API 요청 기본 예산은 2회, CLI 실행 기본 예산은 8회임.
- 발표 대본: 답변을 자유 형식으로 받지 않고 검증 가능한 구조로 받습니다. 결론과 주의사항뿐 아니라
  어떤 검색 결과를 참조했고 어떤 원문을 인용했는지 함께 생성합니다.
- 소스: `hybrid-ai-lab/vector/retriever/app/infrastructure/llm_client.py`,
  `hybrid-ai-lab/vector/retriever/app/application/state.py`,
  `hybrid-ai-lab/vector/retriever/app/application/graph.py`

## verify_evidence | 답변의 참조·인용·위치 검증

- 입력: `raw_answer`, 최종 `hits`, 현재 `repair_count`
- 처리: 답변 스키마, `ref` 범위, 인용문의 원문 포함, 원문 위치 존재를 검사하고 Evidence를 만듦.
- 출력: 검증된 `answer`, `repair_hints`, `repair_count`, 상태
- 다음 단계/분기: 자동 검증 성공은 종료함. 실패하고 한도가 남으면 `build_prompt`, 한도 소진은 종료함.
- 원본 핵심 코드 유지:

```text
- 인용문이 실제 검색 결과 청크에 존재하는지 검사
- 참조하는 원문 위치가 검색 결과에 존재하는지 검사
- 형식 오류·인용 오류·위치 오류를 검증 결과로 생성
```

- 현행 코드 근거:

```python
if not 1 <= ref <= len(hits):
    invalid_refs.append(...)
quote_ok = isinstance(quote, str) and verify_quote(quote, hit.text)
location_ok = bool(hit.location)
```

- 차이: 원본 제목의 오타 `vefify_evidence`를 실제 노드명 `verify_evidence`로 교정함.
- 발표 대본: 모델의 답이 자연스러운지가 아니라 제시한 근거를 실제로 추적할 수 있는지 검사합니다.
  참조 번호, 원문 인용, 위치 중 하나라도 맞지 않으면 실패 이유를 구체적인 수정 지침으로 바꿉니다.
- 소스: `hybrid-ai-lab/vector/retriever/app/domain/scoring.py`,
  `hybrid-ai-lab/vector/retriever/app/application/graph.py`

## verify_evidence | 근거 수정 루프와 실행 한도

- 입력: 검증 오류별 `repair_hints`, 누적 `repair_count`, LLM 호출 예산
- 처리: 수정 지침을 다음 `build_prompt`의 `<수정지침>`에 넣어 답변을 다시 생성함.
- 출력: 수정된 답변 또는 `halted_by_limit`
- 다음 단계/분기: `MAX_REPAIRS=2` 안에서는 `build_prompt`로 돌아감. 이후에는 반복을 멈춤.
- 원본 핵심 코드 유지:

```text
검증 실패 시 다시 build_prompt로 돌아감
검증 실패 시 최대 재시도 수 만큼 반복
```

- 현행 코드 근거:

```python
max_repairs = int(_setting(resources, "MAX_REPAIRS", 2))
if state.get("repair_count", 0) >= max_repairs:
    update.update(status="halted_by_limit", exit_code=0)
```

- 차이: 원본의 `최대 재시도 수`를 현행 기본값 2로 구체화함. API LLM 예산 2회와 CLI 예산 8회는
  수정 횟수와 별도 제한이며, 먼저 닿는 제한에서 멈춤.
- 발표 대본: 실패한 이유를 버리지 않고 다음 프롬프트의 수정 지침으로 되돌립니다. 다만 무한 반복하지 않고
  수정 최대 2회와 실행 환경별 LLM 예산 안에서만 다시 생성합니다.
- 소스: `hybrid-ai-lab/vector/retriever/app/application/graph.py`,
  `hybrid-ai-lab/vector/retriever/app/settings.py`

# 공통 발표 주의사항

- 원본 workflow 이미지는 설계 이력을 보여 주는 자료로 그대로 유지함.
- 원본 이미지의 `check_query`를 현행 노드로 오해하지 않도록 `check_search_readiness의 이전 표기`라고 말함.
- 원본 이미지의 `0.70`은 그대로 보이지만, 현행 기본 질문 변환 관문은 `0.86`임을 상세 슬라이드에서 바로잡음.
- `0.86 미만`은 질문 변환 확정이 아니라 라우터 검토 시작 조건임.
- 질문 변환은 기본 `off`이며 `auto`일 때만 관문과 라우터가 동작함.
- 답변 관문 `0.62`는 최종 1위의 원 `vector_score`를 사용함. 융합 점수나 리랭커 점수가 아님.
- 핵심 코드 블록은 원본 슬라이드의 코드를 먼저 보여 주고, 오른쪽에 현행 코드 또는 차이를 배치함.
- 상담 예시에는 실제 개인정보를 사용하지 않고 `[삭제]`, `m_해시`, `a_해시`, `30대`만 사용함.
