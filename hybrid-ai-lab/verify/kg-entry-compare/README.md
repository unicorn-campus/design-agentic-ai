# 그래프 입구 비교: 청크 입구 vs 엔티티 입구

GraphRAG v0 활성 세대에서 질문으로 그래프에 들어가는 두 길을 같은 질문 20개로 비교한 실험.  
K6 노드 설명 임베딩(엔티티 벡터 인덱스)이 검색엔진 인덱스와 따로 필요한지 판단하려는 것임.

- 청크 입구: 검색엔진(BM25와 kNN 순위를 RRF로 합침) 상위 k개 청크 → 같은 chunk_id의 청크 노드  
  → FROM_CHUNK로 그 청크에서 나온 엔티티 전부가 후보
- 엔티티 입구: 질문 임베딩으로 노드 벡터 인덱스 `kg_entity_embedding` 상위 k개 엔티티가 후보
- 맞춤 기준: 질문마다 정한 정답 엔티티(`questions.json`의 targets)가 후보 안에 있으면 맞춤

## 파일

| 파일 | 내용 |
|------|------|
| `questions.json` | 질문 20개(약관 11, 혜택 안내 5, 상담 기록 4)와 정답 엔티티(라벨, 속성, 들어 있는 글) |
| `compare.py` | 두 입구로 후보를 뽑아 맞춤 여부와 후보 수를 잼. v0 활성 세대를 읽기만 함 |
| `result.json` | 질문별 결과와 요약 |

## 실행

v0의 Neo4j와 OpenSearch가 켜져 있고 v0 활성 세대가 있어야 함(v0 README 참조).

```bash
NEO4J_PASSWORD=비밀번호 ../../indexer/graphrag/v0/.venv/Scripts/python.exe compare.py
```

## 관찰

- 엔티티 입구는 적은 후보로 정답을 짚음. 상위 5개(후보 5)가 청크 상위 1개(후보 11.4)보다 4개 더 맞춤
- 청크 입구도 2개까지 넓히면 17개를 맞춰 엔티티 입구보다 많음. 다만 후보가 평균 20개라 LLM에 넘길 양이 4배임
- 청크 입구가 놓친 까닭
  - 말투 차이: 구어체 질문(T01, T02, T05, T07)에서 상담 청크(대화체)가 약관 청크보다 위로 올라옴
  - 같은 문서의 다른 청크: 약관과 혜택 안내는 청크가 여럿이라, 같은 문서라도 정답이 없는 청크가 1위가 됨(T11, B05)
- 엔티티 입구가 놓친 까닭
  - 맥락이 빠진 설명 글: C04의 정답 「주문 내역 화면으로 대조」에는 「영수증」이란 말이 없음.  
    영수증 이야기는 다른 제안 노드(거절된 제안)의 이유에 있어 그 노드가 1위, 정답은 34위
  - 주어 없는 짧은 처리 문장: T05 「실패 사유와 재출금 예정일을 안내」(15위), T07 「신규 승인 기능을 정지」(11위)
- 둘을 합치면 서로 놓친 것을 메움. 청크 2개 + 엔티티 5개가 19개로 가장 많음(T05만 둘 다 놓침)

## 재실행 (2026-10-23, 세대 gen-sample-003-06e0ccea)

v0의 그래프 구조를 바꾼 뒤 다시 잼. 청크 노드가 검색엔진 청크와 1대1이 되어(노드의 chunk_id = 검색엔진 chunk_id)  
청크 입구 조회가 `any(p IN c.parent_chunk_ids WHERE p IN $cids)`에서 `c.chunk_id IN $cids`로 바뀜.  
같은 표본으로 전체 재색인(sample-003)과 증분 색인(sample-004)을 다시 돌린 세대임. 청크 9개, 엔티티 83개.

| 입구 | 맞춤(이전) | 맞춤(재실행) | 평균 후보 엔티티 수(재실행) |
|------|------|------|------|
| 청크 입구 상위 1개 | 11 / 20 | 9 / 20 | 9.8 |
| 청크 입구 상위 2개 | 17 / 20 | 16 / 20 | 20.5 |
| 엔티티 입구 상위 3개 | 14 / 20 | 15 / 20 | 3 |
| 엔티티 입구 상위 5개 | 15 / 20 | 16 / 20 | 5 |
| 청크 상위 1개 + 엔티티 상위 5개 | 16 / 20 | 16 / 20 | 최대 14.8 |
| 청크 상위 2개 + 엔티티 상위 5개 | 19 / 20 | 18 / 20 | 최대 25.5 |

- 숫자가 바뀐 까닭은 구조가 아니라 검색엔진 순위와 재추출임
  - 청크 입구 상위 1개에서 빠진 T08, B04: 검색엔진 1위 청크가 상담 청크로 바뀜(옛 인덱스에서 T08은 약관 청크, B04는 혜택 안내 청크가 1위)
  - 1위 청크가 같은 질문(T05, T07, B03)은 옛 구조와 새 구조의 후보 엔티티 수가 같음(2, 2, 33). 청크에서 엔티티로 가는 길은 그대로임
  - 엔티티 입구 차이(C04 맞춤, T05와 T07과 B03 순위 밖)는 전체 재색인 때 LLM이 2개 단위를, 증분 색인 때 1개 단위를 다시 추출한 영향임
- 두 청크에 걸친 조항(제16조, 제16조의2)의 엔티티는 두 청크 노드에 모두 이어짐. 어느 청크로 들어와도 후보가 됨

## 판단

- 「K6이 필요한가」에 대한 답은 「찾는 범위」보다 「후보를 줄이는 정확도」에 있음.  
  청크 입구만으로도 후보를 넓히면 대부분 닿지만, LLM에 넘길 엔티티가 많아짐
- 두 입구를 함께 쓰면 맞춤이 가장 높음. 검색기는 청크 입구를 기본으로, 엔티티 입구를 보조로 함께 쓰는 쪽을 권함
- 엔티티 설명 글이 짧고 맥락이 없어 놓치는 경우가 있음. 설명 글에 이웃 노드 정보를 붙이는 개선 여지가 있음(미시험)

## 한계

- 표본이 작음: 청크 9개, 엔티티 82개. 전체 218개 청크에서는 두 입구 모두 더 어려워지므로 숫자를 그대로 옮길 수 없음
- 질문 20개와 정답은 클로니가 그래프의 엔티티를 보고 바꿔 말해 만듦. 엔티티 하나를 겨냥한 질문이라 엔티티 입구에 유리할 수 있음
- 「맞춤」은 정답이 후보 안에 있다는 뜻일 뿐, LLM이 후보에서 정답을 골라 답했는지는 재지 않음
- 합친 경우의 후보 수는 두 후보를 더한 최대값임(겹치는 엔티티를 빼지 않음)
