# Neo4j 전문 검색으로 기존 BM25를 대신할 수 있나 검증

지금 쓰는 BM25(Kiwi 형태소 분석 + 카드명 별칭 사전, `bm25s`)를 Neo4j 전문 검색 인덱스(fulltext index)로  
같은 품질로 재현할 수 있는지 평가 질문 42개의 순위로 견준 결과임.  
"벡터 DB를 Chroma에서 Neo4j 하나로 옮길지" 결정의 근거 자료로 쓰임.

기존 `indexer/`, `retriever/` 코드와 색인 파일은 읽기만 했고 고치지 않음.

## 한 줄 판정

**보정하면 됨.** Neo4j 전문 검색만으로는 기존 순위를 그대로 못 만듦(상위 10 겹침 0.952).  
다만 Neo4j가 돌려준 상위 50건이 기준 상위 10을 100% 담으므로, 후보만 Neo4j에서 받고  
앱이 기존 BM25 점수로 다시 줄 세우면 순위가 42개 질문 전부에서 완전히 같아짐.

주의: 그 보정안은 기존 BM25 색인을 앱에 그대로 둬야 돌아감. 즉 "BM25까지 Neo4j 하나로 합치기"는  
이 결과만으로는 아직 아님(아래 「판정의 뜻」 참조).

## 구성

## 실행

```bash
docker compose -f neo4j/compose.yml up -d
```

- `hybrid-ai-lab` 폴더에서 실행함. 실습 공용 컨테이너 `neo4j`(bolt 7687)를 씀. 처음이면 `neo4j/README.md`대로 `.env`를 만듦
- `run_compare.py`와 `tools/diagnose.py`는 접속값을 환경변수로만 받음. 비밀번호는 `neo4j/.env`의 값을 넘김

```bash
export NEO4J_URI=bolt://localhost:7687 NEO4J_USER=neo4j NEO4J_PASSWORD=$(grep '^NEO4J_PASSWORD=' neo4j/.env | cut -d= -f2-)
```

```bash
# 기준 뽑기 — Kiwi, bm25s, torch가 있는 기존 검색기 가상환경에서 실행
retriever/vector-retriever/.venv/Scripts/python verify/neo4j-bm25-compare/tools/export_baseline.py
```

```bash
# 비교와 원인 분석 — neo4j 드라이버가 있는 검증 전용 가상환경에서 실행
cd verify/neo4j-bm25-compare
../neo4j-vector-search/.venv/Scripts/python run_compare.py
```

### 답이 없어야 하는 질문(12개)의 점수 분포

떨어짐 폭 = (상위 1 점수 − 상위 5 점수) / 상위 1 점수. 점수 크기에 휘둘리지 않는 분포 지표임.

| 후보 | 답 있는 질문 | 답 없어야 할 질문 |
|------|---:|---:|
| 기준 | 0.337 | 0.247 |
| A | **0.336** | **0.244** |
| B | 0.383 | 0.312 |
| C | 0.393 | 0.369 |

A는 기준과 사실상 같은 분포를 유지함. B와 C는 분포가 눈에 띄게 달라짐.

다만 **기준부터가** 답이 없어야 할 질문에서 BM25 점수만으로 걸러 내지 못함 — 42개 질문 전부가  
BM25 적중 건수 0이 아니며(평균 208.5건), 답 없어야 할 질문도 떨어짐 폭이 오히려 더 완만함.  
"모른다"고 답하는 일은 BM25 점수가 아니라 뒷단 채점이 맡는다는 뜻임.

## 차이의 원인

### 1. 점수 공식은 같고 k1 값만 다름

기준 `bm25s`의 `method="lucene"`은 Lucene `BM25Similarity`와 **식이 완전히 같음**.

```
idf = ln(1 + (N - df + 0.5) / (df + 0.5))
tfc = tf / (k1 * ((1 - b) + b * dl / avgdl) + tf)
점수 = idf * tfc
```

파이썬으로 이 식을 다시 적어 설정을 하나씩 Lucene 쪽으로 바꿔 가며 확인함.

| 변형 | 기준과 상위 10 겹침 | A와 상위 10 겹침 | A와 상위 1 일치 | A와 점수 최대 차이 |
|------|---:|---:|---:|---:|
| V1. k1 = 1.5, 문서 길이 그대로 | **1.000** | 0.952 | 0.952 | 16.4% |
| V2. k1 = 1.2, 문서 길이 그대로 | 0.969 | 0.971 | 0.952 | 3.8% |
| V3. k1 = 1.2, 문서 길이 Lucene 뭉갬 | 0.955 | 0.971 | **0.976** | **3.6%** |

- V1이 기준을 **정확히** 재현함(1.000) → 식이 같다는 증거이며, 뒤 변형의 차이는 설정 탓임
- k1만 1.2로 바꿔도 점수 차이가 16.4% → 3.8%로 줄고, 길이 뭉갬까지 넣으면 상위 1 일치가 0.976까지 오름
- Neo4j 2026.09.0은 **k1을 바꿀 수 없음**. 실제로 넣어 보면 거부함:  
  `Invalid index config key 'fulltext.bm25.k1', it was not recognized as an index setting.`

### 2. Lucene은 문서 길이를 1바이트로 뭉개 저장함

Lucene은 점수 계산에 쓰는 문서 길이를 `SmallFloat.intToByte4`로 줄여 담아 값이 뭉개짐.  
청크 218건 중 **203건**의 길이가 달라지고 평균 **5.05%** 어긋남.

| 실제 토큰 수 | Lucene이 쓰는 값 |
|---:|---:|
| 429 | 416 |
| 414 | 384 |
| 402 | 384 |
| 384 | 384 |

### 3. 하이브리드가 더 크게 흔들리는 까닭

가중합(`weighted_hybrid`)은 최소-최대 정규화를 거쳐 **점수 값**을 쓰므로, BM25 순서가 같아도  
점수 간격이 달라지면 벡터 점수와 합쳐진 뒤 자리가 바뀜.  
그래서 BM25 단독 상위 10 겹침은 0.952인데 하이브리드 상위 10 순서까지 같음은 18/42로 떨어짐.

### 4. B와 C는 낱말을 쪼개는 방식 자체가 다름 — 탐침 4건

짧은 글을 넣은 탐침 노드로 같은 질문이 잡히는지 확인함(`tools/diagnose.py`).

| 탐침 | 문서 | 질문 | Kiwi(기준) | cjk | standard |
|------|------|------|---|---|---|
| 조사 붙음 | `연회비를 면제합니다.` | `연회비` | 잡음 | 잡음 | **못 잡음** |
| 복합명사 | `직전 12개월 이용금액이 3,000,000원 이상` | `이용금액` | 잡음 | 잡음 | **못 잡음** |
| 숫자 쉼표 | `3,000,000원 이상이면 면제` | `3000000` | 잡음 | **못 잡음** | **못 잡음** |
| 날짜 표기 | `2026-02 명세서` | `2026년 2월` | 잡음 | **못 잡음** | **못 잡음** |

- `standard`는 한국어를 조사까지 붙은 덩어리로 끊어 `연회비를`과 `연회비`가 다른 낱말이 됨.  
  그래서 적중 문서가 평균 130.5건으로 기준(208.5건)보다 크게 적음
- `cjk`는 두 글자씩 끊어(바이그램) 조사 문제는 넘기지만, 기준의 표기 통일(숫자 쉼표 제거, 날짜 ISO 통일)과  
  카드명 별칭 189개는 전혀 재현하지 못함
- 즉 B와 C가 못 따라오는 까닭은 점수 공식이 아니라 **색인 전처리**임. 기준 토큰화는 Kiwi 형태소 분석에  
  표기 통일, 카드명 사전 64개, 별칭 189개를 얹은 것이라 분석기 교체로는 대신할 수 없음

## 보정안의 효과

A가 돌려준 상위 50건만 받아 앱이 기준 BM25 점수로 다시 줄 세움.

- BM25 상위 10: **42/42 완전 일치**
- 하이브리드 상위 10: **42/42 완전 일치**
- 즉 Neo4j 전문 검색(후보 A)의 상위 50건이 기준 상위 10을 **빠짐없이** 담음

## 판정의 뜻

| 쓰려는 방식 | 판정 | 근거 |
|------------|------|------|
| 후보 A로 BM25를 통째로 Neo4j에 넘김 | **순위가 조금 달라짐** | 상위 10 겹침 0.952, 상위 1 40/42, 하이브리드 상위 5 구성 38/42 |
| Neo4j는 후보만 주고 앱이 다시 채점 | **완전히 같음** | 42/42. 단 기존 BM25 색인을 앱에 그대로 둬야 함 |
| 분석기만 바꿔 본문을 그대로 색인(B, C) | **쓰면 안 됨** | 상위 10 겹침 0.48 / 0.41, 상위 1 20/42와 14/42 |

**권하는 방식**

1. 벡터는 Neo4j로 옮겨도 됨(`verify/neo4j-vector-search`에서 60/60 일치로 이미 확인된 사항임)
2. BM25는 후보 A 방식(Kiwi 토큰을 미리 넣고 `whitespace` 분석기)으로만 옮길 수 있음.  
   그래도 순위가 완전히 같지는 않으므로, 옮기기 전에 **이 순위 차이가 최종 답변 품질을 바꾸는지**를  
   ragas 평가로 한 번 재야 함(이 검증에서는 재지 않음)
3. 순위가 바이트 단위로 같아야 하는 요구가 있으면 지금은 옮기지 않음.  
   Neo4j가 k1을 열어 주지 않는 한 공식 차이는 없앨 수 없음
4. B와 C는 어떤 경우에도 쓰지 않음

## 한계

- **답변 품질은 재지 않음.** 순위 비교만 했고, 순위 차이가 최종 답변의 정확도를 바꾸는지는 확인하지 않음.  
  → 뒤이은 A/B 시험이 `ragas-ab/`에 있음. 검색 지표 4종과 답 없음 문항 거절은 기준과 A가 **같았고**,
  RAGAS도 ContextRecall 1.000으로 같았음. Faithfulness만 숫자가 떨어졌으나 그 차이를 만든 문항이
  기준과 **똑같은 근거**를 써 BM25 탓이 아니었음. 확정하려면 기준을 더 돌려야 함(`ragas-ab/README.md` 참고)
- **적중률이 거침.** 평가 파일에 기대 청크 ID가 없어 출처 문서 이름 단위로만 판정함
- **218건 규모의 결과임.** 문서가 늘면 idf와 평균 문서 길이가 달라져 k1 차이의 영향도 달라질 수 있음
- **V3가 A를 완전히 설명하지는 못함.** k1 1.2와 길이 뭉갬을 넣어도 점수에 최대 3.6% 차이가 남음.  
  남은 차이의 원인은 밝히지 못함(질문의 같은 낱말 중복 처리, 세그먼트별 통계 등이 의심되나 확인 못 함)
- **회원 필터와 열람 등급을 걸지 않음.** 어휘 검색 자체를 보려고 218건 전부를 후보로 둠.  
  Neo4j 전문 검색에 그 필터를 거는 방법(상위 k 자르기와의 순서 문제)은 따로 확인해야 함
- **색인 시간과 저장 용량을 재지 않음.** 후보 A는 토큰을 이어 붙인 속성을 한 벌 더 들고 있어야 함
- **기존 BM25 세대 전환과의 맞물림을 보지 않음.** Neo4j 쪽 세대 분리와 포인터 교체 절차는 설계되지 않음

## 컨테이너 상태

- `docker compose -f neo4j/compose.yml up -d`로 켬. 검증이 끝난 뒤에도 **켜 둔 채로 둠**
- 다른 컨테이너(`opensearch`, `hybrid-ai-lab-rdb` 등)는 켜거나 끄거나 지우지 않음
- 검증이 만든 `BmChunk` 노드와 `bm25cmp_*`, `bm25probe_*` 인덱스는 끝나면 모두 지움. 다른 노드는 건드리지 않음
