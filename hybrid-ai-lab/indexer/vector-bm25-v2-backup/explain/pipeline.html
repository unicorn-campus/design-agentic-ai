STEP 01 · LOAD

파일을 읽는 것보다 중요한 일은
“어떤 문서인가”를 알아내는 것입니다

로더는 확장자만 읽지 않습니다. D3 텍스트를 상담 건별 문서로 분리하고, 상담 ID·날짜·주제 같은 검색 맥락을 메타데이터로 만듭니다. 동시에 구조 줄은 제거 좌표, 개인정보는 치환 좌표로 표시합니다. 이때 원문 자체는 아직 바뀌지 않고 메모리에만 머뭅니다.

입력
D3_S01_신규가입_상담이력_합성.txt
출력
LoadedDocument + 메타데이터 + 원문 좌표
코드
loaders.py:175–242 · _load_consultations()
왜 필요한가요?

파일 안의 여러 상담을 하나로 보면 서로 다른 고객의 맥락이 섞입니다. 상담 건을 문서 경계로 먼저 확정해야 이후 청킹도 그 경계를 넘지 않습니다.

메모리 안의 문서교육용 합성 원문 · 민감 필드 생략 표시

STEP 02 · CHUNK

모델 한도에 맞추되,
의미의 경계를 먼저 존중합니다

한 문서가 길면 검색 질문과 무관한 내용까지 함께 따라옵니다. 우리 분할기는 800토큰을 상한으로 두고, 문서 유형마다 자연스러운 경계를 먼저 찾습니다. D3는 고객:과 상담사:가 시작되는 지점을 우선합니다. 중첩은 최대 200토큰이며 실제 겹침은 경계 위치에 따라 달라집니다.

입력
원문 좌표를 가진 LoadedDocument
출력
RawChunk 목록 · 시작/끝 좌표 유지
코드
splitter.py:36–85 · split()

토큰 ≠ 글자 수 · 청킹과 임베딩이 같은 모델 토크나이저로 세며, 800토큰에는 모델이 덧붙이는 특수 토큰도 포함됩니다.

왜 필요한가요?

너무 크면 질문의 핵심이 흐려지고, 너무 작으면 답의 앞뒤 맥락이 끊깁니다. 상한과 문서 경계를 함께 쓰면 두 위험을 줄일 수 있습니다.

문서 유형별 첫 번째 경계실제 config/document_policies.json
D3 · 발화자 경계고객: 또는 상담사:가 시작되는 곳을 먼저 나눕니다.예: 고객: 같은 요청이 반복돼요. / 상담사: 멈춘 단계를 확인하겠습니다.
CHUNK A

고객: 본인 확인을 마치려는데 같은 요청이 반복돼요.

겹치는 문맥≤ 200 tokens
CHUNK B

고객: 본인 확인을 마치려는데 같은 요청이 반복돼요.

상담사: 원인을 단정하지 않고 보이는 문구와 멈춘 단계를 확인하겠습니다.

그림 읽는 법: A/B는 경계 원리를 보여 주는 설명용 축약입니다. 실제 청크 수와 겹침 길이는 전체 문장과 토큰 계산 결과에 따라 정해집니다.

STEP 03 · CLEAN

좌표를 따라 지울 것은 지우고,
남길 정보는 안전하게 바꿉니다

정제기는 청크 구간과 겹치는 제거·치환 좌표만 적용합니다. 상담 구조 줄은 검색 본문에서 제거하고, 이름·연락처·카드번호 등은 [삭제]로 바꿉니다. 생년월일과 나이는 연령대로 일반화합니다. 정제 뒤에는 잔존 개인정보, 토큰 상한, 메타데이터 스키마를 다시 검사합니다.

입력
원문 좌표를 가진 RawChunk
출력
PreparedChunk + 해시 + 기본 ID
문서 단위 마무리에서 _0000 접미사를 붙여 최종 ID 확정
코드
processor.py:46–92 · process()
왜 필요한가요?

벡터DB와 BM25 corpus는 검색 가능한 저장소입니다. 개인정보를 넣은 뒤 가리는 방식에 기대지 않고, 정해진 정책에 따라 저장 전에 제거·치환해야 합니다.

정제 전후 비교버튼으로 차이를 확인하세요

[접수정보] 고객 식별·연락 정보

고객: 본인 확인을 마치려는데 같은 요청이 반복돼요.

상담사: 원인을 단정하지 않고 보이는 문구와 멈춘 단계를 확인하겠습니다.

고객: 제 이름은 가상 인명입니다.

검증 항목 · 알려진 개인정보 형식 잔존 검사토큰 상한 검사메타데이터 계약 검사

화면의 “고객 식별·연락 정보”, “가상 인명”은 민감 원문을 복제하지 않기 위한 설명용 표기입니다.

STEP 04 · EMBED

문장의 의미를 비교할 수 있는
숫자 좌표 하나로 바꿉니다

임베딩 모델은 정제된 청크 하나를 768개의 숫자로 이뤄진 단일 벡터로 바꿉니다. 비슷한 의미의 문장은 벡터 공간에서도 가까워집니다. 우리 코드는 저장 직전에 L2 노름이 1이 되도록 다시 정규화하고, 값이 유한한지와 차원이 맞는지 검사합니다.

입력
비어 있지 않은 정제 문자열 배치
출력
청크마다 L2 정규화된 768차원 단일 벡터
코드
embedder.py:136–173 · embed()
왜 필요한가요?

사용자 질문과 문서가 같은 단어를 쓰지 않아도 의미가 비슷하면 찾을 가능성이 생깁니다. 아래 Q/A 관계는 유사도를 측정하지 않은 개념 예시이며, 실제 가까움은 모델 벡터로 계산해야 합니다.

의미 공간 미니 지도설명용 2차원 축약 · 실제는 768차원
반복 인증 맥락 점을 선택해 문장을 확인하세요.
[ 0.08, −0.31, 0.17, …, 0.04 ] 설명용 가상 축약 벡터

숫자 배열과 지도 위치는 개념 설명용입니다. 저장된 이전 감사 보고서에서 확인된 값은 차원 768, L2 노름 0.9999999873–1.0000001277입니다.

STEP 05 · STORE

한 번 만든 청크를
두 가지 검색 방식에 연결합니다

Chroma에는 청크 ID, 정제 본문, 벡터, 메타데이터를 함께 upsert합니다. 같은 청크는 별도 경로에서 Kiwi 토큰화와 BM25 색인도 만듭니다. 벡터 검색은 의미를, BM25는 정확한 단어를 잘 찾습니다. 두 저장소를 모두 검증한 뒤에만 활성 세대 포인터를 바꿉니다.

입력
PreparedChunk[] + vectors[]
출력
Chroma 세대 + BM25 검색 파일 + 활성 포인터
코드
index_repository.py:184–215 · upsert()
왜 필요한가요?

벡터만 저장하면 문서의 출처와 접근 등급을 잃습니다. 본문·메타데이터·ID를 함께 보관해야 결과를 설명하고 필터링하며 원문을 추적할 수 있습니다.
