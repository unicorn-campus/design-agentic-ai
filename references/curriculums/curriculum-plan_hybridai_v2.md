## 1. 교육 개요

### 1.1 기본 정보

| 항목 | 내용 |
|------|------|
| 과정명 | 하이브리드 AI 실무 — 생성형 AI · 예측형 AI · 검색 통합 구축 |
| 교육 대상 | 신한카드 엔지니어 · 데이터 모델러 · 기획자 혼합 |
| 인원 | 20~30명 (4~6명 1조, 총 5~6개 조 편성) |
| 교육 형태 | 집합 실습형. 주 1회 4시간 × 10주 |
| 총 시간 | **정규 40시간** (6 Module · 21 Subject · 40차시, 1차시 = 1.0H) |
| 학습 시간 전제 | **정규 40H + 주당 조별 과제 1~2H (총 10~20H) 전제** — 7장 참조 |
| 운영 방식 | 이론 강의 + 개인 실습 + 조별 프로젝트 + 멘토링 + 최종 발표·심사 |
| 실습 데이터 | 교육기관 제작 **카드사형 합성 데이터셋 1벌 공통 사용** (조별 별도 준비 없음) |
| 최종 산출물 | 조별 하이브리드 AI 시스템 1식 + 설명 가능한 응답 서식 + 시연 |

> **주당 과제 1~2H는 권장이 아니라 전제 조건임.** 정규 40시간만으로는 조별 프로젝트가 M4(Graph) 이후
> 누적 지연되며, 각 Module의 `다음 모듈로 넘기는 것` 항목이 과제 시간에 처리되는 것을 전제로 설계함.

### 1.2 수강자 수준 전제

- Python 기초 문법과 실행 경험은 보유한 수준을 기준으로 함
- **LLM · RAG · Graph DB · 온톨로지 · MCP는 첫 경험**인 상태를 표준 난이도 기준선으로 잡음
- 따라서 각 신규 기술은 반드시 `개념 이론 → 설계 실습 → 구현 실습 → 조별 적용 멘토링` 4단 구조로 진입함
- 직무가 섞여 있으므로 조 편성 시 엔지니어 · 데이터 모델러 · 기획자를 각 조에 고루 배치함

### 1.3 직무별 참여 지점

| 직무 | 주 무대 | 밀도가 가장 높은 Module |
|------|---------|------------------------|
| 엔지니어 | 개발 환경, DB·도구 연동, 검색 파이프라인·MCP 서버 구현 | M2 · M3 · M4 · M5 |
| 데이터 모델러 | 스키마, 엔터티·관계 설계, 용어·지표 기준 정의 | M2 · M4 · M5 |
| 기획자 | 문제 정의, 질문 설계, 평가셋, 업무 규칙, 응답 서식, 발표 시나리오 | M1 · M3 · M5 · M6 |

- 기획자 과업은 5장 각 Subject의 `기획자 과업` 항목과 6.5절 역할별 과업 배분표에 명시함

### 1.4 계층 구조와 차시 운영 원칙

- 구조는 **Module(6) → Subject(21) → 차시(40)** 2단 계층임. Day는 운영 회차 번호로만 사용함
- 1개 Day = 4개 차시, 1개 차시 = 1.0H로 고정함. 차시를 1.0H 미만 단위로 쪼개지 않음
- 차시 번호는 `{Day}-{교시}` 형식을 유지함 (예: `4-1`, `9-3`)
- 각 Day의 마지막 차시는 원칙적으로 **실습(멘토링)** 으로 배치해 조별 프로젝트를 그날 안에 한 단계 전진시킴
- 망분리 · 폐쇄망 Local LLM · 민감정보 처리 · 폐쇄망 MCP 운영 주제는 **실습 환경 제약으로 이론 차시로만 편성**함

## 2. 교육 목표 및 기대 효과

### 2.1 교육 목표

**최상위 목표**  
현업 담당자가 평소 쓰는 말로 질문 하나를 던지면, 사내에 흩어진 숫자 · 문서 · 관계 · 예측을 AI가 스스로 모아  
**근거와 출처가 붙은 답**을 내놓는 시스템을, 조별로 10주에 걸쳐 직접 만들어 완성함.

**세부 목표 5가지**

| 번호 | 목표 | 달성 판정 기준 | 담당 Module |
|------|------|----------------|-------------|
| G1 | 문제 유형에 맞는 AI 기술을 골라낼 수 있음 | 임의의 업무 요청 문장을 생성·예측·검색으로 분류하고 근거를 설명함 | M1 |
| G2 | 사내 문서를 검색 가능한 형태로 가공해 RAG를 구축할 수 있음 | 출처가 붙은 응답을 내는 조별 RAG 파이프라인 1식 확보 | M2 · M3 |
| G3 | 업무 개념을 관계망으로 설계하고 Graph RAG로 확장할 수 있음 | 온톨로지 v1 + Multi-hop 검색이 동작하는 조별 그래프 1식 확보 | M4 |
| G4 | 예측 모델을 MCP 도구로 노출해 생성형 AI가 부르게 만들 수 있음 | LLM이 예측 도구를 호출하고 예측값·근거·출처·권고가 함께 출력됨 | M5 |
| G5 | 회사 용어 기준 위에서 최종 판단을 조립할 수 있음 | 지표 정의서 기반으로 동일 질문에 일관된 답이 나오는지 검증 | M5 · M6 |

### 2.2 기대 효과

**조직 관점**

- 근거 · 출처가 붙은 **설명 가능한 AI 응답 체계**를 사내에 이식함. 결론만 내놓는 데모가 아니라
  "무엇을 보고 그렇게 판단했는지"를 남기는 구조가 표준이 됨
- 상담 · 심사 · 리스크 관리처럼 판단 근거를 남겨야 하는 업무에 AI 결과를 바로 얹을 수 있는 형태가 됨
- 이미 운영 중인 예측 모델(이탈 예측, 이상거래 탐지, 연체 위험 등)을 버리지 않고 **MCP 도구로 감싸 재활용**하는
  경로를 확보함. 모델을 다시 만들지 않고 연결만으로 생성형 AI에 붙일 수 있음을 실물로 확인함
- 조별 결과물 5~6건이 "우리 업무의 이 문제를 이렇게 풀었다"는 형태의 동작하는 사례로 남음

**개인 관점**

- 엔지니어: 재사용 가능한 검색 · 도구 연동 파이프라인 코드 뼈대와 MCP 서버 예제를 손에 쥠
- 데이터 모델러: 업무 용어 → 데이터 항목 → 관계 구조 → 지표 정의로 이어지는 정의 체계를 직접 설계해 봄
- 기획자: 각 기술이 무엇을 할 수 있고 무엇을 못 하는지 경계를 파악해, 실현 가능한 AI 요건을 쓸 수 있게 됨

## 3. 커리큘럼 차별성 요소

본 과정은 아래 **2가지 요소**를 축으로 설계함. 그 외 요소는 차별성으로 내세우지 않음.

### (b) 조별 프로젝트 10주 완주형

**정의**: M1(Day 1)에 조별로 풀 업무 문제를 확정하고, M6(Day 10)에 **실제로 동작하는 결과물**로 발표까지
마치는 단일 트랙.

- 매 Subject의 실습이 남의 예제가 아니라 **우리 조 문제를 한 단계 전진시키는 작업**으로 설계됨
- 40차시 중 **11차시가 실습(멘토링)** 으로, 그날 만든 것을 그날 멘토가 점검하고 다음 과제를 확정함
- Module마다 **모듈 산출물**과 **다음 모듈로 넘기는 것**, Subject마다 **이 Subject가 끝나면**을 명시해
  조가 밀리면 그 자리에서 드러나게 함
- 중간 지점(S3.4)에 프로젝트 범위 재조정 Subject를 두어, 과욕으로 인한 미완주를 구조적으로 방지함
- 주제를 자유 발굴이 아니라 **사전 검증된 후보 5개 중 선택 후 각색**으로 제한해, 착수 지연과 실현 불가 위험을 제거함
- 최종 M6는 **발표·심사 전용 회차**로, 완주가 선택이 아니라 일정상 강제되는 구조임

**v1 대비 강화점**: v1은 Day 단위로만 인계 항목을 관리했음. v2는 Module 단위 인계와 Subject 단위 완료 판정을
이중으로 두어, 지연 감지 지점을 10곳에서 21곳으로 늘림.

### (c) 설명 가능한 하이브리드 응답 설계

**정의**: "판단 근거 · 출처 · 예측값 · 한계"가 답변에 함께 나오는 응답 구조를, 마지막에 덧붙이는 것이 아니라
**M1 설계 단계부터 서식으로 고정**하고 매주 버전을 올려 완성하는 방식.

**응답 서식 성장 경로** (v1 그대로 유지)

| 버전 | 확정 시점 | 서식에 담기는 것 |
|------|-----------|------------------|
| v0 | S1.2 (Day 1-4) | 결론 / 근거 / 출처 / 예측값 / 주의사항 — 다섯 칸 골격 합의 |
| v1 | S3.2 (Day 4-4) | + 문서 출처 표기(문서명 · 조항 · 시행일), 근거 부족 시 '확인 필요' 규칙 |
| v2 | S4.4 (Day 7-4) | + 관계 탐색 경로 표기(무엇을 거쳐 이 결론에 왔는지) |
| v3 | S5.2 (Day 8-4) | + 예측값과 확실한 정도, 과잉 해석 방지 문구, 권고 대응 |
| v4 | S5.4 (Day 9-3) | + 업무 규칙 적용 결과와 용어 기준 명시(어느 정의로 계산한 값인지) |
| 최종 | S6.2 (Day 10) | 전 항목이 채워진 응답으로 라이브 시연 및 심사 |

- 모든 조는 매 버전 확정 시 **근거 없는 문장 찾아내기** 점검을 통과해야 다음 Module로 넘어감
- 심사 기준에도 "근거가 답을 실제로 뒷받침하는가 / 출처를 따라가 확인 가능한가"가 포함됨
- 응답 서식의 문안·검수 책임은 기획자에게 두어, 실습 21차시 동안 기획자의 산출물이 끊기지 않게 함

### M3. 뜻으로 찾기 (Vector RAG) (8H · Day 4~5)

**모듈 WHY**: 카드 문의는 같은 뜻을 수십 가지로 표현함("승인이 거절됐어요", "결제가 안 돼요"). 단어가 겹쳐야만
찾아오는 검색으로는 약관·상담 이력에서 맞는 대목을 못 찾음. 이 모듈에서 뜻으로 찾는 검색을 만들고, 찾은 원문을
근거로 답하는 첫 동작 시스템을 손에 쥠. 그리고 처음 만든 RAG는 반드시 틀리므로, 틀린 원인을 검색 단계와 답변
생성 단계로 갈라내고 "얼마나 맞는지"를 숫자로 제시하는 데까지 감.

**모듈 산출물**: 조별 동작 RAG 파이프라인 1식, 청킹 설계서, 평가셋 20건, 개선 전후 비교표, 응답 서식 v1

### M4. 관계로 찾기 (Graph RAG) (8H · Day 6~7)

**모듈 WHY**: 문서 검색은 "무엇이 적혀 있나"에는 강하지만 "누가 무엇과 어떻게 엮여 있나"에는 답하지 못함.
이상거래나 연체 위험은 개별 건이 아니라 회원·가맹점·거래가 이어지는 연결 패턴에서 드러남. 이 모듈은
**S2.4에서 손으로 그려 본 관계 스케치**를 실제 Graph DB로 옮기는 작업이므로, 백지에서 시작하지 않음.
또한 온톨로지도 백지 설계가 아니라 제공되는 **카드사 참조 온톨로지 초안**을 우리 조 질문에 맞게 고쳐 쓰는
방식으로 진행해 진입 난이도를 낮춤.

**모듈 산출물**: 조별 온톨로지 v1, Neo4j에 적재된 관계망 1식, Cypher 조회문 5건,
하이브리드 검색 파이프라인 1식, 응답 서식 v2

### M5. 숫자 붙이고 합치기 (8H · Day 8~9)

**모듈 WHY**: 생성형 AI에게 "이 고객 이탈 가능성이 몇 퍼센트냐"고 직접 물으면 그럴듯한 숫자를 지어냄. 계산은
예측 모델이 하고 설명과 대응 제안은 생성형 AI가 하도록 역할을 나눠 붙여야 함. 이때 붙이는 방식으로
**MCP(Model Context Protocol) 서버**를 씀 — M1에서 개념으로만 배운 AI Agent가 여기서 "LLM이 도구를 골라
부른다"는 실물로 연결됨. 그리고 재료가 다 갖춰져도 부서마다 '활성 고객'이나 '연체'의 기준이 다르면 AI는 매번
다른 답을 내므로, 용어 기준을 못 박은 위에서 최종 답 하나로 조립함.

**모듈 산출물**: 예측 모델을 노출한 조별 MCP 서버 1식, 도구 2개(예측·문서검색) 호출 로그,
비즈니스 용어 사전, 지표 정의서, 통합 동작 시스템 1식, 응답 서식 v3·v4

#### S5.1 예측형 AI 이해와 MCP 서버 구축 (2H · Day 8)

| 차시 | 세부내용 | 방식 | 시간 |
|------|----------|------|------|
| 8-1 | • 판별·예측형 AI와 생성형 AI의 역할 구분<br>• 분류 확률, 예측 스코어, 이상 탐지 결과 해석 연습<br>• 예측 모델 결과를 LLM에 전달하는 구조와 MCP 서버의 역할<br>• MCP 도구 정의 요소(이름·입력·출력·설명)와 LLM의 도구 선택 원리 | 이론 | 1.0H |
| 8-2 | • 스타터 MCP 서버 코드 실행과 구조 확인(도구 등록 · 요청 처리 · 응답 반환)<br>• 이탈 예측 예제 모델을 MCP 도구로 노출(도구 이름·입력 스키마·출력 항목·설명 작성)<br>• LLM 클라이언트에 MCP 서버 연결과 도구 목록 인식 확인<br>• 자연어 질문으로 예측 도구 호출과 호출·응답 로그 확인 | 이론+실습 | 1.0H |

**기획자 과업**: MCP 도구의 `설명(description)` 문구를 작성함. LLM이 언제 이 도구를 불러야 하는지가

**이 Subject가 끝나면**: 조별 MCP 서버가 실행되고 이탈 예측 도구 1개가 등록됨.

### 6.2 사전 검증된 후보 주제 5건

조별로 아래 5건 중 1건을 선택한 뒤, 조원 업무 맥락에 맞게 각색함. 자유 발굴은 허용하지 않음.
5건 모두 공통 데이터셋으로 실제 풀 수 있는지 강사가 사전 dry-run으로 검증한 것임.

| 번호 | 유형 | 예시 질문 | 필요한 재료 |
|------|------|-----------|-------------|
| 1 | 승인·거절 문의 응대 | "이 승인 건이 왜 거절됐고 어떻게 하면 되는가" | 승인 내역(정형) + 약관·규정(문서) |
| 2 | 이상거래 확인 지원 | "이 가맹점과 두 단계 안에 연결된 거래 중 확인이 필요한 건" | 거래·가맹점(관계) + FDS 점수(예측) |
| 3 | 이탈 위험 고객 응대 | "이 고객 이탈 위험이 왜 높고 무엇을 안내해야 하는가" | 이탈 점수(예측) + 상담 이력(문서) + 보유 상품(정형) |
| 4 | 혜택·프로모션 안내 | "이 조건이 어느 카드·어느 업종 가맹점까지 적용되는가" | 프로모션 문서 + 상품·가맹점 관계 |
| 5 | 연체·리스크 안내 | "이 회원의 연체 위험 근거와 규정상 안내 가능 범위" | 연체 지표(정형) + 내규(문서) + 위험 점수(예측) |

**각색 시 확인 사항**

- 결과를 판정할 수 있는가 (성공 기준을 문장으로 쓸 수 있는가)
- 남은 실습 시간 안에 만들 수 있는가 (40시간 중 실습 계열 21시간 기준)
- 하이브리드 구성이 실제로 필요한가 (단일 LLM이나 단순 검색으로 충분하면 각색 방향을 바꿈)

### 7.3 신한카드 측 요청 사항 — 과제 시간 확보

- **업무시간 내 주당 1~2시간의 조별 과제 시간 확보를 신한카드 측에 공식 요청함.**
  본 계획서의 40시간 설계는 Module 간 인계 항목이 과제 시간에 처리되는 것을 전제로 하며,
  이 시간이 없으면 조별 프로젝트는 M3(Day 5) 이후부터 누적 지연됨

**확보되지 않을 경우의 대안**

과제 시간을 확보하지 못하는 경우, 조별 완주 목표를 **M3(Vector RAG 구축·평가·개선)까지로 낮추고**
M4(Graph RAG)와 M5(MCP·시맨틱 레이어)는 조별 구현이 아닌 **강사 시연과 코드 리딩 중심으로 전환**함.
이 경우 각 조는 완성된 참조 구현물을 받아 자기 조 데이터로 실행·관찰하는 수준까지만 수행하며, M6 발표는
"우리 조 RAG 결과물 + Graph·예측 연동 설계안"으로 범위를 조정함. 총 40시간과 차시 구성은 그대로 유지하되,
M4~M5의 실습(멘토링) 차시 6개가 시연·질의응답 중심으로 운영 방식만 바뀜. 이 전환은 S3.4(Day 5) 중간 점검
시점에 판단하며, 그 이전에 과제 시간 확보 여부를 확정해야 함.

### 9.3 원안 대비 주요 판단

- **원안 27차시 주제는 전부 흡수함.** 다만 v2에서 인지부하 감소 목적으로 세부내용 16건을 제거·축소·이동함
  (8.2절). 제거된 것은 주제가 아니라 개별 세부 항목임
- **모듈 2·3에 추가 8시간을 집중한 이유**: 대상자가 LLM·RAG 첫 경험 수준이며, 원안 자체가 "이 시간의 품질이
  다음 모듈 결과를 좌우함"(M2-3), "검색 품질의 절반 이상은 청킹에서 결정됨"(M3-2)이라고 명시함
- **원안 모듈 4·5를 M4 하나로 묶은 이유**: `관계로 찾기`라는 하나의 학습 목표 아래 설계(S4.1·S4.3)와
  구현(S4.2·S4.4)을 교차 배치하는 편이 Graph 첫 경험자에게 흐름이 끊기지 않음
- **원안 모듈 6의 연동 방식을 MCP로 교체한 이유**: 예측 모델을 직접 API로 감싸는 방식보다, 도구를 등록하면
  LLM이 스스로 골라 부르는 구조가 M1에서 배운 AI Agent 개념과 직결되며 재사용 자산으로 남음
- **M6를 통째로 발표에 쓴 이유**: 5~6개 조 × 라이브 시연 + 질의응답에 최소 2시간이 필요하고,
  리허설과 총평·회고까지 포함하면 4시간이 적정 규모임
