## 3. Day별 커리큘럼

이론 주제는 최신 기술 · 아키텍처 · 검증 방법론 세 갈래로 Day 1~2에 배치함.  
Day 3의 배포 실습에 필요한 기술 설명은 별도 이론으로 떼지 않고 해당 실습 시점에 함께 전달함.  
기술 용어의 쉬운 설명은 4절에, 역할별 미션은 5절에 정리함.

### Day 1 · 설계 — 과제 이해와 AI 아키텍처 설계

**주제** — 강사가 사전 수행한 기획 결과를 이해한 뒤, To-Be 프로세스에서 AI로 풀 업무를 팀이 직접 판정하고,
`금융상품 포트폴리오 추천` 업무의 AI 아키텍처를 설계 산출물 7종으로 확정함.

**강사 제공 — 사전 기획 결과 설명**

| 제공 내용 | 설명 |
|-----------|------|
| 가상 금융사 브리핑 | 업종·규모·사업 맥락과 KT에 AX 컨설팅을 의뢰하게 된 배경 |
| 미충족 아웃컴 도출 결과 | JTBD·ODI 진행 과정을 설명하고, 최종 결과인 미충족 아웃컴(고객이 겪는 진짜 문제)과 기회점수 근거를 제시함 |
| 솔루션 탐색·선정 결과 | Design Thinking으로 도출한 해결 방향 |
| As-Is / To-Be 프로세스 | 이벤트스토밍으로 작성한 업무 흐름 전후 비교 |
| PRD · 유저스토리 | 무엇을 만들 것인가의 정의 |
| 프로토타입 시연 | 화면 흐름을 실제로 보여줌. Day 2 프론트엔드 작업의 출발점이 됨 |

**이론**

| 이론 주제 | 한 줄 설명 |
|-----------|-----------|
| AI 적용 적합성 판별 | 이 일을 AI로 풀어야 하는지, 규칙이나 통계로 푸는 게 맞는지 가려내는 기준 |
| 컨텍스트 엔지니어링 | 찾아온 자료를 AI에게 어떤 순서·형태·분량으로 넣어줄지 설계하는 일 |
| MAS 아키텍처 패턴(성능·안정성 등) | 여러 AI 담당자를 어떻게 배치할지. 순서를 사람이 미리 정할지 AI가 그때그때 정할지의 선택과, 그 선택이 성능·안정성에 미치는 영향. 공인 설계 절차 9단계를 프레임으로 제시함(4-4절) |
| 관측 가능성 설계 | 안에서 무슨 일이 있었는지 밖에서 볼 수 있게 기록 지점을 어디에 둘지 정하는 일. 여기서 기록 지점을 잡아 두지 않으면 뒤에서 품질 점수를 낼 데이터가 없음 |

**실습**
- AI 적용 대상 업무 판정 — To-Be 프로세스의 후보 업무 중 AI로 풀 대상을 팀이 직접 판정하고 근거를 제시함.
  강사는 판정 기준만 가이드하고, 팀 판정 후 사전 선정 결과를 공개해 근거를 비교함
- AI 아키텍처 설계 — 아래 7종을 팀이 작성함. 강사는 템플릿과 절차를 제공하고 결론은 제시하지 않음
- Git 저장소 개설 — 설계 산출물을 저장소에 편입해 이후 구현 이력과 이어지게 함
- 강사 순회 리뷰 — 팀별 설계에 대한 피드백

**설계 산출물 7종**

| 산출물 | 무엇을 정하는가 | 왜 필요한가 |
|--------|----------------|------------|
| 목표·품질속성 카드 | 이 시스템의 성공 기준 3개와 우선 품질(정확성·응답시간·설명가능성 등) 3개를 측정 가능한 문장으로 | 이후 모든 설계 결정의 판정 기준. 발표에서 "왜 이 구조인가"에 답하는 근거 |
| 논리 아키텍처 | AI 서비스와 외부 서비스의 관계도. 전체 관계와 내부 구성을 두 단계로 나누고, 개인신용정보가 외부로 나가는 경계선을 표시 | 시스템 전체 그림. 신뢰 경계가 표시되어야 마스킹 지점이 결정됨 |
| 에이전트 역할 계약서 | AI 담당자별로 책임 · **접근 가능한 정보 항목** · 입출력 형식 · 사용 도구 · 사용 모델 · 성공 기준 · 중단 조건 | 가장 중요한 산출물. 권한 경계와 출력 형식이 정해지지 않으면 다음 날 구현에서 담당자 간 데이터가 어긋남 |
| 오케스트레이션 패턴 + 시퀀스 설계 | 여러 AI 담당자를 어떤 방식으로 엮을지 패턴을 고르고 근거를 남김. 처리 순서, 담당자 간 주고받는 데이터 형식, 최종 제안서 출력 형식, 타임아웃·재시도, 동의 상태 확인 지점 | 패턴 없이 그린 흐름도는 구현 시 무한 반복에 빠짐. 제안서 출력 형식 한 장이 화면 연동·품질 측정·추천 근거 제시를 동시에 해결 |
| 지식·도구 설계 | 정형 데이터 접근 경로(NL2SQL), 비정형 문서 검색 방식(벡터 RAG·GraphRAG), MCP 커넥터 목록과 입출력 규격, 민감 필드 분류표 | 마이데이터의 본체는 정형 테이블이므로 접근 경로가 정해져야 추천 근거의 숫자가 맞음 |
| 가드레일·관측 설계 | 시퀀스 위에 겹쳐 그리는 한 장. 단계별로 비용 상한·타임아웃·마스킹을 태그로 붙이고, 기록 지점을 표시. 품질 측정 대상과 문항 수 명시 | 다음 날 "품질 개선" 시간에 어디를 고칠지 찾는 유일한 근거 데이터 |
| 배포 설계 | 배포 단위(이미지 몇 개로 나눌지), 포트, 비밀값 주입 방식, 데이터 저장소 배치 위치 | 3일차 배포의 선행 조건. 이것이 없으면 3일차 오전이 컨테이너 경계 논쟁으로 소모됨 |

**산출물** — 설계 7종 · 개설된 Git 저장소

### Day 2 · 구현 — MAS 구현과 품질 측정·개선

**주제** — 설계를 코드로 옮겨 검색·응답이 도는 상태를 만들고, 품질 점수를 측정해 낮은 지점을 고치는
반복을 수행함. 강사 제공 스타터 리포지토리 위에서 확장하는 방식으로 진행함.

**이론**

| 이론 주제 | 한 줄 설명 |
|-----------|-----------|
| RAGAS | 답변 품질을 네 점수로 재는 방법. 앞의 둘(Precision·Recall)은 검색이 잘됐는지, 뒤의 둘(Faithfulness·Relevance)은 답을 잘 썼는지를 봄 |
| 검증지표 설계 및 개선 방안 | 무엇을 재고, 점수가 낮을 때 어디를 고칠지 정하는 방법 |

**실습**
- 조례와 설계 리뷰 — 전날 설계에 대한 강사 피드백 반영
- 스타터 리포지토리 이해와 기동 확인 — 동작하는 최소 앱에서 출발함(8-1절)
- 정형 데이터 적재와 비정형 문서 색인
- LangGraph로 MAS 구현 — 설계한 역할 분해와 상태 관리를 코드로 옮김
- RAG 구현과 컨텍스트 구성 조정 — 검색 결과를 어떤 순서·형태·분량으로 넣을지 실제로 조정하며 차이를 확인함
- NL2SQL 구현 — 자연어 질문을 SQL 질의로 바꿔 마이데이터 정형 테이블에서 답을 가져오는 경로를 만듦
- 검색 방식 비교 — 같은 질문을 Neo4j GraphRAG와 벡터 RAG 양쪽에 던져 결과 차이를 확인하고 선택 근거를 남김.
  계좌·상품·기관처럼 관계를 따라가야 하는 질문에서 어느 쪽이 유리한지 직접 판정함
- 멀티 LLM 적용 — 작업 성격별로 다른 벤더 모델을 붙이고 결과 차이를 확인함
- 멀티 MCP 연결 — 강사 제공 Mock 서버를 포함해 여러 도구 서버를 조합함
- 관측 기록 심기 — 설계한 기록 지점을 코드에 반영해 측정에 쓸 데이터를 확보함
- 품질 측정과 개선 — 검증 하네스로 반복 실행해 RAGAS 기준선을 잡고, 낮은 항목의 원인을 관측 기록에서
  찾아 검색·컨텍스트·프롬프트·그래프 중 고칠 지점을 정한 뒤 재측정함
- 프론트엔드 연동 — 강사 제공 프로토타입 화면에 API를 연결해 업무 흐름대로 쓸 수 있는 상태로 만듦

**Day 2 종료 게이트** — 컨테이너 이미지 빌드 성공을 통과 조건으로 둠. 배포 위험을 하루 앞당겨 드러냄.

**산출물** — 동작하는 MAS 애플리케이션 · 검증 하네스와 측정 결과 · 개선 전후 비교 · 빌드 성공한 컨테이너 이미지

### Day 3 · 배포·발표 — EKS 수동 배포와 최종 검증

**주제** — 애플리케이션을 컨테이너로 포장해 EKS에 직접 올리고, 배포된 상태에서 품질을 다시 측정한 뒤
과제 이해부터 설계·구현·검증까지의 흐름을 팀별로 발표함.

**이론** — 별도 편성 없이 배포 실습 시점에 컨테이너·쿠버네티스 개념을 함께 다룸. CI/CD 구성은 범위에서
제외하며 수동 배포까지만 수행함.

**실습**

## 4. 기술 범위와 도구

### 4-1. 기술 개념 범위

| 기술 | 한 줄 쉬운 설명 |
|------|----------------|
| LangChain | LLM 호출·검색·도구 사용을 부품처럼 이어 붙여 하나의 처리 흐름으로 만드는 라이브러리 |
| LangGraph | AI의 작업 순서를 그래프로 그려 두고, 상태를 들고 단계 사이를 오가며 실행하게 하는 프레임워크 |
| RAG | 질문에 맞는 자료를 먼저 찾아, 그 내용을 근거로 답을 만들게 하는 검색 결합 방식 |
| GraphRAG | 문서를 지식 그래프로 엮어 관계까지 따라가며 답을 찾는 검색 방식 |
| NL2SQL | 사람이 말로 물으면 AI가 SQL 질의로 바꿔 정형 테이블에서 답을 찾아 오는 방식 |
| MCP | AI가 외부 시스템·데이터에 붙을 때 쓰는 표준 연결 규격. 도구를 갈아 끼우기 쉬워짐 |
| MAS | 큰 AI 하나가 다 하는 대신, 역할이 다른 여러 AI가 나눠 맡아 협업하게 하는 구성 |
| 가드레일 | 비용·응답시간·민감정보 노출을 사전에 막기 위해 각 단계에 거는 제한 장치 |
| 검증 하네스 | 만든 시스템을 같은 조건으로 반복 실행해 결과를 모아 비교하는 검증 실행 틀 |

- `가드레일`과 `검증 하네스`는 서로 다른 개념임. 가드레일은 Day 1 설계 대상, 검증 하네스는 Day 2 구현
  대상으로 구분해 사용함
- RAG는 필수 구현 대상이며, MAS 구성과 NL2SQL도 실제 구현 범위에 포함함
- 사내 시스템 연동은 강사 제공 Mock API로 대체하고, 실제 구현 대상과 구분해 목록화함
- 품질 검증에 사용하는 `RAGAS`는 위 기술 개념 범위와 별개 항목이며 7-2절에서 다룸

### 4-2. Multi-Vendor 범위

### 4-4. MAS 설계 절차 — 이론의 근거

`MAS 아키텍처 패턴` 이론은 확립된 방법론·표준의 **개념을 참조해 재구성한 프레임**임.
아래 표의 참조 대상을 **원문으로 대조**했으며, 확인된 것과 그렇지 않은 것을 구분해 표기함.
9단계 절차를 프레임으로 제시하며, Day 1 설계 산출물 7종이 각 단계에 대응함.

> 대조 결과 전문은 [근거 계보 검증](../../guides/_shared/근거-계보-검증.md)임(2026-08-06 수행).
> 확인 5건 · 부분 확인 3건 · **불일치 5건**이었으며 불일치분을 아래 표에서 걷어냄.

| 계열 | 참조 대상 | 가져오는 것 | 대조 |
|------|----------|------------|------|
| 에이전트 지향 설계 방법론 | Gaia(ACM TOSEM 2003) | 역할 정의에 **권한**(`permissions`)을 포함시키는 규칙 | **확인** — 원문 §4.1.3에 역할의 2대 속성으로 명시됨. 단 Gaia의 권한은 *자원 접근·소비 한도*이며 도구 실행 권한과 뜻이 다름 |

**표에서 걷어낸 주장 3건** — 원문과 어긋나 삭제함.

| 걷어낸 주장 | 원문 확인 결과 |
|------------|--------------|
| `목표 → 역할 → 상호작용 → 조직구조 → 에이전트 → 배치` 뼈대 | Gaia는 **환경 모델**로 시작하며 조직구조가 앞 단계를 되먹임으로 고침 |
| 배치 설계를 독립 산출물로 두는 규칙 | Gaia가 구현·배치를 **명시적으로 범위 밖**이라 선언함(마지막 산출물은 서비스 모델) |
| ATAM이 품질속성 시나리오 **6요소**의 원전 | 원문 Figure 7 템플릿은 **5항목**임. 6요소는 AgentArcEval에 실재하나 출처가 다름 |

9단계: 목표·품질속성 → 시스템 경계 → 단일·멀티 판정 → 역할 계약 → 조직구조·패턴 선정 →
상호작용·상태 → 지식·도구 → 가드레일·관측·평가 → 배치·비용

**9단계는 표준이 아니라 본 과정이 조합한 프레임임.** ATAM에도 9단계가 있으나
`Present the ATAM → Present business drivers → …`로 **평가 워크숍 진행 절차**여서 내용이 다름.
이름이 같아 표준으로 오해되지 않도록 `본 과정 프레임`으로 표기함.
각 단계의 개별 근거는 [근거 계보 검증](../../guides/_shared/근거-계보-검증.md) 및
`references/articles/`의 1차 출처 정리본 11종에 있음.

**(1) 검색·응답 품질 — RAGAS**

**(2) 시스템 품질**

## 9. 5일안(v1) 대비 조정 내역

v1은 `기획·설계·구축·배포 4단계 최소 소요`를 근거로 5일을 산정했고, 3일 구성을 불가로 판단했음.  
4단계는 3일안에서도 유지되며, 5일 산정의 **전제를 교체**하여 3일이 성립함.  
동일 전제로는 여전히 5일이 필요하다는 판단은 유지함.

**교체한 전제 4가지**  
① 케이스·데이터 미확정, 도메인 확정 후 제작 → 사전 확정  
② 기획을 원점부터 수강생이 도출 → 강사 사전 수행·제공  
③ Multi-Vendor 3종을 모두 팀이 직접 구현·비교 → 2종 유지, 1종은 검색 방식 비교로 대체  
④ 선수학습이 전제사항(권고) → 입과 조건

**절감 원장**

| # | 덜어낸 것 | 절감 | 대체 방식 | 잃는 것 |
|---|----------|------|----------|--------|
| 1 | 케이스·도메인 협의 후 제작 | 준비 리드타임 | 마이데이터 케이스·데이터 사전 확정 | KT의 도메인 선택 폭 |
| 2 | 기획 단계 수강생 수행 (시장 정의·아웃컴 도출·솔루션 탐색·프로세스 작성·PRD·프로토타이핑) | 약 1일 | 강사 사전 수행·결과 설명. AI 적용 대상 판정만 수강생 수행 | 문제 정의 훈련 |
| 3 | 아키텍처 원점 설계 | 약 0.3일 | 설계 템플릿 7종 제공. 선택과 근거는 수강생 | 설계 양식 작성 훈련 |
| 4 | 프로젝트 골격 구현 | 약 0.5일 | 스타터 리포지토리·Mock API·배포 템플릿 제공 | 초기 구성 경험 |
| 5 | Microsoft GraphRAG 병행 구현 | 약 0.5일 | Neo4j 단일 구현 + 벡터 RAG와 검색 방식 비교 | 그래프 검색 벤더 비교 경험 |
| 6 | 개선 반복 2회차 이상 | 약 0.3일 | 측정 1회 + 개선 1회 | 반복 개선 사이클 체감 |
| 7 | 팀 간 교차 설계 리뷰 | 약 0.2일 | 강사 순회 리뷰로 대체 | 타 팀 설계 학습 |
| 8 | 선수학습 권고 → 입과 조건 | 약 0.2일 | 사전 진단 + 환경 셋업 사전 완료 | 입과 문턱 상승 |

합계 약 2일분 → 5일 − 2일 = 3일

**유지한 것** — 하나의 고객 과제 3일 관통 · 해결방안과 기술 구성요소의 수강생 주도 결정 ·
멀티 LLM·멀티 MCP 직접 구현 · RAG 필수 구현 · NL2SQL · MAS 구현 · RAGAS 4지표 측정과 개선 ·
컨테이너화와 EKS 수동 배포 · 수료 기준 3종

**추가한 것** — 공인 방법론 기반 MAS 설계 절차 9단계 · 설계 산출물 7종(역할 계약서·배포 설계 신설) ·
금융 도메인 설계 점검 항목 · Day 2 종료 빌드 게이트 · 최소 완주 하한선
